# Web application

Next.js App Router lives in `app/`; `components/` and web-specific `lib/` hold presentation and request adapters. Root `lib/contracts/` is browser-safe; root `lib/server/` is privileged shared source. eve is a peer service, composed through root `vercel.ts`; do not add `eve/next` to this frontend.

From the repository root, use `npm run dev:web`, `npm run build:web` and `npm run start:web`. Use `npm run dev` for the composed web/eve service graph. `npm run check` includes app types; `npm run test:runtime` checks built routes and security headers.

`/app` supports Google-only sign-in, waitlist submission, invitation redemption and sign-out. `POST /api/browser/auth/start` accepts an empty JSON object and returns the Supabase Google authorization URL, with identity-only scopes and explicit account selection. Email login submissions are rejected. `/auth/callback` exchanges the PKCE code in the initiating browser and returns to `/app`. Auth and refresh credentials stay in HttpOnly, SameSite=Lax cookies, Secure on HTTPS; all session refreshes happen in Route Handlers and are attached to their response. The server verifies the original access token and current database session before protected operations. No browser Supabase client or local-storage session is used.

`/booking/[bookingId]` exchanges a private `#token=…` fragment for a request-specific HttpOnly cookie and immediately removes the fragment. The ID alone unlocks nothing. Closed requests expose only the permitted status/receipt projection. Private APIs use `private, no-store`; public page shells contain no personalized data. Admitted hosts and active requesters can send and replay their authorized conversation. Google Calendar connection and disconnect are available through protected in-chat controls. Host calendar choices can be explicitly confirmed in chat. Requester calendars can be selected and checked, and explicit manual windows can replace Calendar dependence. Full feasibility, proposal actions and booking controls remain under implementation.

`/{handle}` starts manual account-free intake with name, email, purpose, duration and an editable browser-detected IANA timezone. Unresolved dates/mode/place remain gathering. Profile and creation perform fresh Calendar metadata checks; the server rechecks account/admission, settings revision and connection generation afterward. `/api/browser/intake/{profile,bind,resume,create,new}` returns only public profile or minimal continuation fields. A separate per-handle HttpOnly proof is established before submission; its non-secret attempt identifier prevents stale tabs from using a replacement attempt. Only hashes enter SQL, and successful creation installs the existing request cookie before navigating to `/booking/[bookingId]`. Same-proof retries and reload recovery return the same request even during a later Calendar outage. Explicitly starting another request preserves the earlier receipt cookie. Transient failures preserve proof; revoked/expired proof is cleared for an explicit fresh retry. No request token enters a URL, browser storage, model input or JSON response. Optional Google identity/prefill, verified-contact recovery and complete negotiation/booking remain open; manual contact is not verified by submission.

For the local browser journey, start disposable Supabase, install Chromium with `npx playwright install chromium`, then run `npm run build:web` and `npm run test:browser`. The test starts its own port-3000 server and isolated eve instance with a deterministic model, uses local Auth/Mailpit and removes its synthetic database/Auth fixtures. Stop any other server on that port first. CI installs Chromium and runs the same journey.

Target origin: `https://release.findmeatime.com`. Canonical local origin: `http://localhost:3000`. Environment files are app-root-relative in standalone Next.js; provide shared secrets through the process environment or composed Vercel development configuration. Never prefix server secrets with `NEXT_PUBLIC_`.

The browser uses `/api/browser/conversations` as a cookie-authenticated gateway to the application-owned eve routes. It forwards only verified host tokens or the matching request cookie, never arbitrary destinations or runtime control paths. In standalone local development, set `EVE_LOCAL_ORIGIN` to the loopback eve origin; production uses the composed `APP_ORIGIN`. NDJSON replay advances an absolute cursor, deduplicates events, replaces provisional text with completed blocks and retries an uncertain send using its original message ID. Access revocation aborts the stream and removes the visible transcript. Credentials, grants and runtime session IDs stay out of browser JavaScript; no conversation is cached in local storage. Shared messages use a neutral participant label until attributed channel presentation is implemented.

Chat primitives are shadcn `radix-nova` (`@shadcn/react` 0.3.1) with the AI Elements suggestion component and Tailwind 4.3.3. The selected `b6rtA2Hmi` theme uses olive neutrals, green actions and self-hosted Inter through `next/font`; semantic tokens also style the landing/Auth shell. `components.json` records paths under `apps/web`; use the `@web` alias when adding components.

Calendar browser routes are `GET /api/browser/calendar/status`, `POST /api/browser/calendar/start` and `POST /api/browser/calendar/disconnect`. Host authority comes from the current Auth session; a supplied request ID selects only its matching request cookie. Consent uses random single-use state, S256 PKCE, an OIDC nonce and a ten-minute HttpOnly browser-binding cookie. `/connections/google/callback` verifies the original authority again before saving encrypted credentials and returns to the fixed host/request path. Return query strings never establish a connected state; the card confirms it through the status endpoint. Connect permission is separate from calendar selection, settings confirmation and booking.

Host-only `GET /api/browser/calendar/list` returns current authorized metadata and saved choices; `POST /api/browser/calendar/select` accepts only the strict choice/revision contract. The server fetches Google permissions again before saving, rejects read-only destinations and never substitutes the primary calendar. Refresh preserves encrypted credentials and uses compare-and-swap; current Auth, grant generation and setup revision fence results after provider calls. Reconnect resets selections. Failed metadata reads show retry/reconnect without replacing confirmed choices with an empty result. Metadata is visible only to the authorized browser, not sent to the model. The list has a 15-second total deadline and at most ten 250-item pages; refresh has a ten-second deadline without automatic retries.

Requester-only availability routes use the matching request cookie: `GET /api/browser/availability/status`, `GET /api/browser/availability/list`, and `POST /api/browser/availability/select`, `/manual`, `/check`. Listing exposes only calendar metadata; a check returns a safe completion notice without raw busy intervals. Calendar failures persist a scheduling pause; a successful fresh retry clears it. Manual confirmation saves windows/timezone and removes the local Calendar grant atomically. Local wall-clock input uses Temporal 0.5.1 with IANA timezone validation and rejects repeated/nonexistent DST times. Disconnect alone does not assume manual availability.

Host setup is a private card inside `/app`. `GET /api/browser/setup/read` returns current draft/review state; protected POST actions `/draft`, `/rebase` and `/confirm` edit, refresh and explicitly confirm it. `/progress` remembers host skip/dismiss/re-offer choices with current revision and idempotency guards. The shared guide presents the next question, schedule defaults with use/adjust/manual actions, and separate transportation/extra-buffer steps. Dismissed schedule defaults stay blank in missing form fields after reload. Profile, weekly windows, timezone, meeting mode, locations and travel have structured controls that remain usable without a model response. Defaults are labeled; the optional analysis card provides selected-calendar suggestions. Online-only hides physical travel; switching back requires fresh explicit physical choices. An uncertain submission retains the original payload/idempotency key until retry or explicit reload. A rules/calendar version change invalidates the old review; **Refresh my draft** preserves answers and provenance before a new review. Confirmation checks fresh Google permissions and database revisions before saving. Settings confirmation does not certify a working public link, iMessage linking or booking readiness.

The private Calendar suggestions card uses `GET /api/browser/analysis/read` and POST `/start`, `/apply`, `/dismiss`. A host explicitly selects calendars, dates and timezone before scanning; analysis does not change conflict/booking choices. Results show scope, evidence limits, text weekly windows and private unconfirmed places. A failed read offers reload/retry/manual editing and never means free time. Applying fills only missing nonexplicit schedule preferences in a draft; mode/location/travel still need explicit choices and final settings confirmation. Status refreshes every 30 seconds without another provider read. The same dismissed evidence stays dismissed on later scans.

Calendar review has focused editable windows, explicit mode and private place-candidate steps, followed by one draft application. No mode/place is preselected; existing explicit answers are reused. The setup source disclosure retains Calendar/default origins across unrelated edits and reload. Guided default actions send bounded `starterFields`; raw origin metadata cannot be supplied by the client.

Protected iMessage backend routes are `GET /api/browser/imessage/read` and POST `/bind`, `/start`, `/verify`, `/cancel`, `/skip`, `/unlink`. They require the current admitted host; POSTs also require the application origin. Call `bind` first to establish the HttpOnly, Secure-in-production browser proof, then start with an E.164 phone and immutable request key. Verify accepts a six-digit code, challenge ID and immutable attempt key. Codes never enter eve, response state or persisted browser cards. State contains masked phone numbers and authoritative challenge/link status. A separate login session or browser cannot complete a challenge. After settings confirmation, `IMessageLink` renders Connect/Maybe later, phone entry, protected code entry and a masked connected summary inside the existing chat. It polls current status while visible and on window focus, with stale-read fencing across mutations. Lost responses retain the immutable start/attempt identity in memory; the raw code clears on submission and reload. Requesting a new code requires re-entering the number; change-number cancels the old challenge. Explicit unlink requires confirmation. Disabled provider configuration offers web continuation. This UI does not establish live delivery or linked conversational processing.

The preset’s light-mode muted foreground is darkened to OKLCH lightness 0.54 so small helper text reaches at least 4.5:1 against both white and muted surfaces. The latest-message control occupies its own chat footer, with a 44px target, so it cannot obscure inline actions. The message-scroller primitive continues to own scroll state and inactive-control behavior.


### Incoming private iMessage links

`/app#imessage=<id>.<token>` strips its fragment immediately and exchanges it after establishing a separate HttpOnly browser proof. A bounded HttpOnly continuation cookie survives sign-in and invitation redemption. Before admission, only the masked original number and next sign-in action appear. Once admitted, an inline **Send verification code** action is available before settings confirmation. It sends a fresh OTP to the immutable originating conversation, capped by the original fifteen-minute entry deadline. Browser, Auth session, receiver, expiry and revocation are rechecked server-side. Codes stay outside chat/model/storage; token possession cannot grant host access. Skip/cancel/link completion clears the continuation cookie. A lost exchange can retry by reopening the original private link in the same browser; a transferred link cannot rebind to another browser.


### Booking confirmation email

The protected receipt shows the organizer returned by Google, separately from the transactional sender. Email-only requester links at `/booking/[bookingId]#receipt=<token>` exchange for an HttpOnly receipt cookie, clear the fragment and work after reload without granting conversation or scheduling access. Host **View booking** links select the request in `/app?request=<id>`. Receipt access ends on original credential expiry, rotation or verified-recipient change.

`POST /api/internal/booking/delivery` is a server-secret-only worker entrypoint. It uses the frozen Cloudflare adapter and encrypted SQL ledger; never call it from a browser or retry a possibly dispatched message manually. Configure its separate Vault wake-up URL only after inspecting pending work. See [provider setup](../../documentations/technical_specification/03_provider_setup.md#booking-confirmation-email-worker).

Requester contact verification lives in the protected booking conversation. `/api/browser/contact-verification/state`, `/start` and `/confirm` use the request guest cookie, strict contracts and no-store responses; POSTs require same origin. The code field bypasses chat and keeps pending retries only in component memory. The separate secret-authenticated `/api/internal/contact/delivery` worker sends frozen Cloudflare messages. See the [provider setup](../../documentations/technical_specification/03_provider_setup.md#requester-verification-email-delivery) for scheduler configuration.

Optional requester identity uses `/api/browser/requester-identity/state` and same-origin `start`, `skip`, and `apply` commands, with intake-attempt or current guest cookies. The existing Google callback recognizes an `identity.` state marker and a separate HttpOnly binding cookie; it never falls back to Calendar or host login after identity failure. Public intake restores its saved draft and editable prefill. Existing requests require an explicit matching-recipient proof action. Provider credentials, codes and identity are absent from browser storage and conversation messages. Live Google/iPhone acceptance remains separate from signed HTTP fixtures.

The optional `fmat-display-timezone-v1` session-storage entry contains only the user's display timezone. It preserves the tab's explicit choice through reloads and provider returns; no authentication or identity material is stored there. Candidate display changes do not submit scheduling commands.

Public agent entry: `GET /SKILL.md` returns host onboarding instructions; `GET /{handle}/SKILL.md` returns requester instructions after the same current readiness/Calendar checks as intake. Both support HEAD, return UTF-8 Markdown with an instruction version and no-store headers, create no cookies, and use only configured-origin links. Host fields are encoded data. Unknown/unavailable targets return neutral 404 and transient failures return sanitized 503 with Retry-After. The current release offers browser continuation while protected agent tooling remains under implementation.
