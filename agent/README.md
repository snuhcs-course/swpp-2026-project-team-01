# Agent runtime

This is the eve agent source root. `agent.ts` selects direct OpenAI `gpt-6-luna`, explicit context-window metadata, low reasoning and bounded session usage. `instructions.md` describes scheduling authority and privacy; deterministic authorization and approval must remain in application code.

- `tools/`: thin adapters to authorized operations in `lib/server/`.
- `channels/`: eve web/messaging integration with verified application identity.
- `connections/`: supported eve connection definitions when required.

Run `npm run dev:eve`, `npm run build:eve` or `npm run start:eve` from the repository root. eve loads the root environment. `OPENAI_MODEL=gpt-6-luna` is required; runtime model calls additionally require server-only `OPENAI_API_KEY`. `npm run verify:model` verifies direct-provider structured tool generation using synthetic input. No gateway or subscription fallback is configured.

`channels/eve.ts` denies every caller of the default session API. `channels/conversations.ts` exposes application-owned open, snapshot, message and stream routes under `/api/conversations`, authenticated by host bearer tokens or request credentials. The public health endpoint remains available. Default tools, subagent dispatch and shared memory are not enabled. Sandbox preparation still follows eve defaults; local builds need Docker.

Separate eve and Next.js builds are composed by root `vercel.ts`. Managed Vercel Workflow persistence is the selected deployed topology. Local process-kill, revocation and repeated-tool checks pass, and a protected managed preview verifies post-commit worker termination and recovery. See the [managed acceptance](../documentations/technical_specification/05_rebuild_evidence.md#managed-workflow-recovery-acceptance--2026-10-10) for exact scope and cleanup. Complete Phase 1 and live-provider gates remain tracked separately. No separate worker or Photon bridge is introduced before compatibility evidence requires it.

The first authored tools read the current request/setup, save host-private notes and propose requester-reviewed detail drafts. They use `ctx.session.auth.current`, never the session initiator, and delegate to the atomic conversation-tool RPC. They cannot confirm policy, agreement, approval, travel exceptions or provider outcomes. The message inbox freezes accepted input and binds one canonical runtime session. Current authority is checked at delivery, before each streamed event, every two seconds while idle, and inside each tool transaction. Streams expose text and safe lifecycle events, with a cursor for reconnect; raw tools, reasoning and auth metadata are suppressed.

Runtime execution now carries the immutable `ctx.session.id` to SQL, where it is matched to the current scope and private generation ledger. Tools (including both sides of readiness-provider I/O), model reservations, delivery and settlement reject retired identities under the same runtime advisory lock used by recovery. The legacy four-argument tool RPC remains compatible only for generation zero; identity-free calls fail on recovered scopes. Generation-zero delivery enrolls its canonical binding. A generation awaiting a successor cannot bind through ordinary delivery or be claimed by the ordinary dispatcher. Dispatcher acknowledgments are checked against the generation captured by their lease. These are local recovery foundations; the explicit recovery endpoint, leased successor creation and production activation remain pending.

Retry keys use conversation, accepted-message ID and operation, allowing at most one mutation of each kind per message even when a crashed model step regenerates tool-call IDs. Same-key changed payloads conflict. One message may be pending per conversation; the lifetime inbox cap is 200 messages. New input also consumes the shared principal/service admission budget described in the [operations policy](../documentations/technical_specification/01_backend_architecture.md#conversation-admission-limits). Accepted exact retries do not consume another allowance; temporary throttling never creates a replacement session. A terminated canonical workflow cannot silently be replaced. A leased dispatcher recovers accepted-but-undispatched input and retries uncertain delivery. Supabase Cron wakes the authenticated `/api/internal/conversations/dispatch` endpoint only when due messages exist; the original grant is checked again before sending. Browser credential exchange and protected conversation replay are implemented; remaining runtime controls and full scheduling operations are pending.

See the [source organization](../documentations/technical_specification/02_frontend_architecture.md#source-organization), [implementation plan](../documentations/technical_specification/04_implementation_plan.md) and [evidence ledger](../documentations/technical_specification/05_rebuild_evidence.md).

`update_setup_draft` accepts one bounded partial preference update per accepted message through the shared conversation-tool authorization. `read_context` with `context: "setup"` supplies draft/review/next-action state. Assistant proposals preserve uncertainty and cannot replace explicit host choices. Human-only controls record applicable mode/location/travel answers, refresh a stale draft and confirm the exact review. These operations create no proposal approval or booking effect. Deterministic fixtures verify guided review and linked iMessage continuation; live Google/iPhone acceptance remains open.

`read_context` accepts `setup_analysis` for current private, minimized Calendar suggestions. It reveals dates/timezone/calendar count, derived windows and fixed evidence limits, excluding calendar IDs and observed locations. Scan consent and suggestion application/dismissal remain protected browser actions. The agent must label defaults, respect explicit choices and avoid repeating dismissed/stale/failed results; no scan establishes booking availability or approval.

Final assistant output is retained in the channel checkpoint and included in runtime settlement. Only accepted linked Photon inputs create a private reply intent; web turns do not. Settlement and SQL outbox creation are atomic, so database failure leaves an input recoverable through the existing sweep. Repeated delivery of a completed checkpoint settles its saved output without invoking the model again. The separate reply worker rechecks current private authority and never resends an uncertain intent. See [reply recovery](../documentations/technical_specification/03_provider_setup.md#private-reply-recovery).

Model selection uses the shared `conversationModel` factory and durable [execution allowance](../documentations/technical_specification/01_backend_architecture.md#model-execution-allowance). Every actual provider attempt, including compaction and retries, requires current accepted-input authority and reserves before network execution. Restart retains earlier charges. Input above 128 KiB fails safely even though the native model context is larger; context is never silently truncated to bypass this bound. Failed turns preserve committed commands and settle through the normal channel path. Browser failure feedback survives reconnect/reload while structured settings remain available.

`read_context` also accepts `setup_readiness`. It first reads setup under the current conversation grant, checks the public profile and live Calendar metadata, then repeats the private grant/revision checks. Only a current ready result returns canonical booking and agent-instruction URLs. The model cannot choose a host or URL. Missing access returns not-ready; provider errors, stale revisions or revoked private authority fail without links. Readiness cannot confirm policy or create booking work.

## Runtime authorization inventory

The current application runtime exposes six routes in `channels/conversations.ts`. The browser gateway accepts only open, snapshot, message and stream operations, derives credentials from the matching HttpOnly session/request cookie and strips caller headers and runtime-only response fields. Root `vercel.ts` routes these application paths to eve; the default session API has no authenticators.

| Route | Authority and continuation checks |
|---|---|
| `POST /api/conversations` | Verified host or request credential; strict audience/resource input; current SQL access and scope binding. |
| `GET /api/conversations/:conversationId` | Current credential and execution grant; authorized message inspection; no runtime session/grant identifier in projection. |
| `POST /api/conversations/:conversationId/messages` | Current scope/grant, immutable accepted input and retry key; canonical session/generation verification before delivery. |
| `GET /api/conversations/:conversationId/stream` | Current scope/grant and stored session; recheck before each projected event and during idle waits; bounded lease and absolute cursor. |
| `POST /api/internal/conversations/dispatch` | Dispatch secret, inbox lease bound to a generation and current execution grant; old acknowledgments cannot settle successor work and unbound recovered scopes await explicit successor dispatch. |
| `POST /api/agent/conversations/read` | Resource-bound agent token and current scoped grant; audience-bound encrypted cursor; authorization before and after buffered history reads. |

Provider ingress routes live in the web service and reach runtime only through their separately authorized durable adapters.

Six authored tools use `ctx.session.auth.current` and the atomic `ConversationTools` boundary: `read_context`, `update_setup_draft`, `save_private_note`, `propose_request_details`, `list_host_requests` and `propose_host_revision`. Navigation is read-only and never selects a request. Host revisions create private drafts and cannot apply changes; authored web/iMessage controls own explicit human review. Reads select only the bound setup/request; mutations derive retry identity from conversation/message/operation and enforce current audience, revision, grant and immutable runtime generation in SQL. No tool confirms settings, participant agreement, approval or provider success. Shared runtime memory, default tools and subagent dispatch remain disabled.

The [foundation runtime audit](../documentations/technical_specification/05_rebuild_evidence.md#foundation-runtime-access-acceptance--2026-10-09) records real-process restart, route-denial and browser isolation evidence. The managed diagnostic adds hosted post-commit recovery; production-load recovery targets and live provider/client acceptance remain separate release gates.

The isolated [managed recovery fixture](../tests/managed/README.md) uses the production channel and command boundary with a deterministic model and a scoped post-commit worker termination. It must only run in a diagnostic preview, never the release agent. The dated acceptance links source, deployment, managed crash logs, database readback and exact cleanup; source/build alone cannot establish hosted recovery.
