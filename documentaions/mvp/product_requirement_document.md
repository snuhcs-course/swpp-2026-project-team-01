# PRD — AI 미팅 예약 (가칭)

작성일: 2026-09-29 · 상태: 확정 (2026-09-29, [검토] 항목은 제안안으로 채택) · 근거: `one_pager.md`


---

## 1. 목표 / 비목표

**목표**
- G1. 두 사람의 캘린더, 가능 시간 규칙, 이동시간 규칙으로 60일간 예약 가능한 슬롯을 정확히 계산한다.
- G2. 클라이언트가 자연어 대화만으로 원하는 슬롯을 찾는다. AI는 필터를 만들고 대화를 이끌며, 슬롯 판정과 순위는 코드가 한다.
- G3. 요청 → 수락/거절 흐름을 끝까지 시연할 수 있다.

**비목표 (MVP)**
- Google Calendar 연동, 실제 이동시간 API, 근무시간 규칙
- AI의 자동 예약 전송, 호스트용 AI
- 인증, 알림(이메일/푸시), 외부 에이전트용 API
- 다중 타임존

## 2. 용어

| 용어 | 정의 |
|---|---|
| 일정(Event) | 캘린더 항목. 시작, 끝, 장소(회사 / 장소명 / 온라인 / 없음) |
| 가능 시간 규칙 | 요일별로 미팅에 있을 수 있는 시간대. 기본값은 매일 08:00–22:00 |
| 장소(Place) | 호스트가 등록한 미팅 장소. 종류: 회사 근처 / 특정 장소 / 온라인 |
| 미팅 양식(MeetingType) | 호스트가 정한 이름과 길이 |
| 슬롯(Slot) | (시작 시각, 장소, 미팅 양식). 양쪽 모두 이동시간을 포함해 가능한 조합 |
| 필터(Filter) | 반드시 조건 + 선호 조건(강/약)의 집합 |
| 요청(Request) | 슬롯 + 메시지. 상태는 pending / accepted / declined |

## 3. 기능 요구사항

### 3.1 사용자 · 데이터
- **FR-1** 시드 사용자 여러 명이 있고, 상단에서 현재 사용자를 전환한다. 로그인은 없다.
- **FR-2** 사용자마다 시드 캘린더(오늘부터 60일)가 있다.
- **FR-3** 사용자는 자기 캘린더를 조회하고, 일정을 추가·삭제할 수 있다.
- **FR-4** 사용자는 요일별 가능 시간 규칙을 수정할 수 있다.
- **FR-5** 호스트는 장소(3종)와 미팅 양식(이름, 길이)을 추가·수정·삭제할 수 있다.
- **FR-6** 클라이언트는 호스트 목록에서 예약할 호스트를 고른다. 예약 링크(`/book/{host}`)는 이후 확장.

### 3.2 슬롯 계산 (코어, 결정적)
- **FR-10** 범위는 지금 이후 ~ 60일이다. 시작 시각은 30분 간격이고 시간대는 Asia/Seoul이다.
- **FR-11** 가능 시간 규칙 밖은 바쁜 시간으로 처리한다. 규칙 경계에는 이동시간을 붙이지 않는다.
- **FR-12** 미팅 앞뒤로 가장 가까운 **오프라인 일정**과의 간격이 이동시간 이상이어야 한다. 온라인 일정은 겹침 검사에만 쓰고, 이동의 기준점으로는 쓰지 않는다.
  - 호스트: one_pager 4.3의 표를 따른다.
  - 클라이언트: 오프라인 1시간, 온라인 0분.
  - 같은 장소는 0분이다.
  - 장소가 없는 일정은 "회사 외 장소"로 본다.
- **FR-13** accepted 요청은 양쪽 캘린더의 일정으로 계산에 반영한다. pending 요청은 반영하지 않는다.
- **FR-14** 슬롯 계산은 순수 함수이고, 이동시간 표의 모든 칸을 단위 테스트로 검증한다.
- **FR-15** 최소 사전 예약 시간. 지금으로부터 N시간 이내 슬롯은 제외한다. N=2.

### 3.3 대화 · 필터 · 순위
- **FR-20** 클라이언트가 호스트를 고르면 대화 화면이 열린다. 대화는 (클라이언트, 호스트)마다 하나씩 유지된다. 대화는 서버에 저장되어 새로고침해도 유지된다.
- **FR-21** 한 턴에 LLM을 두 번 호출한다(`user_flow.md` F4).
  - ① 해석 호출
    - 입력: 대화 내역, 현재 필터, 오늘 날짜, 호스트의 장소·양식 목록, **직전에 보여준 버튼**(상대 표현 해석용)
    - 출력: JSON(필터 변경분, `showOptions`)
  - 코드가 필터를 적용하고 결과 요약을 만든다. 요약은 남은 개수, 주·요일·시간대·장소·양식별 분포, 최고점 동점 수다.
  - ② 응답 호출
    - 입력: 대화 내역, 새 필터, 새 요약, 버튼 표시 여부, 이번 턴에 바뀐 조건, **선택 근거**(코드가 계산)
    - 출력: 응답 문장
  - **슬롯 목록 자체는 LLM에 넣지 않는다.**
- **FR-22** ① 해석 호출의 출력은 스키마로 검증한다. 실패하면 1회 재시도하고, 그래도 실패하면 필터를 바꾸지 않은 채 칩으로 직접 조정하라고 안내한다. 이때 **AI 서비스에 닿지 못한 경우("AI 응답 불가")와 모델 출력을 쓸 수 없었던 경우("해석 실패")를 구분**해 각각 다른 배너를 보이고, 전자에서는 ② 호출을 건너뛴다. ② 응답 호출이 실패하면 코드 템플릿으로 요약 문장을 만든다. 호출 하나의 제한 시간은 20초다.
- **FR-23** 필터 항목은 날짜 범위, 요일, 시간대, 장소, 미팅 양식, 빠를수록/늦을수록, 앞뒤 여유다. 정렬은 항상 **날짜가 가까운 순**이 먼저이고, "빠를수록"은 같은 날 이른 시각부터, "늦은 시각 우선"은 같은 날 늦은 시각부터다. 가장 먼 날짜를 뜻하지 않는다. 세기는 반드시 / 강 / 약이고, 코드가 고정 가중치로 바꾼다.
- **FR-24** 같은 종류의 조건은 새 것으로 바꾸고, 다른 종류는 더한다.
- **FR-25** 현재 필터를 칩으로 표시한다. 사용자가 칩을 지우면 즉시 다시 계산한다.
- **FR-26** 동점일 때는 이른 시각 순으로 정렬한다.
- **FR-27** 버튼 표시 조건은 셋 중 하나다: `showOptions`, 3위가 확정됨, 남은 슬롯 ≤3. 조건을 만족하면 상위 최대 3개를 표시한다. 후보는 **서로 다른 시간**이어야 한다: 같은 날 이미 고른 후보와 시작 시각이 60분 미만 차이 나는 후보(같은 시각의 다른 장소·양식 포함)는 건너뛰고, 모자라면 순위 순으로 채운다.
- **FR-27a** 상대 표현("조금 더 늦은/이른 시간")은 정렬이 아니라 시간대 조건으로 바꾼다. 기준은 직전에 보여준 버튼이며, 보여준 것이 없으면 조건을 바꾸지 않는다. "N시쯤"은 N시 30분 전부터 1시간 뒤까지로 해석한다.
- **FR-27b** 방금 보여준 것과 같은 버튼은 사용자가 다시 요청한 경우가 아니면 반복해서 띄우지 않고 "직전과 같다"고 안내한다. 사용자가 다시 요청했는데 같으면 다시 보여주되 왜 같은지 설명한다. 이전 버튼은 화면에 남아 있다.
- **FR-28** 버튼은 한 줄 형식이다: `M월 D일(요일) HH:MM · 장소 · 양식`
- **FR-28a** 버튼과 함께 AI는 **어떤 기준에서 어떻게 골랐는지**를 1~3문장으로 설명한다: 이번 턴에 반영한 조건, 반드시/선호 조건, 정렬 기준, 후보를 서로 다른 시간으로 골랐는지, 후보가 못 맞춘 선호. 근거는 코드가 계산해 넘기고 LLM은 그 밖의 이유를 만들지 않는다. LLM을 쓸 수 없으면 같은 근거로 만든 템플릿 문장을 쓴다.
- **FR-29a** 후보가 많아 되묻는 경우, 미팅 양식이 아직 정해지지 않았고 호스트에게 양식이 둘 이상이면 **미팅 길이를 가장 먼저 묻는다.**
- **FR-29** 남은 슬롯이 0개면 조건을 하나씩 풀었을 때 몇 개가 생기는지 계산해 LLM에 넘기고, LLM이 이를 안내한다.

### 3.4 요청
- **FR-30** 버튼을 누르면 슬롯이 고정된 요청 폼이 열린다. 메시지는 사용자가 직접 입력한다(필수). 최대 500자.
- **FR-31** 전송 시 서버가 다시 검증하고, 실패하면 이유를 보여준 뒤 대화로 돌아간다.
  - 슬롯이 여전히 가능한가
  - 이 클라이언트의 다른 pending 요청과 시간이 겹치지 않는가 (호스트 무관)
- **FR-32** pending은 슬롯을 막지 않는다. 여러 클라이언트가 같은 시간에 요청할 수 있다.
- **FR-33** 클라이언트는 자기 요청 목록과 상태를 볼 수 있다.
- **FR-34** 클라이언트가 pending 요청을 철회할 수 있다.

### 3.5 호스트 요청함
- **FR-40** 호스트는 받은 요청 목록을 본다(상태별). 같은 시간대에 들어온 요청은 묶어서 보여준다.
- **FR-41** 수락/거절.
  - 수락할 때 다시 검증한다. 그사이 캘린더가 바뀌어 불가능해졌을 수 있으므로, 불가능하면 수락을 막고 이유를 보여준다.
  - 수락하면 시간이 겹치는 다른 pending 요청은 자동으로 거절된다.
  - accepted 요청은 양쪽 캘린더에 일정으로 추가된다.
- **FR-42** 거절하면 해당 클라이언트는 그 시간에 다시 요청할 수 있다.
- **FR-43** 시작 시각이 지난 pending 요청은 만료 처리한다(표시만).
- **FR-44** accepted 요청의 취소는 MVP에서 제외한다.

## 4. 비기능 요구사항
- **NFR-1** 슬롯 계산(2명 × 60일)은 1초 이내.
- **NFR-2** 대화 한 턴 응답은 p50 3초 이내. gemma4:31b 1회 실측 0.72초 기준, 결과 요약 포함 시 변동 가능.
- **NFR-3** LLM 장애 시에도 칩 편집, 목록 보기, 요청 기능은 동작한다.
- **NFR-4** API 키는 서버에만 둔다. `.env`는 저장소에 커밋하지 않는다.
- **NFR-5** LLM은 교체할 수 있다(모델명은 env로 지정). 어댑터는 kibitzer `ollamaChat.ts`의 `postChat`을 이식한다. 코드펜스로 감싼 JSON 응답도 파싱한다.
- **NFR-6** 한국어 UI.
- **NFR-7** 서버는 대화 한 턴마다 해석·응답 호출의 지연시간, 재시도 횟수, 실패 종류, 폴백 여부, 남은 후보 수, 버튼 표시 사유를 JSON 한 줄로 로그에 남긴다. 예약 상태 변경과 거부 사유도 남긴다. **메시지 본문과 API 키는 남기지 않는다.** `LOG_LEVEL=silent`로 끌 수 있다.
- **NFR-8** 개발 서버와 `start`는 `127.0.0.1`에만 연다(인증이 없는 데모이므로).

## 5. 수용 기준 (데모 시나리오)
1. 이동시간 표의 모든 칸에 대한 단위 테스트가 통과한다.
2. "다음 주 평일 오후, 온라인이면 좋겠고 금요일은 절대 안 돼" → 칩 [다음 주][월–목: 반드시][오후: 강][온라인: 강]이 뜬다. ("평일 + 금요일 제외"는 요일 칩 하나로 합친다.)
3. 후보가 많고 동점이면 AI가 분포를 근거로 되묻는다. "제일 빠른 걸로"라고 답하면 버튼 3개가 나온다.
4. 두 클라이언트가 같은 슬롯에 요청 → 호스트가 하나를 수락 → 다른 요청은 자동 거절 → 양쪽 캘린더에 반영된다.
5. 한 클라이언트가 두 호스트에게 겹치는 시간으로 요청 → 두 번째 요청이 거부된다.

## 6. 불필요 기능 후보 (MVP에서 뺄지 검토)
- 필터의 "늦을수록"(사용 빈도가 낮을 것으로 예상)
- 필터의 "앞뒤 여유"(점수 설계가 추가로 필요)
- 캘린더 일정 추가·삭제 UI(FR-3). 시드 데이터만으로도 데모가 가능하다.
