# 공통 장치 (여러 기능이 함께 쓰는 것)

## 1. 두 번 눌러도 안전한 작업
- 중요한 변경은 버튼을 누를 때마다 **작업 키**를 하나 만들어 서버에 함께 보냅니다.
- 서버는 같은 키의 결과를 기억합니다. 같은 요청이 다시 오면 다시 실행하지 않고 저장된 결과를 돌려줍니다.
- 네트워크가 끊겨 결과가 불분명하면 화면은 "… 결과 확인" 버튼을 보여줍니다. 이 버튼은 **같은 키**로만 확인하므로 중복 요청이나 중복 예약이 생기지 않습니다.
- 예외: 호스트 장소·양식, 앱 일정 추가·삭제, 데모 사용자 전환은 아직 이 방식이 아닙니다.

## 2. 버전 확인
초안, 예약 탐색, 요청, 보정, 캘린더 연결에는 모두 버전이 있습니다. 화면이 알고 있는 버전과 서버 버전이 다르면 "다른 화면에서 바뀌었어요"로 막고 최신 상태를 다시 보여줍니다.

## 3. 결정적인 순간에는 최신 캘린더로 다시 확인
- 탐색 시작, 말하기, 조건 바꾸기, 다시 확인, 요청 보내기, 수락 직전에는 양쪽 캘린더를 새로 가져옵니다.
- 저장하는 순간에도 그 캘린더 상태가 그대로인지 한 번 더 봅니다.
- 미팅 허용 시간이 없는 사람이 끼어 있으면 "참여자 모두 미팅 허용 시간을 설정해야 해요"로 막습니다.

## 4. 동시 실행 막기
- 예약처럼 두 사람의 캘린더를 동시에 바꾸는 작업은 사람별 잠금을 정해진 순서로 잡습니다.
- 같은 요청을 두 곳에서 동시에 수락하면 한쪽만 성공합니다(로컬 Postgres에서 확인됨, 이식 노트).

## 5. AI를 쓰는 방식
- **연결 구조**: LLM 연결부는 하나이고(Ollama Cloud, 기본 모델 `gemma4:31b`), 키 세 개를 돌려 씁니다. 한 번 호출의 제한은 20초입니다.
- **실패 구분**: "AI에 닿지 못함"과 "AI 답을 쓸 수 없음"을 다르게 처리합니다.
- **현재 AI를 부르는 곳은 세 군데뿐입니다.**
  - 예약 조건 해석
  - 프로필 변경 추출
  - 일정 업무/개인 분류
  - 셋 다 JSON으로만 받고, 하나하나 검증하며, 재시도는 최대 한 번입니다.
- **안전 장치**: 일정 제목과 사용자 글은 "명령이 아닌 데이터"로 다룹니다. 존재하지 않는 장소·양식이나 범위 밖 날짜는 버립니다.

## 6. 개인정보
- DB의 모든 테이블에 행 단위 보안을 켜고 외부 직접 접근 권한을 회수했습니다. 앱 서버만 접근합니다.
- 가져오는 것: 제목, 설명, 장소, 상태, 시간, 반복 정보, **나의** 응답 상태, 화상회의 링크가 있는지 여부
- 가져오지 않는 것: 첨부파일, 다른 참석자 정보
- 상대에게는 장소·양식·후보 시간·요청 메시지만 보입니다.
- 로그는 한 줄짜리 JSON이고, 제목·장소·메시지·토큰은 남기지 않습니다.

## 7. 배포와 테스트
- 배포 지역은 서울 DB 옆(Vercel `icn1`)입니다.
- 서버 테스트는 실제 마이그레이션을 적용한 메모리 Postgres(PGlite)에서 돌아갑니다.
- 실제 모델로 해석·온보딩 품질을 재는 평가 스크립트가 있습니다(`scripts/eval-*.ts`).
