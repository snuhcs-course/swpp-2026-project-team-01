# Frontend Architecture — AI 온보딩과 개인 미팅 프로필

작성일: 2026-10-04 · 상태: 확정 (2026-10-04)

상위: `technical_architecture.md` · 화면: `app_screen_list.md` · 흐름: `user_flow.md`.

현재 Next.js App Router·React·Tailwind 구성을 유지하며 화면·컴포넌트·상태·서버 계약의 연결을 구체화한다. 아래 컴포넌트·훅·계약은 구현할 설계이며 아직 존재하는 파일을 뜻하지 않는다. API 경로와 상세 오류 스키마는 다음 Backend Architecture에서 이 계약과 대조해 확정한다.

---

## 1. 원칙과 현재 코드의 변경

1. 페이지는 서버 컴포넌트에서 인증·소유권을 확인하고 읽기 전용 초기 모델을 받는다. 상호작용은 화면별 클라이언트 루트가 담당한다.
2. 서버가 저장한 값, 저장되지 않은 폼 입력, 작업 중 상태를 구분한다. 주간표·조건 칩은 동일 상태에서 파생하며 별도 정답처럼 저장하지 않는다.
3. 전역 상태 라이브러리를 추가하지 않는다. 복잡한 화면은 `useReducer`와 화면 범위 Context, 작은 폼은 `useState`를 사용한다.
4. 모든 변경·외부 갱신은 명시적 작업으로 실행한다. 페이지 렌더·GET 조회·링크 프리패치가 탐색·초안·AI 응답을 생성하지 않는다.
5. 서버 응답의 식별자·revision·작업 결과를 확인하고 수용한다. 클라이언트가 가능 슬롯이나 양쪽 선호 순위를 독자적으로 계산하지 않는다.

| 현재 코드 | 변경 방향 |
|---|---|
| `app/layout.tsx`의 인증 전제 Header | 공개 로그인과 보호된 앱 레이아웃 분리 |
| `book/[hostId]/page.tsx`의 `getOrCreateConversation` | 읽기 전용 진입 페이지 + 명시적 새 탐색 작업 |
| `ChatView`의 메시지·칩·후보 수 개별 상태 | search revision을 포함한 서버 모델과 로컬 입력·작업 상태 분리 |
| `AvailabilityForm`의 즉시 규칙 저장 | S2는 확정값 조회, S11 초안 편집, S12 최종 적용으로 통합 |
| `RequestModal` 내부 메시지 상태 | 부모 탐색 화면이 요청 작성 상태를 소유해 모달 종료·재선택 시 보존 |
| `api.ts`의 `ok:boolean`과 강제 `data:T` | 성공·도메인 오류·결과 불명확을 구분하는 타입 계약 |
| 모든 성공 뒤 단순 `router.refresh()` | 변경 응답으로 해당 상태를 갱신한 뒤 필요한 서버 조회만 refresh |

설치된 Next.js의 [Server/Client Components 가이드](../../node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md)와 [useRouter 가이드](../../node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md)를 기준으로 한다. `router.refresh()`는 기존 클라이언트 상태를 모두 초기화하지 않으므로 서버 props와 로컬 폼의 합성 규칙이 필요하다.

## 2. 라우트·레이아웃·URL

| URL | 화면 | 서버에서 읽는 것 | 클라이언트 진입 동작 |
|---|---|---|---|
| `/` | 진입 분기 | 세션·설정/초안·해제 후 선택 상태 | 필요한 목적지로 이동, 변경 없음 |
| `/login` | S9 | 실제/데모 모드와 로그인 상태 | 명시적 Google 로그인 시작 |
| `/calendar?w=…` | S1 | 주간 일정·규칙·조회 상태 | 수동 갱신, 일정 선택·보완 |
| `/settings/availability` | S2 | 확정 프로필·기존 규칙·초안 유무 | 편집 시작 또는 초안 재개 |
| `/settings/host` | S3 | 장소·양식·예약 준비 상태 | 기존 설정 변경 |
| `/settings/calendars` | S10 | 연결·선택 캘린더·조회/이용 선택 상태 | 연결·선택·조회·해제 |
| `/onboarding?draft=…` | S11 | 본인 초안·진행·자료 요약 | 초안 편집·재개 시 갱신 |
| `/onboarding/review?draft=…` | S12 | 서버에 저장된 초안과 확정값 차이 | 최종 적용 |
| `/book` | S4 | 호스트 목록·본인 준비 상태 | 상대 선택 |
| `/book/[hostId]` | S5 진입 | 공개 호스트 정보·본인의 최근 탐색 요약 | 이어가기 또는 새 탐색 생성 |
| `/book/[hostId]/search/[searchId]` | S5·S6 | 지정 탐색·조건·메시지·이전 계산 결과 | 재진입 갱신·대화·요청 |
| `/requests/sent` | S7 | 본인 요청·확정 충돌 상태 | 철회·상태 재조회 |
| `/requests/inbox` | S8 | 받은 요청·묶음·확정 충돌 상태 | 수락·거절 |

- 최상위 layout은 문서 뼈대와 공통 스타일만 가진다. route group `(public)`에 로그인, `(app)`에 S0와 보호된 화면을 배치한다. route group 이름은 URL에 나오지 않는다.
- 레이아웃의 로그인 검사는 UX용 진입 경계다. 개별 페이지 조회와 변경 API에서도 소유권을 검사한다. S9가 기존 `currentUser()`의 시드 폴백에 의존하지 않게 한다.
- 기존 `/book/[hostId]`는 상대 선택 진입 URL로 유지한다. 정확한 이어가기는 searchId가 있는 URL을 사용해 새로고침·뒤로가기에서 같은 탐색을 찾는다.
- 진입 페이지에서 이전 탐색이 없으면 화면 진입 작업으로 새 탐색을 준비할 수 있다. 이전 탐색이 있으면 사용자의 선택 전 새 탐색을 만들지 않는다. 생성 성공 후 `replace`로 구체적인 탐색 URL을 넣어 뒤로가기가 생성 동작을 반복하지 않게 한다.
- S11에 draft가 없으면 본인의 기존 초안을 조회한다. 없을 때만 클라이언트 진입 작업으로 생성하고 URL을 교체한다. S12에 유효 초안이 없으면 편집 진입으로 돌아가며 빈 값으로 확정하지 않는다.
- 프로필로 이동했다 돌아올 때는 상대·탐색 ID를 포함하는 앱 내부 복귀 목적지를 유지한다. URL에 대화 내용·일정 제목·토큰을 넣지 않는다. 복귀 URL은 서버 허용 목록과 소유권 검사를 거친다.
- S13은 URL을 새로 만드는 독립 페이지가 아니라 호출 화면의 패널이다. 닫으면 기존 주·주제·포커스를 복원한다.

**공용 컴포넌트**

- `WeekSchedule`: 일정·근무·허용·선호의 표시를 공용화한다. 저장·AI·예약 계산을 하지 않는다. S1에서는 확정 자료, S11에서는 유효한 초안 미리보기를 받는다.
- `WeeklyWindowsEditor`: 요일별 복수 구간 폼. 근무시간과 허용시간을 같은 UI로 편집하되 서로 다른 필드에 연결한다.
- `PreferenceEditor`: 기본 선호의 지원 항목·강/약/없음. 예약 필터 편집과 구분해 호스트별 장소·날짜를 기본값에 쓰지 않는다.
- `SyncStatus`, `SaveStatus`, `OperationNotice`: 진행·실패·저장됨의 공용 표현. 서로 다른 상태를 하나의 busy 값으로 합치지 않는다.
- `FieldError`, `EmptyState`, `RetryAction`, 모달·패널: 접근성·복귀 동작을 공용화한다.

기존 `OptionButtons`, `StatusBadge`, 호스트 설정·요청 목록 컴포넌트는 필요한 계약을 확장해 사용한다. 이름만 바꾸거나 이미 있는 UI를 전면 재작성하는 것은 이 설계의 목표가 아니다.

## 4. 상태 소유권과 UI 계약

### 4.1 소유권

| 상태 | 소유자 | 보존·갱신 원칙 |
|---|---|---|
| 세션·권한·현재 사용자 | 서버 | 로그인/로그아웃 후 확인. 토큰을 클라이언트 상태에 저장하지 않음 |
| 확정 프로필·외부 일정·요청 상태 | 서버 | 성공 응답·조회 결과만 정답으로 수용 |
| 마지막 저장된 초안·탐색 | 서버, 클라이언트에 snapshot | ID·revision으로 수용 여부 판단 |
| 폼의 작성 중 값·dirty 필드 | 해당 Workspace reducer | 유효해도 서버 저장 전에는 미저장. 잘못된 중간 입력도 화면에서 유지 |
| AI 입력창·전송 중 말풍선 | 대화 Workspace | 실패 시 재입력 가능한 상태 유지, 서버 ID와 확인 후 병합 |
| 요청 메시지·선택 후보 | `BookingWorkspace` | S6를 닫거나 후보 재선택해도 같은 화면 안에서 보존 |
| 선택 주·주제·패널·포커스 | 페이지/Workspace | 필요한 탐색 식별은 URL, 나머지는 화면 상태 |
| 진행 중 작업 키·결과 확인 상태 | `useMutationOperation` | 같은 입력 재시도에서 같은 키 사용 |

Workspace의 React key는 `userId + draftId` 또는 `userId + searchId`다. revision이 바뀔 때마다 remount하지 않는다. 사용자나 탐색이 바뀌면 이전 사람·탐색의 편집 상태를 제거한다.

### 4.2 계약 위치와 응답 수용

- 화면용 DTO와 입력·오류 스키마는 프레임워크/DB에 의존하지 않는 `src/contracts/`에 둔다. 클라이언트가 `src/server/services`의 내부 타입에 직접 결합하지 않게 한다.
- contracts는 필요한 `core` 타입을 사용하되 `core`가 contracts나 UI를 import하지 않는다. 프런트엔드가 사용할 순수 시간 표시·폼 검증은 공용화할 수 있다.
- `ProfileDraftView`에는 draftId·revision·baseProfileVersion·정규화된 값·주제 확인 상태·저장 시각·검증 오류를 포함한다.
- `BookingSearchView`에는 searchId·revision·상속 기준·항목별 상태·유효 조건·출처·메시지·후보 결과와 자료 기준을 포함한다.
- 후보 결과는 `not_ready / ready / stale / unavailable`을 구분한다. 실제 계산된 `ready`에서만 0개라는 값을 단정한다. stale은 마지막 결과와 기준 시각을 가진다.
- 외부 조회 상태는 연결 여부·자료 범위·generation·성공 시각·실패를 구분한다. 본인에게 보여줄 정보와 상대의 최소 상태를 서로 다른 투영으로 받는다.
- 더 낮은 revision의 늦은 응답은 현재 상태를 덮어쓰지 않는다. 같은 revision이라도 더 새로운 조회 결과가 있을 수 있으므로 자료 generation·결과 기준을 함께 확인한다.
- dirty 필드가 있는데 새 서버 props가 도착하면 무조건 `setState(initial)`하지 않는다. 아래 자동 저장·충돌 규칙으로 합친다.

## 5. S11 초안 자동 저장과 AI 경합

### 5.1 직접 입력

1. 입력은 즉시 로컬 폼에 반영하고 dirty 필드를 기록한다. 입력 중 잘못된 시간 문자열은 필드에 남기되 유효한 주간표와 구분한다.
2. 마지막 입력 후 **500ms** 동안 추가 입력이 없으면 유효한 변경만 저장 대기열에 넣는다. 이 시간은 UI 제안값이며 제품 응답 성능 보장이 아니다.
3. 한 초안의 직접 저장 요청은 순서대로 처리한다. 요청마다 예상 revision·작업 키·변경 항목을 보낸다.
4. 저장 중 추가 입력은 로컬에 남기고, 응답이 오면 그 요청에 포함됐던 값까지만 저장된 것으로 표시한다. 이후 dirty 값은 새 revision 기준의 다음 저장에 반영한다.
5. 성공한 정규화 결과로 저장 snapshot을 갱신한다. `저장됨`은 dirty 값과 미해결 작업이 없을 때만 표시한다.

시간 범위 검증과 필드 오류는 클라이언트에서 빠르게 표시할 수 있지만 서버에서 다시 검증한다. 주간표는 마지막 유효 입력을 보여주며, 잘못된 구간이 저장된 것처럼 표현하지 않는다.

### 5.2 AI 입력과 늦은 응답

- AI 메시지 전송 전에 유효한 직접 편집의 저장을 완료한다. 아직 잘못된 입력이 있으면 해당 위치를 먼저 수정하도록 안내한다.
- AI 작업은 시작 revision을 사용한다. 기다리는 동안 직접 편집은 가능하며, 이미 저장된 새 직접 편집을 오래된 AI 결과로 덮어쓸 수 없다.
- 서버가 revision 충돌을 반환하면 최신 초안을 조회하고 현재 로컬 입력을 유지한다. 바뀐 항목을 보여주고 재질문 또는 직접 수정을 선택하게 한다. 옛 AI 결과를 자동 재적용하지 않는다.
- AI 작업이 먼저 저장되고 직접 편집이 충돌한 경우에도 동일하게 최신값과 미저장 입력을 비교한다. 사용자 모르게 같은 항목을 마지막 응답으로 덮어쓰지 않는다.
- 확인하지 않은 제안과 이미 적용된 유효 초안을 구분한다. 분석 근거가 제거·변경됐으면 최신 근거 확인 없이 제안을 확정하지 않는다.

### 5.3 최종 확인·이탈

- `최종 확인`은 dirty 값 저장을 완료하고 서버가 확인한 revision으로 S12에 이동한다. 저장 실패·결과 불명확·검증 오류가 남으면 이동을 완료하지 않는다.
- 앱 내부의 `나중에 이어하기`·다른 메뉴 이동은 가능한 저장을 마친 뒤 실행한다. 저장 실패 시 재시도하거나 미저장 입력을 남기고 이동할지 명시적으로 선택한다.
- 브라우저 강제 종료·새로고침에서는 마지막 **서버 저장값**까지 복구를 보장한다. 미저장 입력이 있으면 지원되는 브라우저 이탈 안내를 사용하되 `beforeunload`나 종료 직전 fetch가 저장을 보장한다고 가정하지 않는다.
- 원본 캘린더·대화·폼 내용을 localStorage/sessionStorage에 복제하지 않는다. 새로고침 후 미완성 입력까지 복구하는 오프라인 편집은 첫 버전 범위가 아니다.

## 6. S5 탐색 시작·갱신·조건 조정

### 6.1 진입 작업

- 서버 페이지는 탐색을 만들지 않는다. `SearchEntry`가 새 시작 작업을 실행하고 성공한 searchId로 이동한다. 같은 상대에게 여러 탐색을 만드는 행동은 사용자 선택에 따른다.
- `useEntryOperation`은 사용자·리소스·진입 목적별 작업 키를 한 번 생성한다. 개발 모드 effect 재실행·중복 클릭은 같은 작업으로 합친다. 단순 `useRef`만으로 서버 중복 방지를 대신하지 않는다.
- 탐색 페이지의 실제 재진입은 명시적 refresh 작업을 실행한다. RSC 재렌더·props 갱신만으로 새 진입으로 판정하지 않는다. 선택 캘린더 revision과 처리한 진입 작업을 기준으로 같은 재진입의 중복 호출을 억제한다.
- 직접 URL 진입·뒤로가기로 복원될 때도 최신 허용 규칙과 조회 상태를 확인한다. 복원된 브라우저 화면을 현재 일정의 확정 결과로 간주하지 않는다.

### 6.2 선호와 후보 상태

- 화면 reducer는 서버의 inherit/override/disabled를 유지하고 칩을 파생한다. 칩 삭제 시 disabled 상태를 없애지 않는다.
- 명시 조건 변경·기본값 복원·최신 기본값 적용은 서로 다른 command다. 프런트엔드에서 임의로 전체 필터를 합쳐 저장하지 않는다.
- 한 탐색의 조건 변경은 순차 처리한다. AI 턴 처리 중에는 중복 메시지와 조건 변경 command를 대기시키고 입력창 작성은 유지할 수 있다. AI 실패 후 직접 조정 경로는 즉시 사용 가능하다.
- 후보·칩·추천 이유는 같은 서버 결과로 갱신한다. 입력 중 추정 슬롯 수를 보여주거나 이전 설명을 새 조건에 붙이지 않는다.
- 양식 미정이면 직접 `MeetingTypePicker` 또는 자연어 입력으로 지정한다. 최초 후보 준비 여부를 별도 상태로 두어 새로고침마다 첫 응답을 삽입하지 않는다.
- `router.refresh()`는 헤더·다른 서버 표시 갱신에 사용한다. 변경 command의 성공 응답을 받은 Workspace는 그 응답으로 먼저 갱신하며 refresh 완료를 새로운 command의 성공으로 해석하지 않는다.

### 6.3 요청 메시지와 프로필 복귀

- `RequestModal`의 입력은 부모가 소유한다. 조회 실패·모달 닫기·후보 재선택에서 메시지를 유지하고 성공 전송 또는 명시적 새 탐색 시작 때 정리한다.
- 전체 페이지를 새로 여는 경우 서버에 저장하지 않은 요청 메시지까지 유지한다고 보장하지 않는다. 같은 화면 안의 재선택 보존과 구분한다.
- 프로필 편집으로 이동할 때 이번 탐색 URL을 복귀 목적으로 보존한다. 프로필 저장 후 같은 searchId로 돌아와 현재 허용 규칙으로 재계산한다.
- 기본 선호가 바뀌어도 진행 중 탐색의 상속 기준은 그대로 두고 `최신 기본 선호 적용`을 표시한다. 적용 시 명시적 변경·해제는 유지한다.

## 7. 변경 호출·결과 불명확·오류 처리

### 7.1 API 클라이언트

`src/components/api.ts`를 공용 API 모듈로 정리하고 화면에서는 도메인별 command 함수를 사용한다. JSON 파싱 실패·네트워크 오류를 성공 데이터처럼 `{}`에 강제 캐스팅하지 않는다.

| 결과 종류 | 클라이언트 동작 |
|---|---|
| 성공 | 검증된 data·revision·작업 결과를 수용 |
| 입력 오류 | fieldErrors 표시, 입력 유지 |
| 인증 만료 | 자기 로컬 입력의 미저장 여부 안내 후 S9, 복귀 목적지 유지 |
| 접근 불가·리소스 없음 | 이전 개인 자료 제거, 안전한 목록으로 복귀 |
| revision 충돌 | 최신 모델 조회, 로컬 입력 보존, 재확인 |
| 캘린더 갱신 실패·재연결 필요 | 기존 자료·시각 유지, 재시도·본인 연결 관리 동작 |
| 슬롯 불가·자동 거절 영향 변경 | 요청 미완료 유지, 후보 재선택 또는 영향 재확인 |
| AI 해석·설명 실패 | 도메인 결과에 따라 초안/조건 유지 또는 템플릿 설명 |
| 네트워크 단절·응답 파싱 불가 | 결과 불명확으로 전환, 작업 결과 확인 후 재시도 |

HTTP 상태만으로 저장됐는지를 추측하지 않는다. 예상 오류는 화면 안에서 처리하고 `error.tsx`는 예상하지 못한 렌더·초기 조회 오류의 재시도 경계로 사용한다. `loading.tsx`는 페이지 초기 대기, 작업 진행은 각 화면의 상태 영역을 사용한다.

### 7.2 작업 키와 재시도

- 변경 작업을 시작할 때 입력을 고정하고 idempotency key를 만든다. 같은 입력·같은 논리 작업의 전송 재시도는 같은 키를 사용한다.
- 입력 변경·명시적 새 탐색·충돌 확인 후 다른 내용 적용은 새 작업이다. 이미 사용한 키로 다른 입력을 보내지 않는다.
- 상태는 `idle → submitting → succeeded / failed / reconciling`으로 구분한다. reconciling에서는 소유자 전용 작업 조회로 성공·실패·미완료를 확인한다.
- 브라우저 취소·AbortController는 응답 대기를 끝낼 뿐 서버 작업을 되돌리지 않는다. 취소했다고 프로필 저장·요청 생성이 실패한 것으로 처리하지 않는다.
- 결과 확인은 알려진 진행 중 작업에만 제한적으로 재조회하고 대기 간격을 늘린다. 서버가 미완료/만료/실패를 반환하면 사용자 재시도 경로를 제공하며 백그라운드 무한 폴링하지 않는다.
- 새로고침 후 결과 확인이 필요한 작업 키·리소스 ID·작업 종류만 사용자별 sessionStorage에 둘 수 있다. 입력 본문·캘린더 자료·토큰은 넣지 않는다. 완료·로그아웃·계정 전환 시 정리한다. 저장소를 사용할 수 없으면 서버의 리소스 상태 조회로 복구한다.

## 9. 캘린더·패널·화면 간 갱신

- S10의 선택·조회·해제 성공은 connection revision과 자료 generation을 갱신한다. S1·S11·S5는 해당 화면 진입 시 서버 기준 상태를 다시 읽는다.
- 같은 화면의 S13 보완 저장은 결과에 포함된 변경 revision을 부모로 전달한다. 부모는 자기 일정/근거 모델을 갱신하고 패널을 닫으면 원래 포커스로 복귀한다.
- S11의 재분석으로 생긴 제안은 확정 프로필 조회를 즉시 바꾸지 않는다. S12 저장 성공 후 S2와 헤더의 완료 상태를 refresh한다.
- 요청·수락·철회 성공 후 현재 요청 목록과 배지를 갱신한다. 반대 역할 화면은 다음 조회 때 서버 상태를 반영한다. 실시간 구독·웹소켓은 추가하지 않는다.
- 계정 전환·로그아웃에서는 진행 중 응답을 이전 사용자 키에 묶어 무시하고 개인 폼·작업 키를 정리한다. 늦은 응답으로 새 사용자의 화면을 채우지 않는다.

## 10. 접근성·반응형·표시 기준

- S11의 좁은 화면 전환은 같은 Workspace를 유지한다. 탭 이동만으로 새 초안·중복 effect·AI 호출을 만들지 않는다.
- 주간표 색과 함께 '근무', '미팅 허용', '선호', '기존 일정' 텍스트·범례를 사용한다. 직접 편집은 시간 입력·버튼으로 가능하며 드래그가 필수 조작이 아니다.
- 시간·요일은 공용 KST formatter를 사용하고 UI와 서버 설명이 다른 시각을 표시하지 않게 한다.
- 메시지·저장 결과는 적절한 status 영역으로 알리고 오류는 field와 연결한다. 매 답변마다 포커스를 강제로 입력창으로 이동하거나 사용자가 읽는 위치를 무조건 끝으로 스크롤하지 않는다.
- 모달은 초점 범위를 관리하고 Escape/닫기 동작을 제공한다. 진행 중 닫기는 서버 작업 취소를 뜻하지 않는다는 상태 규칙을 따른다.
- 소유권 없는 상세 데이터는 서버에서 전달하지 않는다. 화면에서 가리기만 하는 방식이나 DOM에 숨긴 민감 정보를 사용하지 않는다.

| 예약 작업 | 메시지 보존, 조회 실패, 결과 불명확 뒤 중복 방지, 자동 거절 영향 재확인 | AC-11, AC-12 |
| 계정·자료 경계 | 로그인/연결 분리, 계정 전환 후 늦은 응답 무시, 해제 후 사용 결정 | AC-01, AC-12 |

현재 Vitest를 상태·command 검증에 활용한다. DOM 상호작용 테스트가 필요한 구현 단계에서 React Testing Library와 적절한 DOM 환경을 개발 의존성으로 추가한다. 브라우저 검증에서는 실제 클릭·키보드·좁은 화면·새로고침을 확인한다. OAuth와 실제 캘린더 수집 성공은 UI 목 응답으로 검증했다고 보고하지 않는다.

## 12. 다음 문서

다음 `backend_architecture.md`에서 화면 계약의 endpoint·payload·오류·revision·작업 상태 조회를 확정한다. 프런트엔드와 백엔드가 각각 다른 규칙으로 계산하거나 실패를 해석하지 않도록 `src/contracts/`를 공유 경계로 삼는다. 이 단계에서는 제품 코드·라이브러리·DB를 변경하지 않는다.
