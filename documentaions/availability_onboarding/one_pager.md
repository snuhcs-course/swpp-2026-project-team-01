# One Pager — AI 온보딩과 개인 미팅 프로필

> **One-liner**: 연결한 캘린더를 바탕으로 AI와 근무시간·미팅 허용 시간·선호를 함께 설정하고, 저장한 개인 미팅 프로필로 새로운 예약의 첫 후보부터 개인화한다.

작성일: 2026-10-04 · 상태: 확정 (2026-10-04 검토 완료, PRD 작성 진행)

기존 MVP의 예약 흐름을 확장하는 기능이다. 이 문서는 새 기능의 제안이며, 기존 구현의 완료 상태를 나타내지 않는다. 합의한 방향과 이번 문서에서 제안하는 범위는 아래에서 구분한다.

---

## 1. 문제

현재 MVP에서는 사용자가 요일별 가능 시간을 직접 설정하고, 특정 상대와 예약할 때마다 대화로 원하는 조건을 전달한다. 기본 가능 시간은 매일 08:00–22:00이며, 저장된 개인 선호를 이용한 예약 시작 흐름은 없다.

사용자의 캘린더에는 기존 일정과 활동 패턴이 있지만, 빈 시간이 모두 미팅 가능한 시간은 아니다. 근무 중에도 미팅을 받지 않을 시간이 있고, 자주 잡혔던 미팅 시간이 실제 선호와 다를 수 있다. 사용자가 캘린더를 다시 해석해 설정값으로 옮기는 부담을 줄여야 한다.

## 2. 해결

1. 첫 진입 시 캘린더를 연결하고, 사용할 캘린더의 일정·시각·장소를 가져온다.
2. AI가 **근무시간 → 미팅 허용 시간 → 추가 선호**를 설정하는 대화 세션을 제안하고 시작한다.
3. 기록에서 얻은 단서를 근거와 함께 제안하고, 사용자의 선택·수정으로 개인 미팅 프로필을 확정한다.
4. 새로운 예약에서는 두 사람의 실제 가능 시간에 클라이언트의 기본 선호를 적용해 첫 후보 또는 추가 질문을 제시한다.
5. 클라이언트 관점에서 동등한 후보는 호스트의 선호를 보조 기준으로 정렬한다.

**AI는 캘린더를 해석하고 설정 초안과 질문을 만든다.** 일정 집계, 슬롯의 가능 여부, 필터 적용과 순위는 코드가 계산한다. 확정 전 추정은 예약 규칙으로 적용하지 않는다.

## 3. 사용자와 결과물

- 대상은 **일하는 사용자**이며, 정해진 주간 근무시간이 없는 사용자도 직접 자기 패턴을 설명할 수 있다.
- 한 사람은 호스트와 클라이언트 양쪽 역할을 가질 수 있다. 우선 개인 프로필 하나를 양쪽 역할에 활용한다.
- 온보딩 결과는 이후 예약에서 재사용하는 개인 미팅 프로필이다. 가져온 일정은 별도로 보관하고 프로필과 함께 가능 시간을 계산한다.

| 정보 | 의미 | 예약에 쓰는 방식 |
|---|---|---|
| 캘린더 일정 | 이미 잡힌 일정의 시작·종료·장소·온라인 여부 | 겹침과 앞뒤 이동 가능 여부 계산 |
| 근무시간 | 사용자가 일하는 요일과 시간 | 미팅 허용 범위를 제안하는 배경. 전체를 바쁜 시간으로 처리하지 않음 |
| 미팅 허용 규칙 | 실제로 미팅에 참석할 수 있도록 열어둔 요일·시간 | 호스트와 클라이언트 모두 만족해야 하는 필수 조건 |
| 기본 선호 | 허용 범위 안에서 더 원하는 요일·시간·앞뒤 여유 등 | 후보 순위에 반영. 맞지 않는다는 이유만으로 후보를 제거하지 않음 |

## 4. 핵심 규칙

### 4.1 캘린더를 근거로 제안하고 사용자에게 확인한다

| 설정 주제 | 캘린더에서 살펴볼 단서 | 확인 원칙 |
|---|---|---|
| 근무시간 | 반복 업무 일정, 업무 일정 시작, 개인 약속 시작 시각 | 개인 약속 시작은 근무 종료의 단서로만 사용한다. 근무 시작·종료를 함께 확인한다. |
| 미팅 허용 시간 | 업무 미팅이 주로 있었던 시간대와 가장 늦었던 사례 | 늦은 미팅이 반복 패턴인지 예외인지 묻는다. 최대 시각 한 건으로 허용 범위를 정하지 않는다. |
| 기본 선호 | 미팅을 자주 잡았던 요일·시간대 | 자주 있었던 시간과 앞으로 선호할 시간을 구분해서 묻는다. |

- 일정의 업무·개인 여부가 불명확하면 추정으로 표시하고, 설정에 영향을 주는 경우 질문으로 보완한다.
- 근거가 부족하면 직접 질문한다. 일정이 적거나 비어 있다는 이유로 모든 시간을 가능하다고 설정하지 않는다.
- 제안 근거는 실제로 가져온 기록에 연결돼야 한다. AI가 기록에 없는 빈도·일정·장소를 만들어 설명하지 않는다.
- 사용자가 명시한 설정이 추정보다 우선한다. 이후 일정 수집으로 사용자의 설정을 자동 덮어쓰지 않는다.

### 4.2 일정과 장소를 보존한다

- 가져온 일정의 시작·종료 시각과 제공된 장소·온라인 정보를 유지한다.
- 장소가 없거나 모호하면 미확인 상태를 유지하고 필요할 때 보완한다. 일정 제목만으로 실제 위치를 확정하지 않는다.
- 일정의 종료 장소는 이동 계산의 기준점이다. 그 이후 계속 그 장소에 머문다고 단정하지 않는다.
- 근무시간을 등록했다고 그 시간 내내 회사에 있다고 가정하지 않는다.
- 실제 길찾기 API 도입은 별도 범위다. 첫 버전의 이동 계산은 기존 규칙을 활용하되, 미확인 장소의 처리 방식은 PRD에서 명시한다.

### 4.3 프로필과 이번 예약의 조건을 구분한다

- 확정한 미팅 허용 규칙과 기본 선호를 저장하고, 새 예약마다 불러온다.
- 이번 예약에서 명시한 선호는 같은 항목의 기본 선호를 대체한다. 언급하지 않은 항목은 기본 선호를 유지한다.
- “이번에는 오전도 괜찮아” 같은 수정은 해당 예약에만 적용한다. 기본 선호 변경은 사용자가 지속 적용을 명시했을 때 별도로 처리한다.
- 선호를 바꾸는 것만으로 양쪽의 미팅 허용 규칙을 해제할 수는 없다. 허용 규칙의 예외 처리 범위는 PRD에서 정한다.
- 후보가 없으면 어떤 조건 때문에 없는지 설명하고 조정을 제안한다. 필수 조건을 자동으로 풀지 않는다.

### 4.4 양쪽 선호를 적용하는 순서

1. 양쪽 일정·미팅 허용 규칙·이동 조건을 만족하는 슬롯을 계산한다.
2. 이번 예약에서 명시한 필수 조건을 적용한다.
3. 이번 예약의 선호와 항목별로 상속한 클라이언트의 기본 선호로 순위를 계산한다.
4. 클라이언트 관점에서 동등한 후보에 호스트의 기본 선호를 적용한다.
5. 그래도 같으면 기존의 결정적 정렬 기준으로 순서를 정한다.

- 첫 버전에서는 **클라이언트 선호 점수가 같은 후보**를 동등한 후보로 보는 방식을 제안한다. “비슷한 점수”의 임의 범위를 두지 않는다.
- 호스트의 선호가 클라이언트의 명시적인 선호 순서를 뒤집지 않는다.
- 호스트의 미팅 금지 시간은 1단계의 필수 조건이고, 더 좋아하는 시간은 4단계의 선호다.
- 상대에게는 예약에 필요한 후보와 추천 근거를 제공한다. 상대의 사적 일정 제목이나 구체적인 개인 활동을 근거 설명에 노출하지 않는다.

### 4.5 예약의 첫 응답

- 프로필이 있으면 호스트를 선택한 직후 후보를 계산하고, 어떤 기본 선호가 반영됐는지 설명한다.
- 조건이 충분하면 최대 3개 후보를 보여준다. 미팅 길이 등 중요한 조건이 미정이면 기존 예약 흐름처럼 먼저 질문한다.
- 선호에 맞는 후보가 없더라도 필수 조건을 만족하는 대안이 있으면, 어떤 선호를 충족하지 못했는지 밝혀 제안한다.
- 기본 선호를 예약 화면에서 확인하고 해당 예약에 한해 수정할 수 있게 한다.

## 5. 대표 흐름

아래는 제품 동작을 설명하기 위한 가상 예시다.

1. 사용자가 캘린더를 연결하고 온보딩을 시작한다.
2. AI: “평일 저녁에 개인 약속이 시작되는 패턴이 보여요. 보통 몇 시부터 몇 시까지 일하시나요?”
3. 사용자: “월–금 9시부터 6시까지. 외부 미팅은 화·목 오후만 받을래.”
4. AI는 근무시간과 미팅 허용 시간을 구분해 초안을 표시하고 선호를 묻는다.
5. 사용자: “2시 이후가 좋고, 앞뒤로 여유가 있으면 좋겠어.”
6. 사용자가 주간표와 설정 요약을 확인하고 프로필을 저장한다.
7. 다른 호스트와 예약을 시작하면 “기본 선호인 화·목 오후 2시 이후를 기준으로 가능한 시간을 살펴봤어요”라는 설명과 후보가 나온다.
8. 클라이언트에게 같은 점수인 화·목 후보 중 호스트가 목요일을 선호하면 목요일을 먼저 제시한다.

## 6. 첫 버전 범위 제안

**포함**
- 한 종류의 캘린더 공급자 연결과 선택한 캘린더의 일정 가져오기.
- 일정의 시간·장소 정보 보존, 설정에 필요한 패턴 요약과 불확실한 정보 확인.
- 근무시간·미팅 허용 시간·기본 선호를 설정하는 AI 대화, 초안 확인과 저장·수정.
- 설정 결과를 보여주는 주간표와 요약.
- 저장한 프로필을 이용한 새 예약의 첫 응답과 클라이언트 동점 후보의 호스트 선호 반영.
- 기록이 부족하거나 AI를 사용할 수 없을 때 직접 설정할 수 있는 경로.

**후속 확장**
- 여러 캘린더 공급자 지원, 원본 캘린더로의 일정 쓰기와 양방향 동기화.
- 실제 경로별 이동시간 조회.
- 행동 이력만으로 기본 선호를 자동 변경하는 학습.
- 역할·상대·미팅 목적마다 별도의 개인 프로필 운영.

연결 인증, 재조회와 중복 방지, 일정 변경·삭제 반영, 데이터 최신성은 연동에 필요한 요구사항이다. 구체적 범위와 처리 방식은 PRD에서 정한다.

## 7. 성공 기준

1. 가져온 일정의 시간과 장소가 예약 가능 시간 계산에 연결된다.
2. 사용자가 캘린더 근거를 확인하며 세 주제의 설정을 완료할 수 있고, 잘못된 추정을 수정하면 최종 프로필에 반영된다.
3. 확정된 프로필이 새 예약의 첫 응답과 후보에 적용되고, 설명은 실제 적용된 조건과 일치한다.
4. 이번 예약만의 수정이 다음 예약의 기본 선호를 바꾸지 않는다.
5. 클라이언트 선호가 동점인 후보에서만 호스트 선호가 순서를 바꾸며, 양쪽의 필수 조건은 항상 지켜진다.
6. 캘린더 단서가 부족하거나 AI가 실패해도 직접 설정으로 완료할 수 있다.

제품 검증에서는 수동 설정 대비 **완료 시간, 중도 이탈, 제안 수정 내용, 첫 후보의 수용 여부**를 관찰한다. 수치 목표는 초기 사용자 검증 후 정한다.

## 8. 다음 문서에서 결정할 사항

- **캘린더 입력**: 첫 공급자와 실제 계정 연결 범위. 가져오기만 하는 데모와 지속 연동의 수용 기준을 구분한다.
- **분석 기간**: 과거 몇 주를 패턴 분석에 쓰고, 미래 일정을 어디까지 수집할지. 기존 슬롯 계산의 미래 60일 범위와 구분한다.
- **규칙 표현 범위**: 하루 여러 구간, 날짜별 예외, 온라인 여부별 허용 시간 중 첫 버전에 포함할 항목.
- **온보딩 진입과 재개**: 연결 건너뛰기, 중간 저장, 재접속, 기존 MVP 사용자 전환 방식.
- **기존 예약과 설정 변경**: 저장된 대화에 새 프로필을 적용하는 시점과 이미 대기·확정된 예약에 대한 처리.
