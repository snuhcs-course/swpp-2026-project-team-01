# PRD — AI 온보딩과 개인 미팅 프로필

작성일: 2026-10-04 · 상태: 확정 (2026-10-04 검토 완료) · 근거: `one_pager.md`

합의한 One Pager를 동작과 수용 기준으로 구체화한다. 2026-10-04 검토에서 아래 범위 결정 A–F를 채택했다. 요구사항의 확정은 구현 완료를 뜻하지 않는다.

---

## 1. 목표 / 비목표

**목표**
- G1. 캘린더의 일정·시각·장소를 가져와 기존 예약 가능 시간 계산에 연결한다.
- G2. AI와의 대화와 직접 편집으로 근무시간·미팅 허용 시간·기본 선호를 확정한다.
- G3. 새 예약에서 개인 프로필을 활용한 첫 응답과 후보를 제공한다.
- G4. 클라이언트에게 동등한 후보는 호스트 선호로 정렬한다.
- G5. 기록 부족·AI 실패·중간 이탈에도 설정을 완료하거나 재개할 수 있다.

**비목표**
- 외부 캘린더에 예약 쓰기, 양방향 동기화, 여러 공급자 지원.
- 실제 길찾기, 근무시간만으로 사용자의 위치 추정.
- 기록만으로 기본 설정을 자동 확정하거나 변경하는 학습.
- 역할·상대·미팅 목적별 프로필, 호스트의 요청 처리 AI.
- 기존 MVP 범위 밖인 확정 예약 취소·변경과 알림.

## 2. 확정한 범위

| 항목 | 결정 | 이유 |
|---|---|---|
| [결정 A] 첫 연동 | Google Calendar, 사용자당 Google 계정 1개, 해당 계정에서 선택한 복수 캘린더, 읽기 전용 | 실제 사용자의 일정으로 온보딩과 예약 흐름을 검증 |
| [결정 B] 분석·조회 기간 | 과거 8주(56일)는 패턴 분석, 오늘부터 60일은 예약 계산 | 과거 습관과 미래 가능 시간을 구분. 기간의 적절성은 사용자 검증으로 평가 |
| [결정 C] 시간 규칙 | 요일별 여러 구간 지원. 날짜별 예외와 온라인 여부별 허용 시간은 후속 | 점심을 제외한 오전·오후를 표현하면서 첫 구현 범위를 제한 |
| [결정 D] 기본 선호 | 요일·시작 시간대·온라인/오프라인·앞뒤 여유, 강/약 선호 | 특정 호스트의 장소·미팅 양식 ID에 종속되지 않게 재사용 |
| [결정 E] 초기 후보 | 미팅 양식이 정해지면 기본 선호로 최대 3개를 우선 제시 | 온보딩 결과를 예약 시작부터 체감. 양식이 여러 개면 길이를 먼저 질문 |
| [결정 F] 운영 경계 | 실제 연동 모드는 Google 계정으로 사용자 식별. 기존 사용자 전환은 시드 데모 모드에만 유지 | 연결한 개인 일정의 소유자를 명확히 하고 기존 데모를 보존 |

실제 OAuth 연결은 이 기능에 필요한 범위에 포함한다. 일반적인 이메일 회원가입·비밀번호 관리·조직 관리는 포함하지 않는다. 프로필 하나를 호스트·클라이언트 공통으로 사용한다.

| 용어 | 정의 |

| 근무시간 | 사용자가 일하는 주간 패턴. 미팅 허용 범위를 제안하는 배경이며 그 자체가 바쁜 일정은 아님 |
| 미팅 허용 규칙 | 미팅 전체가 들어가야 하는 요일별 시간 구간. 양쪽 사용자 모두에 적용 |
| 기본 선호 | 허용된 슬롯 중 더 원하는 조건. 후보를 제거하지 않고 순위에 반영 |
| 개인 미팅 프로필 | 확정한 근무시간·미팅 허용 규칙·기본 선호와 버전 |

| 이번 예약 조건 | 기본 선호를 상속·대체·해제한 탐색별 조건. 프로필과 별도로 저장 |
| 분석 근거 | 수집 기간, 대상 일정, 집계 결과, 분류의 확인 여부 등 제안의 출처 |

## 4. 기능 요구사항

### 4.1 진입 · 연결 · 재개

- **FR-01** 프로필이 없는 사용자의 첫 진입에서 캘린더 연결과 가능 시간 설정을 안내한다. 연결이 끝나면 AI 설정 세션을 시작한다.
- **FR-02** 캘린더 연결을 건너뛰거나 권한 요청을 취소해도 직접 설정할 수 있다. 전체 설정도 나중으로 미룰 수 있으며, 완료를 강요하는 반복 팝업 대신 재개 진입점을 제공한다.
- **FR-03** 로그인한 사용자만 자신의 연결·초안·프로필·수집 일정을 읽고 수정할 수 있다. OAuth 결과는 연결을 시작한 사용자와 결합하며 사용자 전환으로 다른 실제 계정의 일정에 접근할 수 없어야 한다.
- **FR-04** 연결 후 사용할 캘린더를 선택하고, 조회 기간과 분석 목적을 보여준다. 선택한 캘린더의 마지막 성공 조회 시각과 연결 상태를 표시한다.
- **FR-05** 초안과 대화 진행을 저장한다. 새로고침·재접속 시 마지막 저장 상태에서 재개하며, 실패한 응답이나 중복 전송으로 확정 설정을 변경하지 않는다.
- **FR-06** 기존 사용자는 저장된 가능 시간 규칙을 초안으로 불러와 확인할 수 있다. 프로필을 새로 확정하기 전까지 기존 규칙은 유지한다. 신규 사용자는 확인하지 않은 08:00–22:00 기본값으로 예약을 열지 않는다.
- **FR-07** 신규 사용자는 미팅 허용 규칙을 확정한 뒤 예약 요청·수신을 사용할 수 있다. 근무시간은 '고정 패턴 없음', 선호는 '없음'으로 완료할 수 있다. 허용 구간이 없는 상태도 저장 가능하나 예약 불가로 표시한다. 호스트의 장소·미팅 양식 등록 요건은 유지한다.

### 4.2 일정 가져오기와 갱신

- **FR-10** 최초 수집에서는 선택한 캘린더의 과거 56일과 오늘부터 60일에 겹치는 일정을 가져온다. 부분적으로 기간에 걸치는 일정도 포함한다. 모든 선택 캘린더의 조회가 완료된 시점에 성공 상태를 기록한다.
- **FR-11** 시작·종료 시각, 원본 시간대, 제목, 제공된 장소·온라인 단서, 반복 일정의 회차 식별 정보, 바쁨 여부와 취소 여부를 보존한다. 원본 식별자와 사용자 보완 정보는 구분한다. 분석에 불필요한 첨부파일·참석자 연락처는 수집하지 않는다.
- **FR-12** 반복 일정의 실제 회차, 이동된 회차, 취소된 회차를 조회 범위에 맞게 반영한다. 같은 연결·캘린더·회차를 재수집해도 중복 생성하지 않는다. 복수 캘린더의 동일 일정은 공급자의 동일성 근거가 있을 때만 중복 집계하지 않으며, 제목·시각이 같다는 이유만으로 다른 약속을 합치지 않는다.
- **FR-13** 종일 일정은 종료 날짜를 포함하지 않는 날짜 구간으로 처리한다. 바쁜 종일 일정은 해당 날짜를 막되 근무 시작·종료 시각 추정과 이동 기준점에는 사용하지 않는다. 시각이 있는 일정은 KST로 표시·계산하고 원본 시각 의미를 유지한다.
- **FR-14** 취소되었거나 사용자가 참석을 거절한 일정, 비차단 일정은 바쁜 구간에서 제외한다. 미응답·참석 미정 초대는 바쁜 일정으로 취급한다. 업무 위치 정보는 그 자체로 바쁜 일정이나 실제 이동 기준점으로 만들지 않는다. 집중 시간·부재는 바쁨 상태를 따르되 실제 업무 미팅 횟수에 포함하지 않는다.
- **FR-15** 제목이나 장소를 읽을 수 없어도 바쁨 구간이 있으면 충돌 계산에 반영한다. 정보 부족을 빈 시간으로 해석하거나 개인·업무로 단정하지 않는다.
- **FR-16** 사용자는 수동으로 일정을 새로 가져올 수 있다. 온보딩 재개·새 예약 탐색·예약 화면 재진입에서도 연결된 캘린더를 갱신한다. 갱신 시 조회 범위를 현재 날짜에 맞춰 이동하고 변경·삭제를 반영한다. 실시간 푸시 동기화는 첫 버전에서 제외한다.
- **FR-17** 갱신은 완결된 결과 단위로 반영한다. 일부 페이지·캘린더 조회 실패를 삭제나 빈 일정으로 처리하지 않으며 마지막 성공 데이터는 유지한다. 실패 상태와 조회 시각을 보여주고 기존 데이터를 현재 상태라고 설명하지 않는다.
- **FR-18** 연결된 사용자 양쪽의 미래 일정을 요청 전송·수락 직전에 다시 조회하고 검증한다. 필요한 조회가 실패하면 해당 동작을 완료하지 않고 재시도를 안내한다. 연결을 건너뛴 사용자에게는 앱에 등록된 일정 기준임을 표시한다. 외부 조회와 원본 변경 사이의 경합까지 완전히 없앤다고 보장하지 않는다.
- **FR-19** 캘린더 선택 해제·연결 해제 시 해당 출처의 일정과 분석 근거를 제거하고 더 이상 조회하지 않는다. 확정 프로필과 앱 내 수동·예약 일정은 유지한다. 외부 일정이 빠지면 가능 시간이 늘 수 있음을 알리고, 남은 데이터 기준으로 계속 사용할지 또는 다시 연결할지 사용자가 선택하게 한다.

### 4.3 분석 · 장소 확인

- **FR-20** 코드가 요일·시간대별 일정 빈도, 업무로 분류된 일정의 시작·종료 분포, 반복 여부와 예외 사례를 집계한다. 분석 대상은 과거의 취소·거절되지 않은 바쁜 일정으로 하며 종일 일정은 시각 분포에서 제외한다.
- **FR-21** 업무·개인·미확인 분류와 업무 중 미팅 여부를 구분한다. AI 추정과 사용자 확인 상태를 기록한다. 업무 일정 전체를 업무 미팅으로 간주하지 않는다. 제목이 없거나 해석이 모호한 항목은 미확인으로 남길 수 있다.
- **FR-22** 근무 종료 제안에는 개인 약속 시작 시각을 단서로 활용할 수 있다. 근무 시작을 그 정보에서 도출하지 않고 별도로 확인한다. 최대 종료 시각 한 건으로 미팅 허용 시간을 정하지 않는다.
- **FR-23** 자주 미팅이 있었던 시간은 '관찰된 패턴'으로 표현하고, 앞으로도 선호하는지 묻는다. 횟수를 말할 때는 집계한 건수·기간과 일치해야 한다. 모든 제안에는 사용자가 확인할 수 있는 근거 또는 '직접 입력' 출처가 있어야 한다.
- **FR-24** 기록이 없거나 특정 주제에 필요한 단서가 없으면 해당 주제를 직접 질문한다. 근거 없이 전형적인 출퇴근 시간을 개인화된 결과로 제시하지 않는다. 적은 수의 기록으로 제안할 때는 관찰 범위가 제한됨을 밝힌다.
- **FR-25** 일정의 장소와 온라인 여부를 보여주고 수정할 수 있게 한다. 원본에 장소와 화상회의 링크가 함께 있으면 자동으로 온라인 참석을 확정하지 않는다. 회사·온라인·특정 장소는 원본의 명확한 정보나 사용자 확인으로 결정한다.
- **FR-26** 미확인 장소가 있는 시각 일정은 기존 MVP의 '장소 없음' 이동 규칙을 적용하며 실제 위치를 안다고 설명하지 않는다. 사용자 보완은 재조회로 덮어쓰지 않되, 원본 장소·온라인 정보가 바뀌면 보완의 재확인을 요구한다. 실제 이동시간 API는 사용하지 않는다.
- **FR-27** 근무시간은 위치나 바쁜 일정으로 자동 생성하지 않는다. 일정의 시작·종료 장소와 근무 패턴은 별도 정보로 유지한다.

### 4.4 온보딩 대화와 프로필 확정

- **FR-30** 기본 진행은 근무시간 → 미팅 허용 시간 → 선호 → 최종 확인이다. 한 발화에 여러 정보가 있으면 모두 반영하며 이미 답한 질문은 반복하지 않는다. 사용자는 앞선 주제로 돌아가 수정할 수 있다.
- **FR-31** 대화와 함께 주간표·설정 요약을 갱신한다. 근무시간, 기존 일정, 미팅 허용 범위, 선호를 구분하고 같은 설정을 직접 편집할 수 있게 한다.
- **FR-32** 근무시간과 미팅 허용 시간은 요일별로 복수 구간을 지원한다. 구간은 KST의 같은 날 안에 있어야 하며 시작보다 종료가 늦어야 한다. 겹치는 구간은 합치고, 자정을 넘는 입력은 다음 요일의 구간과 나누어 확인한다. 미팅 전체가 허용 구간 안에 들어가야 한다.
- **FR-33** 근무시간 밖도 사용자가 미팅 허용 시간으로 열 수 있다. 근무시간을 바꿔도 허용 시간을 자동 변경하지 않는다. 날짜별 예외·온라인 여부별 허용 규칙을 요청하면 첫 버전의 제한을 설명하고 지원하는 대안만 제안한다.
- **FR-34** 기본 선호는 요일 집합, 시작 시간대 하나, 온라인/오프라인 중 선호 방식, 앞뒤 여유로 구성한다. 각 항목은 강/약 선호 또는 없음이다. 특정 상대의 장소 ID·미팅 양식 ID, 날짜 범위, 빠른/늦은 순서는 기본 프로필에 저장하지 않는다.
- **FR-35** 선호 시간대는 슬롯의 시작 시각에 적용하고 미팅 허용 시간은 전체 길이에 적용한다. '미팅 사이 여유가 좋다'는 선호다. '반드시 30분 비워야 한다' 같은 최소 여유 규칙은 첫 버전에서 지원하지 않으며 선호로 몰래 변환하지 않는다.
- **FR-36** 허용 범위와 맞는 시간이 전혀 없는 선호는 저장 전 충돌을 표시하고 수정을 요청한다. '고정 근무 없음', '선호 없음', '미팅을 받지 않음'은 유효한 선택이다.
- **FR-37** 마지막 확인 화면에서 세 주제의 결과를 보여주고 사용자가 저장하면 한 버전의 프로필로 원자적으로 확정한다. AI의 응답만으로 완료 처리하지 않는다. 새 프로필 편집 중에는 마지막 확정 프로필이 계속 적용된다.
- **FR-38** 재분석은 새 제안만 만든다. 기존 사용자 설정을 자동 덮어쓰지 않는다. AI 실패 시 마지막 유효 초안을 유지하고 직접 편집·저장을 제공한다. 해석 불가능한 발화를 성공으로 표시하지 않는다.

### 4.5 예약 시작 · 기본값 상속 · 수정

- **FR-40** 새 예약 탐색을 시작할 때 클라이언트의 확정 프로필 버전과 기본 선호를 가져온다. 상대를 다시 방문한 경우 기존 탐색을 이어갈지 '새 미팅 찾기'로 시작할지 구분한다. 새 탐색은 이전의 일회성 조건을 상속하지 않는다.
- **FR-41** 후보 계산에는 항상 최신 확정 허용 규칙과 현재 수집 일정을 사용한다. 진행 중 탐색의 기본 선호는 시작 시점 값을 유지한다. 사용자가 최신 기본 선호 적용을 선택하면 상속 항목만 갱신하고 이번 탐색의 명시적 변경·해제는 보존한다.
- **FR-42** 이번 예약에서 언급한 항목은 해당 항목의 기본 선호를 대체하고, 나머지는 상속한다. 기본 선호 칩을 삭제하면 그 탐색에서 '해제됨'을 저장해 다음 턴에 되살리지 않는다. 기본값으로 복원하는 동작을 제공한다.
- **FR-43** 칩에는 기본 선호인지 이번 예약에서 바꾼 조건인지 표시한다. 이번 예약 조건 변경은 프로필에 쓰지 않는다. '앞으로도 이렇게'라는 요청은 프로필 변경 초안을 열고 저장 후 적용한다.
- **FR-44** 기본 선호가 있어도 본인·상대의 미팅 허용 규칙을 넘어설 수 없다. 허용 범위 변경은 프로필 편집에서 처리한다. 이번 예약만 허용 시간을 넓히는 예외는 첫 버전에서 제공하지 않는다.
- **FR-45** 새 탐색에서는 적용한 기본 선호와 실제 후보 수에 근거한 첫 응답을 자동 생성한다. 미팅 양식이 하나거나 이미 지정됐으면 동점이 많아도 최대 3개를 제시한다. 여러 양식 중 길이가 미정이면 먼저 길이를 묻고, 답변 후 첫 후보를 제시한다. 기본 선호가 없으면 개인화했다고 표현하지 않는다.
- **FR-46** 필수 조건을 만족하는 후보는 있지만 선호를 충족하지 못하면 그 차이를 밝혀 대안을 제시한다. 필수 조건 때문에 후보가 없으면 0개임을 표시하고 어떤 조건을 조정할지 묻는다. 허용 규칙을 풀어야 한다면 해당 사용자의 설정 변경이 필요함을 설명한다.
- **FR-47** 호스트 선호는 탐색 재계산 시 최신 값을 사용한다. 호스트 선호만 바뀌어도 클라이언트의 조건은 변경하지 않는다. 상대의 사적 일정·장소 상세는 응답 근거로 전달하지 않는다.

### 4.6 순위와 추천 설명

- **FR-50** 양쪽 일정·이동·허용 규칙 및 이번 탐색의 필수 조건을 먼저 적용한다. 선호는 후보를 제거하지 않는다.
- **FR-51** 클라이언트 점수는 이번 탐색의 조건과 항목별로 상속한 기본 선호로 계산한다. 호스트 점수는 호스트 기본 선호만으로 별도 계산한다. 두 점수를 합산하지 않는다. 강/약 선호의 기존 가중치 10/3과 여유 점수 방식을 유지한다.
- **FR-52** 명시적인 빠른/늦은 순서가 없으면 `클라이언트 점수 → 호스트 점수 → 가까운 날짜·이른 시각 → 장소·양식` 순서로 정렬한다. 호스트 점수는 클라이언트 점수가 같을 때만 작용한다.
- **FR-53** 클라이언트가 이번 탐색에서 빠른/늦은 순서를 명시했다면 `클라이언트 점수 → 가까운 날짜 → 같은 날의 요청한 시각 순서 → 호스트 점수 → 장소·양식` 순서다. 호스트 선호로 클라이언트의 명시적인 시간 순서를 뒤집지 않는다. '늦은 순'은 가장 먼 날짜를 뜻하지 않는다.
- **FR-54** 점수의 동등성은 같은 입력에서 재현 가능하게 판정한다. '거의 같다'는 허용 오차로 호스트 선호를 끼워 넣지 않는다. 숫자 표현 방식은 아키텍처 문서에서 정한다.
- **FR-55** 정렬된 목록에서 기존처럼 최대 3개의 다양한 시간대를 선택한다. 다양화를 위해 어떤 후보를 건너뛰었는지 선택 근거에 남긴다. 첫 후보 이후의 되묻기·버튼 표시 판정은 양쪽 점수와 명시적 순서를 포함한 순위 기준에 맞춰 갱신한다.
- **FR-56** 설명은 적용한 기본 선호, 이번 예약에서 바꾼 조건, 미충족 선호, 필요할 때 호스트 선호의 동점 해소 역할을 구분한다. 실제로 호스트 선호가 순위에 영향을 주지 않았으면 영향을 준 것처럼 설명하지 않는다. AI 실패 시 같은 계산 근거의 템플릿을 사용한다.

### 4.7 기존 데이터와 예약 상태

- **FR-60** 기존 가능 시간 규칙을 복수 구간 표현으로 옮길 때 의미를 유지한다. 기존 사용자에게 기본 선호를 임의로 생성하지 않는다. 기존 대화의 필터는 이번 탐색에서 명시한 조건으로 취급한다.
- **FR-61** 시드 데모와 실제 연동 데이터는 구분한다. 실제 계정에 시드 일정·데모 인물을 자동 복사하지 않는다. 자동 검증용 데이터와 실제 연결 검증은 별도로 제공한다.
- **FR-62** 기본 선호 변경은 이미 제출한 요청의 상태나 확정 일정을 바꾸지 않는다. 미팅 허용 규칙·외부 일정 변경은 대기 요청을 즉시 자동 거절하지 않으며 수락 시 최신 상태로 재검증한다.
- **FR-63** 확정 예약은 이후 허용 규칙 변경으로 삭제하지 않는다. 외부 일정과 새 충돌이 발견되면 당사자의 화면에 표시하되 자동 취소하지 않는다. 기존 요청 철회·수락·겹치는 요청 자동 거절 규칙을 유지한다.

## 5. 비기능 요구사항

- **NFR-01** 기존과 같이 한국어 UI, KST 기준 표시·프로필 설정, 미래 60일·30분 시작 격자·최소 2시간 후 예약을 사용한다. 외부 시간대를 올바르게 변환하되 사용자별 시간대 설정 UI는 첫 버전에서 제외한다.
- **NFR-02** 슬롯 계산은 기존 성능 기준인 1초 이내를 유지한다. 외부 일정 조회·AI 시간은 분리해서 측정한다. 온보딩 대화는 p50 3초를 초기 목표로 하고 달성 여부를 평가한다. 외부 호출에는 제한 시간을 두고 대기·재시도 상태를 표시한다.
- **NFR-03** AI 출력은 구조 검증을 거쳐 초안에 반영한다. 잘못된 출력은 한 번 재시도하고 실패하면 상태를 유지한다. 계산 결과와 달리 시간·장소·빈도를 만들어낸 출력은 그대로 확정하지 않는다.
- **NFR-04** 일정 제목·장소 등 외부 텍스트는 분석 데이터로 취급하며 그 안의 지시문으로 앱의 규칙·도구 호출을 바꾸지 않는다. AI에는 해당 사용자의 분석에 필요한 필드와 집계만 전달한다. 연결 단계에서 외부 AI 분석에 쓰이는 데이터 범위를 안내한다.
- **NFR-05** 연결 토큰과 API 키는 서버에서 관리하고 사용자 간에 공유하지 않는다. 로그에는 일정 제목·장소·대화 본문·토큰을 기록하지 않는다. 상대방에게는 슬롯과 필요한 추천 근거만 제공한다.
- **NFR-06** 테스트는 고정 시각·고정 캘린더 자료로 반복 가능해야 한다. 실제 외부 서비스 호출이 필요한 검증과 오프라인 자동 테스트를 구분한다. 실제 연동 수용 기준을 목 데이터 통과만으로 충족했다고 보고하지 않는다.
- **NFR-07** 프로필 저장·수집 반영·예약 검증은 부분 적용을 방지한다. 조회 중 중복 클릭이나 재요청으로 일정·초안·첫 응답을 중복 생성하지 않는다.

| AC-11 | 추천 뒤 외부 일정 추가 / 수락 전 연결 실패 | 전송·수락 전에 최신 조회로 충돌 차단. 조회 실패 시 예약 동작을 완료하지 않음 | FR-18, FR-62 |
| AC-12 | 연결 해제·프로필 변경·대기/확정 예약 존재 | 외부 자료 제거와 지속 사용 선택 제공. 프로필·앱 일정 보존, 기존 예약 자동 삭제 없음 | FR-19, FR-62–63 |

추가 회귀 검증: 기존의 요청 철회, 수락 트랜잭션, 양쪽 캘린더 반영, 겹치는 대기 요청 자동 거절, 권한 검사 시나리오가 유지돼야 한다.

## 7. 제품 검증

- 같은 일정 자료로 직접 설정과 AI 제안 기반 설정을 비교해 완료 시간·완료율·수정한 항목을 관찰한다.
- 제안 수락률만으로 추정 정확도를 판단하지 않는다. 완료 후 사용자가 설정의 의미를 설명하고 의도와 맞는지 확인하게 한다.
- 새 예약에서는 첫 후보 선택 여부, 첫 선택까지 대화 턴 수, 기본 선호를 해제한 이유를 관찰한다.
- 근무시간·미팅 허용 시간·선호별 수정 이유를 구분해 다음 개선에 사용한다. 수치 목표는 초기 검증 후 정한다.

## 9. 연동 근거

공급자 필드와 권한·변경 반영 방식은 공식 문서를 확인했다. 분석 기간, 초대 차단 정책, 재조회 시점은 위에서 정한 앱의 정책이며 공급자의 권장값을 뜻하지 않는다.

- 시작·종료, 반복 회차, 바쁨, 취소, 장소와 화상회의 정보의 의미: [Google Calendar Events](https://developers.google.com/workspace/calendar/api/v3/reference/events).
- 읽기 전용 권한 선택의 근거: [Google Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth). 구체적인 권한 조합은 아키텍처에서 필요한 필드와 대조한다.
- 변경·삭제 반영과 재동기화 처리의 근거: [Synchronize resources efficiently](https://developers.google.com/workspace/calendar/api/guides/sync). 증분 조회와 전체 재조회 중 구현 방식은 아키텍처에서 결정한다.
