# Design

## Context

See [proposal.md](proposal.md). Follow the [implementation plan](../../../documentations/technical_specification/04_implementation_plan.md): root `agent/`, Next.js in `apps/web/`, shared contracts and authorized server operations in root `lib/`, and separately built eve/web services composed through root `vercel.ts`. The reconstruction target is `https://release.findmeatime.com` with Supabase project `mriseqztcwmezvtawnbo`. Runtime and provider compatibility require fresh verification.

## Goals / Non-Goals

**Goals:** one authorized setup state across web and private iMessage; useful suggestions with explicit choices; secure browser continuation; restart-safe transport and honest readiness.

**Non-Goals:** group iMessage, booking approval during setup, guest scheduling logic in the onboarding agent, new Google scopes or a mandatory separate bridge service.

## Decisions

### Shared application authority

Eve tools delegate to authorized operations in `lib/server/`; model output cannot admit a host, authorize a grant or save settings by itself. Store host-owned transcript access, versioned drafts and current-review confirmations separately from provider identity. Serialize cross-channel mutations, reject stale reviews and recheck admission and channel authority before processing and dispatch. Use typed contracts for protected actions; runtime failure leaves confirmed settings unchanged and offers structured recovery.

### Agent guidance and preference confirmation

Derive the next action from authorized server state. Explicit current answers and confirmed settings outrank authorized observations, which outrank labeled starter defaults. Keep provenance, uncertainty and dismissed suggestions with the draft. Ask one focused unresolved question, allow correction/skip where permitted, and never guess identity, consent, verification codes, exact addresses or approval.

Explicitly ask online/in-person/either unless answered. In-person/either requires preferred areas/venues or **Decide per meeting**, then supported transportation or **Depends on the trip**, and a separate extra travel buffer. Suggestions accompany these questions but cannot count as answers. Online-only skips physical venue/travel questions. Current final review includes applicable explicit answers; actual bookings still resolve locations, modes and both travel legs.

### Calendar analysis and in-chat experience

After browser consent, recommend calendar roles from authorized metadata, distinguish conflict calendars from a writable booking destination and let the host choose a disclosed bounded scan. Resolve scan range, normalization and freshness limits before implementation. Normalize recurrence, timezone/DST, all-day, cancelled and free events server-side. Only minimized summaries reach the model; event text is untrusted data, not instructions. Candidate venues remain private and are not labeled home/work or published without explicit choice.

Calendar cards, scan state, editable weekly preview, preference actions and final review live inside `/app`. Use real status, accessible text alternatives, focus management and mobile/reduced-motion behavior. Sparse, partial, failed or revoked reads produce uncertainty and manual recovery. Applying a suggestion changes only the draft. Calendar selection, permissions, refreshed analysis or cross-channel edits invalidate dependent results and reviews. Future booking availability is checked again.

### Browser handoffs and private linking

Sign-in, email-bound invitation redemption and Google consent use protected browser controls; tokens never enter model context or transcripts. Resume from server state and recheck selected calendar IDs/permissions. iMessage continuation URLs contain no long-lived credentials.

After web settings review, show **Connect iMessage** and **Maybe later** inline. Phone entry → **Send code** → protected six-digit field → **Confirm and link** → verified connected state. Typed endpoints handle phone/code actions outside the model path. Store an expiring hashed challenge bound to the initiating browser and chosen private conversation, plus one durable outbound intent. Never return the code in the API or persist it in transcript, analytics or card state. Apply bounded attempts, rate limits, expiry and single-use consumption; change-number invalidates the prior challenge. A known failed/revoked dispatch cannot link; an accepted or uncertain send still requires code possession.

For iMessage-first entry, bind the short-lived browser continuation to the original private sender/conversation; require authenticated admission, a fresh response in that conversation and browser confirmation. Reject groups and mismatched identities. Permit one active private link per host and one host per channel identity; conflicts require explicit unlink/relink. Unlink revokes queued and outbound authority while web remains available.

### Photon transport and durable effects

Test eve's native Photon channel with the selected project and current SDK contract. Application-owned verified sender-to-host/session mapping remains mandatory. Persist/deduplicate provider IDs and outgoing intents, order turns by authorized conversation and distinguish acceptance, delivery, failure and uncertainty. A lost acknowledgement cannot trigger a fresh message identity or blind resend. Scope reconciliation to the authorized conversation. Validate the send response against the frozen text before binding its provider reference. Reconciliation must return the exact persisted reference, outgoing sender and expected chat; inconclusive or mismatched reads retain the original reference with uncertain status and never trigger a resend. A transient receipt-write failure with a validated provider reference permits one retry of the identical outcome and lease; it cannot retry a send, reacquire a lease or bypass an authority/lease conflict. Sustained failure remains unresolved.

The installed native adapter returns acknowledgment before downstream commit and cannot accept the application's durable send identity. The selected Next.js receiver, database inbox/outbox, eve execution and pinned low-level Photon SDK satisfy those boundaries without another process; local protocol tests cover frozen protobuf identity, no automatic resend and reference-only reconciliation. The receiver also bounds body reads to 32 KiB/five seconds and cancels stalled/aborted streams. Only create a narrow persistent bridge if a later runtime spike demonstrates it is necessary. In that case it receives scoped service credentials and delegates to application commands, with no arbitrary host-operation surface or embedded scheduling policy. Hosting selection remains a runtime gate, not an assumed Fly.io dependency.

## Risks / Trade-offs

- Concurrent channels → serialized operations and current revision checks.
- Private data or credential leakage → protected controls, minimized model context and host-only reads/streams.
- Provider outage or restart → durable inbox/outbox, conservative reconciliation and web continuation.
- False preferences → labeled evidence, explicit applicable answers and current final confirmation.

## Implementation and verification

Build private persistence/contracts, shared authorized onboarding operations, web guidance/cards and provider handoffs in that order. Preserve existing migration history and add reviewed migrations through pg-delta. Validate disposable local rebuilds and isolation before controlled live tests. Test current host setup, OTP linking, consent return, cross-channel resumption and revocation against the reconstruction origin. Disable affected entry points on failure without deleting settings or unresolved outbound evidence. The runtime transport choice and bounded scan contract are prerequisites to their implementation slices.

### Photon transport spike and durable receipt (2026-10-07)

The bundled eve 0.71.3 Photon adapter verifies signatures but acknowledges before its downstream promise settles. Replaying an event invokes that downstream path again; sending through `postMessage` supplies content without an application-owned retry identity. Executable synthetic compatibility probes exercise the installed adapter without initializing a provider connection. These observations select an application-owned ingress/outbound boundary inside the existing service graph, not an additional bridge process.

`POST /api/providers/photon` validates the raw signature, timestamp and configured receiver ID, then normalizes only private inbound text with consistent sender/platform/space/line evidence. The service-only ingress RPC checks the enabled receiver registry, serializes receipt order per project/line/space, and atomically commits a private inbox row plus a durable job. Deduplication uses project/message ID rather than unsigned header values; a changed body under the same ID is rejected. HTTP success follows commit. Neither provider authentication nor the stored inbox grants application authority. Linking, current-authority dispatch, outbound delivery/reconciliation and live provider acceptance remain pending, so the registry remains disabled until their verification.

### Implemented private drafts and review controls (2026-10-07)

The browser calls `HostSetup` and service-only `fmat_host_setup`; eve calls `fmat_conversation_tool` with the current execution grant. Both use the retained host-owned setup conversation/turn/draft/review tables. Mutations lock the current admitted host and setup conversation, bind immutable input to actor/operation/idempotency identity, and advance a conversation revision. Browser-authenticated edits receive host provenance; model edits receive assistant provenance. Confirmed policy is unchanged until the explicit confirmation transaction. Model suggestions cannot overwrite explicit answers or satisfy applicable mode/location/travel questions. Online normalization clears physical-field provenance so switching back requires an explicit answer.

Read projections separate confirmed settings, draft answers, original clarification questions, computed missing fields and the current review. Changes to confirmed rules or calendar selection hide stale reviews. Protected refresh requires current conversation/rules versions, preserves draft answers/provenance/questions and generates a new review; ordinary edits reject a stale base instead of discarding earlier answers. A fresh Google list checks selected IDs and destination write permission before confirmation, followed by atomic version/grant checks. Lost-confirmation replay reauthorizes the current host and does not save again. These operations create no booking work.

Structured in-chat forms support profile, timezone, weekly windows, meeting buffer, explicit mode/location, per-trip transportation and separate extra travel buffer during model failure. They label starter defaults and preserve unresolved questions until the host explicitly resolves them. Public-link readiness and complete linked-channel acceptance remain unfinished. The selected preset and inline browser linking card are now implemented.

The shared operations are now verified through actual eve calls from signed linked input: malformed output preserves state, ambiguous output retains clarification, a changed tool-call ID cannot bypass one mutation per message, and a later private draft invalidates the earlier web review. Only the host can confirm the current review in protected web controls; confirmation replay does not save twice or create booking work. These fixtures use injected providers and do not establish live Google/iPhone acceptance.

### Bounded Calendar analysis contract

An explicit browser scan selects 1–10 authorized calendars, an IANA display timezone, and an exclusive-end 14–56-day range within 90 days of today. Its default UI range is the next 28 days and is disclosed before reading events. Analysis selection does not change conflict calendars or the booking destination. Event reads use `singleEvents=true` and complete pagination (250 per page, ten pages per calendar), with a 20-second deadline, 10,000-event total cap, 2 MiB per-page and 8 MiB total response limits. Any failed, inaccessible, malformed or truncated calendar produces no usable result. No additional OAuth scope is requested.

Provider fields omit titles, descriptions and attendee identities; only the self attendee response is requested to exclude declined invitations. Recurrence expands at Google; normalization clips half-open intervals, uses each calendar's timezone for all-day exclusive dates, and rejects ambiguous offset-free times. Cancelled, transparent, declined and working-location entries do not count as busy. The suggested-window search frame is disclosed as weekdays 09:00–18:00: choose at most one two-hour gap per weekday that was clear on at least 75% of sampled dates. These are candidate preferences, never actual availability or a reservation. Fewer than five busy entries yields labeled weekday-afternoon starter defaults; a dense range with no qualifying gap requires manual times. Repeated plain-text locations (at least two entries, at most five candidates) and video-link counts remain unconfirmed observations. Source locations are private browser text and cannot issue instructions or imply home/work.

Scans bind current Auth/admission, connection generation, rules version and setup revision. Starting one advances the setup revision and supersedes pending reviews. Completion and application recheck those versions; applying also fetches current Calendar permissions. Results expire in 15 minutes; an interrupted scan becomes failed after 90 seconds and requires an explicit new attempt. Start identity prevents duplicate provider dispatch; up to three starts per host per minute are allowed. Scan rows are removed on that host's next scan/status operation after 24 hours; global retention cleanup is owned by the [bounded cleanup change](../archive/2026-10-09-expire-calendar-analysis-evidence/tasks.md), with local concurrency and actual production scheduler acceptance complete. Dismissal fingerprints suppress unchanged result content across later scans. Applying only fills missing nonexplicit schedule fields; explicit/confirmed values win, a conflicting display timezone requires manual correction or a new scan, and settings still require final confirmation. Replay does not create another draft.

Model reads expose only scope dates/timezone/count, derived windows/counts and fixed limitation codes; observed places and calendar IDs are excluded. Models cannot select/scan/apply/dismiss through these operations. The browser offers retry, refresh, dismissal and manual edits without a provider-success claim. Complete cross-channel guidance and live AC-28 remain acceptance work.

API semantics follow the [Google events list reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) and [event resource](https://developers.google.com/workspace/calendar/api/v3/reference/events), checked on 2026-10-07.

### Focused guidance progress

A shared browser-safe derivation supplies one next question to the UI and authorized model read. Host-only progress actions remember optional-analysis skip and schedule/mode dismissal/re-offering under current authority, revision and immutable idempotency identity. Scan start also persists the analysis choice; temporary summary deletion does not reset it. Existing scan evidence is backfilled separately from generated schema changes. These actions do not change settings. Schedule suggestions preserve existing values, label missing defaults, and offer use/adjust/manual paths; dismissed defaults are not repopulated in blank manual fields. Explicit physical location, transportation and extra buffer are paced separately, and the first clarification is resolved independently of later questions. Cross-channel acceptance remains open.

### Atomic reviewed suggestions and source retention

The shared guide directs hosts to current ready Calendar evidence before proposing starter defaults. The browser can review/edit windows, explicitly answer mode and applicable location, and apply the choices in one scan-bound action. Existing explicit answers are retained; a conflicting proposed replacement fails and must use ordinary editing. Place inputs reference a current private candidate index with an editable label, or provide a manual label. Online excludes place input; no venue can infer a mode. Each action rechecks fresh provider access and the existing grant/rules/setup fences before making one private draft.

Draft `origins` is separate from the human/assistant decision provenance: Calendar suggestions, host-edited Calendar suggestions and starter defaults keep their derivation after explicit acceptance. Minimal dates/timezone and scan ID remain with these origins after temporary summaries expire. Changed ordinary edits replace only their own origin; unrelated and unchanged values preserve it. Browser default actions can name bounded `starterFields` only when their values match the documented defaults; models cannot use that input or change dismissed schedule/mode guesses. Old drafts without evidence remain unannotated. End-to-end fixtures cover a no-history manual/default path and a rich edited-place path; live Calendar and linked-channel acceptance remain independent gates.

### Reusing extracted chat answers

The shared guide offers an `answers_review` step for supported assistant-provenance mode/location/transport/buffer values already in the current draft. It shows those values for explicit selection rather than asking the host to re-enter them. No checkbox starts selected; physical choices cannot be accepted while their suggested mode remains unchosen. Hosts can edit any extraction, accept a subset, and leave missing answers or clarification questions pending. Dismissed modes, stale drafts and online-only physical fields are excluded.

The existing protected draft action records only selected exact values at the displayed revision, with host provenance while preserving their assistant origin. This selection changes neither saved policy nor booking state. Reload resets unsubmitted checkboxes; a new revision remounts the review so an older selection cannot implicitly accept changed values. Final current-review confirmation remains separate. Natural-language extraction is not treated as proof of human authority, even when it appears to restate a host message. Model output and retained Calendar observations cannot bypass these controls. The actual linked iMessage equivalent and live model acceptance remain independent verification work.

### Browser-bound linking backend and delivery

The new `photon_link_challenges` row is both the private proof record and the durable outbound intent. It freezes the project, sender line, private recipient, Auth session, browser-proof hash and challenge UUID. Six-digit codes are generated cryptographically, HMAC-hashed with a domain-separated server key, and temporarily encrypted with project/host/challenge authenticated context. A separate same-origin `bind` action establishes an HttpOnly browser proof before `start`; a lost start response therefore cannot lose a newly issued binding cookie. Typed browser actions never route phone/code data through eve or transcript storage. Views disclose masked numbers and verification/delivery state only.

Codes expire ten minutes after the request, with five distinct guesses, one start per minute and five per hour per host and per project/recipient. Immutable request and guess keys prevent retries from issuing another code or consuming another guess. A replacement or cancellation invalidates the prior challenge; consumption clears protected material. Correct proof can resolve an uncertain send, but a prepared, failed, revoked, expired or locked challenge cannot link. Current Auth/admission, initiating browser/session, receiver configuration and one active host/recipient owner are checked transactionally. A successful retry returns the existing link; it cannot resurrect an explicitly unlinked one.

Authorization deadlines are checked again after receiver/challenge/recipient lock waits. Before a new link is inserted, the correct-code path rechecks both the challenge deadline and inbound-handoff validity under the recipient lock. Final delivery authorization repeats current Auth checks after acquiring the challenge lock. Rechecking already-held authority rows preserves the lock order. An exact successful verification retry may recover its still-active link after code expiry, but never create or resurrect a link.

The code worker claims up to five oldest-due intents with two-minute leases, acquiring selected hosts in consistent order. It records uncertainty before external work, rechecks authority after route/address preflight, and uses the challenge UUID as the supported low-level Photon `clientMessageId`. The pinned `@photon-ai/advanced-imessage` 2.2.0 gRPC transport disables automatic retries and automatic message-ID generation, fixes the selected line and closes its per-call client. Duplicate acceptance is distinct from device delivery. Lost responses or expired worker leases permit read-only reconciliation of the same provider reference, never another send. A missing reference remains uncertain until proof/expiry; hosts can explicitly request a later challenge under the same limits. Unexpected database failures abort a claim rather than being interpreted as revocation.

The named `fmat-photon-links` cron sweep calls `/api/internal/photon/dispatch` only for due work. It derives the fixed endpoint from the verified release runtime URL in Vault and uses the existing internal dispatch secret. No Vault configuration means no network activity. This challenge-owned sweep avoids a second queue/job lifecycle for the same code. Disabled receivers prevent new sends and links. Inbound-first linking, linked host execution, general conversational outbound delivery and live recipient acceptance remain separate unfinished work; this backend alone does not enable the receiver or certify Phase 7.

### Inline linking UI and preset

`IMessageLink` follows current settings confirmation inside the existing chat scroller, without a new route or settings dialog. Protected phone/code actions bypass eve. Masked state polls while visible and refreshes on focus; a generation fence discards older reads during mutations. Lost start responses retry the same immutable input, while uncertain verification requires code re-entry against an in-memory attempt ID/digest. Raw code state clears on every submit and is never persisted. Invalid guesses return keyboard focus to the empty invalid field.

Expiry and cooldown are displayed locally but enforced by the server. Change-number cancels first; new-code requests re-enter the private number. Skip persists, unlink requires an explicit confirmation, and unavailable configuration offers web continuation. Acceptance, delivery and connection remain distinct. The selected `b6rtA2Hmi` theme/font were applied through the shadcn CLI; existing components retain their composition, olive/green semantic tokens replace legacy shell colors, and Next.js self-hosts Inter.

The preset’s light-mode muted foreground is darkened to OKLCH lightness 0.54 so small helper text reaches at least 4.5:1 against both white and muted surfaces. The latest-message control occupies its own chat footer, with a 44px target, so it cannot obscure inline actions. The message-scroller primitive continues to own scroll state and inactive-control behavior.

### Linked private input execution

Signed ingress freezes the receiver ID and the exact active project/phone/line/private-space link at receipt. Provider timestamps predating the link or more than five minutes ahead do not bind; historical and unlinked receipts remain unbound. Replaying a provider message cannot attach it to a later link. Phone/space/line matching follows the [Photon event contract](https://photon.codes/docs/webhooks/events), checked on 2026-10-07.

The service-only `fmat_photon_dispatch` transaction consumes one eligible linked receipt, preserving receipt order per private route. It respects an active transport job lease, recovers an expired lease, and waits while the canonical host setup conversation has a pending runtime input. Other hosts can proceed. Input acceptance, transport-job completion and queue acknowledgment commit together; lost acknowledgments cannot duplicate input. A bounded server sweep invokes at most five such transactions, each holding only one host's locks. Existing eve runtime recovery then executes the input in the same conversation/session used by web.

Each receipt has an internal grant expiring one hour after receipt, with no retry extension. This is an execution deadline, not expiry of the phone link or web conversation. The grant rechecks current admission, confirmed/unbanned/nondeleted account and admitted email, the frozen receiver, and that exact active private link before runtime delivery and every tool call. Browser logout does not itself unlink a separately verified phone; explicit unlink, account/admission revocation and receiver replacement deny subsequent channel execution. The browser credential entrypoint cannot accept this grant's private credential shape. Suppressed/expired input records a terminal outcome without reaching the model. Setup tools can read and draft with iMessage attribution but cannot confirm settings, approve a proposal or create a booking.

The `fmat-photon-inbox` minute schedule derives the same protected `/api/internal/photon/dispatch` endpoint from the existing runtime Vault configuration. No configured Vault entries means no network activity. Inbound-first browser continuation and live private-channel acceptance remain unfinished; keep the production receiver inactive until those gates pass.

### Durable private replies

Capture final assistant text synchronously in the channel checkpoint, keyed by accepted input and output sequence. Do not reconstruct output from the raw event stream, which can include abandoned model attempts. The installed eve 0.71.3 adapter logs and swallows handler failures rather than retrying them; therefore SQL settlement and reply creation share a transaction. Failure leaves input pending, and repeated delivery of a checkpointed completed input retries settlement without model execution. Late turn/session failure preserves saved completion. One inbox owns one frozen reply, with no reply for web-only input and a fixed recovery message for failed/empty output.

`fmat_photon_reply_delivery` is service-only. Claims acquire authority before reply locks, check the exact frozen link/receiver, and persist uncertainty before transport work. The stable reply UUID is the provider client message ID. Two-minute leases fence results, and uncertain earlier replies block later ones for that private route until known acceptance or suppression. Current authorization is checked again after external preflight. Recovery reconciles the same reference without resending; absent references remain uncertain. Terminal delivery/failure or revocation removes the body. A dedicated minute cron and authenticated Next.js route reuse existing Vault configuration and the pinned transport, with five claims per sweep. Complete live channel acceptance remains separate from local SQL, runtime and transport fixtures.

### Unlinked private continuation foundation

Signed unlinked receipts have a separate service-only handoff intent. Preparation locks the transport job, current receiver and phone scope, rejects noncanonical/private mismatches, provider timestamps outside five minutes, receipts older than fifteen minutes and identities that have since linked. It permits one continuation per sender per five minutes and five per hour. Receipt completion, job/publication acknowledgment and encrypted continuation creation commit together. The original unlinked message never inherits later host authority or reaches eve.

Each continuation has a random 256-bit token, a SHA-256 lookup proof and AES-GCM ciphertext bound to project/intent. Its lifetime ends fifteen minutes after receipt, with no retry extension. Synthetic dispatch uses a fixed setup message and `/app#imessage=<id>.<token>`, preserving the exact sender line/private recipient and stable provider message ID. It rechecks receiver/current-link status after preflight, persists uncertainty before sending and uses reference-only reconciliation. Delivered, failed and revoked intents clear ciphertext; token resolution checks lifetime, exact receiver and unlinked status and returns server-only route metadata, never host/account records.

The browser exchange now establishes an HttpOnly browser proof in a separate request before binding the continuation. It strips the fragment before network activity, stores the bounded proof in a second HttpOnly cookie and retains it through sign-in/admission. Anonymous responses contain only masked phone and expiry. An admitted host explicitly requests a fresh OTP for the immutable original sender/line; no client-supplied route can replace it. The handoff permits one challenge, with immutable retry identity and Auth session/browser ownership. Its deadline also caps the code deadline. Current receiver identity, expiry and revocation are checked before code dispatch and verification. Existing code-attempt replay preserves a successful link without resurrecting an unlinked identity.

Inbound linking is available inside `/app` before settings confirmation; browser-first linking retains its normal position after confirmation. Skip, cancel and successful verification clear the continuation cookie. Unlinked text never inherits later host authority. A dedicated authenticated `/api/internal/photon/handoffs` worker and minute sweep prepare and dispatch up to five entries using the existing Vault runtime URL/dispatch secret. Unconfigured or disabled receivers do not trigger scheduled network activity. Local browser and database fixtures cover this path; live provider/actual iPhone acceptance and receiver activation remain separate gates.

### Cross-channel readiness reporting

The authored `read_context` tool accepts `setup_readiness` without model-supplied identity or URLs. It reads setup under the current execution grant, calls the existing public profile/Calendar permission service for that confirmed handle, and rechecks private authority and setup/rules/connection revisions after external I/O. Missing Calendar access returns not-ready; transient errors, changed revisions or lost authority return no links. A current result exposes only the canonical booking and agent-instruction URLs. The browser and private channel share the same confirmed handle and public permission boundary. Deterministic signed-input/eve fixtures cover ready reporting and disconnect recovery; live Google/iPhone acceptance remains separate.

### Application-authored setup clarifications

The shared setup operation currently accepts arbitrary `unresolved` text. A rollback-only regression through `fmat_conversation_tool` reproduced a Korean claim that settings were saved and booking completed in `draft.clarifications`, while confirmed settings remained unchanged. Structured guidance must not grant that text application authority.

Eve and external-agent draft contracts accept finite clarification categories with optional English/Korean selection. Their server adapters encode categories for the shared database operation. The database authors questions and projects only recognized authored wording; unknown legacy text becomes a fixed neutral clarification. Preserve order and pending-question cardinality, including during rebase and exact retries. Browser edits can carry or resolve those displayed questions. Do not clear pending questions merely because their old wording is untrusted.

Normalize new stored clarification wording and all current-state projections, including replay results. Keep immutable original idempotency inputs unchanged so a changed retry remains a conflict; do not rewrite historical transcripts or claim old backups are sanitized. Accept old callers at the SQL boundary through neutral fallback during deployment, while new typed model/agent contracts reject free-form clarification text. This protection covers structured guidance; the existing honest completion requirement still applies to free-form assistant narration and requires separate runtime acceptance.
