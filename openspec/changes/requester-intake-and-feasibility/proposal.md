# Proposal

## Why

Phases 1 and 2 give a host an account, confirmed settings and a public `/{handle}` page, but that page and `/{handle}/SKILL.md` still say requests are not accepted yet. The [implementation plan](../../../documentations/technical_specification/06_implementation_plan.md#phase-3--requester-intake-and-feasibility) makes Phase 3 the step where a requester reaches a ready host, is understood, and sees feasible candidates, so that Phase 4 has a real request awaiting approval to review and book. Nothing in this change approves or books a meeting.

The main specifications already state most of the behavior: [meeting requests](../../specs/meeting-requests/spec.md), [meeting feasibility](../../specs/meeting-feasibility/spec.md), [email delivery](../../specs/email-delivery/spec.md) and the admission and redaction parts of [chat workspaces](../../specs/chat-workspaces/spec.md). Two things block implementation: decisions the plan assigns to this phase, and conflicts between owning documents, one of which is a requester Google sign-in path that does not exist.

## What Changes

- **Public intake and the booking link.** `/{handle}` opens an assistant conversation for a ready host's visitors and accepts a request. Request creation issues a random UUID booking link stored as a hash, with a thirty-day lifetime, `Referrer-Policy: no-referrer`, no indexing and the generic unavailable view with **Resend my booking link**. `/{handle}/SKILL.md` stops saying intake is closed.
- **Guest identity and timezone.** **Continue with Google** through a new request-bound Google OAuth flow with its own callback, separate from host sign-in (it may reuse the host sign-in OAuth client), recording identity and read-only Calendar access as two grants bound to the request. **Continue without Google** with a compact name and email card. The browser's IANA zone is shown beside times with a selector, and an explicit choice survives reload and Google return.
- **Request lifecycle.** Gathering, negotiating and awaiting-host-approval states, seven-day and window-end expiry, and withdrawal. Booking, booked and declined arrive with Phase 4.
- **Contact confirmation and email.** A Cloudflare Email Service adapter with delivery evidence and frozen dispatch identity; the creation email with the booking link and an optional confirmation link; the bounded link resend to confirmed addresses.
- **Conversation protection.** Credential redaction of conversation input and the conversation admission budgets with recoverable throttling, for host and requester conversations alike.
- **Feasibility.** A deterministic engine for full intervals, date-specific offsets, overnight windows, busy and focus constraints, the weekly limit as a preference, both host travel legs through Google Routes with host buffers, the requester's own travel legs when their calendar is connected, and the shared 18-second deadline; model ranking of valid candidates only.
- **Requester conversation.** The shared requester audience with `read_request` (requester projection), `draft_request_review`, `evaluate_candidates` and `read_booking_status`, the `requester.md` fragment, authored English and Korean clarification questions, the candidate times card, **Choose this time**, the exact proposal version and **Agree to this proposal**.

## Decisions

The plan assigns D1–D6 to Phase 3; designing them raised D7–D12, and using the deployed flow raised D13. Dohyeon Park decided each one on 2026-10-21, choosing between the options the earlier draft of this proposal set out; the [design](design.md) records the reasoning and the rejected options. The decisions were made before a teammate reviewed this proposal, so the plan's **Teammate review** box covers reviewing them.

| # | Decision | Choice |
|---|---|---|
| D1 | Supported geography, route freshness and adjacency ([design 9](design.md#9-travel-legs-and-google-routes)) | No country list: wherever Google Routes returns a route for the mode. Each leg checks the nearest commitment before or after the candidate on the same local day, whatever the gap; an overnight window's candidate uses the window's starting day. An adjacent event with no location, only a conference link, or both a place and a link leaves its leg unresolved. Estimates are reused for 24 hours per endpoints, mode and 15-minute departure slot. Lane C records which modes route in South Korea. Freshness at booking is for the Phase 4 proposal. Rejected: a country allowlist; a 3-hour horizon |
| D2 | Manual travel allowance granularity ([design 10](design.md#10-manual-travel-allowances)) | Per candidate leg: one allowance covers one leg of one candidate, in 5-minute steps from 5 to 240 minutes, and is void when that candidate's interval, either endpoint or the mode changes. The host confirms it in Phase 4; Phase 3 builds the engine input. Rejected: per request and endpoint pair; a standing host rule |
| D3 | Contact confirmation, replacing verification codes ([design 6](design.md#6-contact-confirmation)) | Confirmation is optional. When a request is created or its contact address changes, one email carries the booking link and a single-use confirmation link; opening it marks the address confirmed. Nothing waits on confirmation; the host sees whether the address is confirmed. A Google-verified address counts as confirmed. Only a confirmed address receives **Resend my booking link**. Sending the confirmation email again: 60 seconds apart, 5 per request and 10 per address per hour, 1,000 per day service-wide. Trade-off accepted: a mistyped address receives the booking link, as with Calendly and Cal.com. Rejected: six-digit codes |
| D4 | Cloudflare sending and evidence ([design 5](design.md#5-cloudflare-email-adapter)) | The REST API from the web service with an account-scoped **Email Sending: Edit** token in the existing `CLOUDFLARE_EMAIL_API_TOKEN`; `findmeatime.com` onboarded under **Email Sending** (`cf-bounce` MX, SPF, DKIM and `_dmarc`); the Workers Paid plan. Evidence: every recipient delivered or queued, plus an application dispatch ID in an `X-` header. Rejected: a Worker relay |
| D5 | `evaluate_candidates` placement ([design 8](design.md#8-evaluation-runs-as-an-application-job)) | A durable application job that the tool publishes and awaits for up to 20 seconds; the **Find times** card runs the same job. Rejected: running inside the tool's workflow step |
| D6 | Online meeting link, moved here from Phase 4 ([design 11](design.md#11-online-meeting-link-plan)) | A Google Meet conference created with the event when the booking destination supports it, otherwise an `https:` link the requester supplies. Rejected: a host-saved link; requester links only |
| D7 | Request creation bounds ([design 2](design.md#2-one-guest-thread-from-the-first-message)) | 5 per source address per hour and 20 per day, 500 service-wide per day, and no per-host cap, so nobody can block a host's intake. Rejected: a per-host cap of 30 a day; looser numbers |
| D8 | Requester Google consent ([design 3](design.md#3-requester-google-consent)) | A request-bound flow requesting `calendar.calendarlist.readonly` and `calendar.events.readonly`, always shown. It reuses the host sign-in OAuth client by default (`GOOGLE_REQUESTER_CLIENT_ID`/`GOOGLE_REQUESTER_CLIENT_SECRET` may name another), and grants are delete-only: closure, link expiry and **Disconnect** delete the stored token and never call Google's revocation endpoint (decided by Dohyeon Park on 2026-10-22). Event details are used for host-style busy rules and for the requester's own travel legs, and are never shown to the host or any agent. This changes PRD FR-12 and section 5, which said requester access was availability-only. While the Google app is in Testing, consent fails for unlisted users. Rejected: free/busy only; hiding the button until publication; revoking at Google on closure (on a shared client it would also revoke the host's Calendar grant) |
| D9 | Local messaging ([design 13](design.md#13-local-messaging)) | Local execution can send only toward a loopback stand-in. Rejected: admitting local sending; denying local sending entirely |
| D10 | Booking link storage ([design 7](design.md#7-link-resend)) | Lookup by hash, with the UUID sealed under `TOKEN_ENCRYPTION_KEY` and opened only to email it to the requester or finish their Google return. Rejected: rotating the link on resend |
| D11 | Public page before identification ([design 2](design.md#2-one-guest-thread-from-the-first-message)) | Revised by D13 on 2026-10-22: the assistant conversation on `/{handle}` is kept, but runs as a draft request instead of a separate anonymous intake. Rejected then: a static intake page |
| D12 | Contact verification before agreement | Withdrawn by D3: nothing waits on confirmation |
| D13 | Continuous, chat-native guest experience ([design 2](design.md#2-one-guest-thread-from-the-first-message), [design 12](design.md#12-requester-conversation)) | Decided by Dohyeon Park on 2026-10-22. The first message on a ready host's `/{handle}` creates a **draft request**: hidden from the host, deleted after 24 hours if the guest never identifies, under the creation bounds and the unconfirmed-request model cap. One assistant session serves the whole thread from that first message to agreement. Identity, timezone, contact confirmation, Calendar connection, reviews, candidates, the proposal and status are cards inside the thread, at the point the conversation needs them; no form or card sits outside it. Once the guest is identified, the address bar changes to `/booking/{bookingId}` in place, without a reload, and the same thread continues there and after a Google return. Rejected: stitching a separate intake session to the request session, which keeps the seam under the hood |

## Conflicts resolved here

| Conflict | Resolution |
|---|---|
| **Requester Google sign-in has no account-free path.** The only Google path, `completeGoogleSignIn` → `ensureHostAccount`, creates a host account, and [`chat-workspaces`](../../specs/chat-workspaces/spec.md#requirement-google-only-mvp-host-login) fixes `/auth/callback` to return to `/app`. [`host-admission`](../../specs/host-admission/spec.md#requirement-requesters-remain-account-independent) requires requesters to stay account-free | A separate, application-owned Google OAuth flow that never touches Supabase Auth: started from `/{handle}` or `/booking/[bookingId]`, returning to `/connections/google/callback`, bound to one intake or request, recording identity prefill and an availability-only Calendar grant against the request. The new `requester-calendar-access` capability states it ([design 3](design.md#3-requester-google-consent)) |
| **Unavailable booking page.** The `chat-workspaces` scenario "Request link without authority" forbids recovery controls; [`meeting-requests`](../../specs/meeting-requests/spec.md#requirement-accessible-link-resend) requires a resend control on the unavailable view | MODIFIED `chat-workspaces` "Conversation-first entry": the view offers only the generic link resend, still with no credential-paste field |
| **Local messaging.** [`messaging-environments`](../../specs/messaging-environments/spec.md#requirement-preserve-admitted-environment-authority) admits standalone local execution; [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md#local-development-and-deployment) and the plan deny it. The [foundation design](../application-foundation/design.md#open-questions) asks for a fix before the first transport | MODIFIED `messaging-environments` per D9, and Lane B's first task changes the gate before the Cloudflare adapter exists. Agent configuration and the plan are corrected to name the loopback exception |
| **Conversational public page.** The [page list](../../../documentations/user_experience/04_page_list.md#primary-pages) P08 and the [guest booking flow](../../../documentations/user_experience/06_guest_booking_flow.md#steps) describe a conversational intake on `/{handle}` that gathers every field | No conflict after D11: `/{handle}` keeps a conversational intake, under an anonymous intake principal until the request exists |
| **Online meeting link phase.** Plan Phase 3 lists "who creates an online meeting link"; the plan's decision table assigns it to the Phase 4 proposal | Phase 3, because requester agreement in this phase already covers the proposal's link plan (D6). The decision table and PRD section 10 are corrected |

## Capabilities

### New Capabilities

- `requester-calendar-access`: the request-bound Google flow for requesters: its own callback and browser binding, identity prefill and the Google-verified contact, a read-only Calendar grant recorded separately and used only privately for busy intervals and the requester's travel, calendar selection, request-bound lifetime with delete-only closure, and failures that pause evaluation instead of reading as free time. The PRD's [guest identity section](../../../documentations/02_product_requirements.md#guest-identity-timezone-and-optional-google-connection) and AC-27 describe the intent; no capability spec holds the contract.

### Modified Capabilities

- `meeting-requests`: the booking link may be kept sealed (D10); the three code-verification requirements are replaced by optional contact confirmation (D3); the anonymous intake conversation and request creation gain bounds (D7, D11); the proposal gains its online meeting link plan (D6).
- `meeting-feasibility`: route estimates gain their geography, adjacency and freshness rules (D1), manual allowances their per-leg scope (D2), and connected requesters their own travel legs (D8).
- `email-delivery`: delivery evidence accepts recipient acceptance with an application dispatch identity when Cloudflare returns no message ID (D4).
- `chat-workspaces`: the unavailable booking view offers link resend.
- `messaging-environments`: local execution is denied except toward a loopback stand-in (D9).

## Impact

- **New code:** `lib/server/{requests,intake,booking-links,requester-google,requester-calendar,contact-verification,link-resend,email-delivery,cloudflare-email,conversation-admission,redaction,feasibility,routes-client,evaluation}*.ts`, `lib/contracts/{request,feasibility,requester}*.ts`, `agent/tools/request.ts` (one resolver for request discussions), `agent/instructions/requester.ts`, the `/{handle}` intake and `/booking/[bookingId]` pages, `/connections/google/{start,callback}`, `/api/requests/*` and `evals/`.
- **Schema:** private tables for requests, booking links, intake transactions, requester grants, proposals and agreements, evaluations, route estimates, verification challenges, email deliveries, resend issuance and admission windows, plus the request expiry schedule, generated through pg-delta.
- **Systems:** the host sign-in web OAuth client in the Google Cloud project `findmeatime` (or an optional second client for requesters) gains the `calendar.events.readonly` scope on the consent screen and the redirect URIs `https://findmeatime.com/connections/google/callback`, `https://release.findmeatime.com/connections/google/callback` and `http://localhost:3000/connections/google/callback`; the Google Cloud project enables the Routes API with a server key restricted to it; Cloudflare onboards `findmeatime.com` for Email Sending and issues one token; Vercel Production sets the existing `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_EMAIL_API_TOKEN`, `CLOUDFLARE_EMAIL_FROM` and `GOOGLE_MAPS_API_KEY`, and `GOOGLE_REQUESTER_CLIENT_ID` and `GOOGLE_REQUESTER_CLIENT_SECRET` only if a separate requester client is used; tests use `CLOUDFLARE_EMAIL_API_URL` and `GOOGLE_ROUTES_API_URL` for stand-ins; a migration on the shared project `anelszynxtvxoxqvzgqt` after a shown dry run.
- **Documents:** the plan's decision table and Phase 3 boxes, PRD section 10, [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md), [provider setup](../../../documentations/technical_specification/03_provider_setup.md), the [page list](../../../documentations/user_experience/04_page_list.md), the [guest booking flow](../../../documentations/user_experience/06_guest_booking_flow.md#open-decisions), `.env.example` and the acceptance record, with the Korean mirrors regenerated.
- **Tracking:** the tracking-issue rule proposed in PR #20 has not reached `main`, so this change has no tracking issue yet.
