# Proposal

## Why

Phases 1 and 2 give a host an account, confirmed settings and a public `/{handle}` page, but that page and `/{handle}/SKILL.md` still say requests are not accepted yet. The [implementation plan](../../../documentations/technical_specification/06_implementation_plan.md#phase-3--requester-intake-and-feasibility) makes Phase 3 the step where a requester reaches a ready host, is understood, and sees feasible candidates, so that Phase 4 has a real request awaiting approval to review and book. Nothing in this change approves or books a meeting.

The main specifications already state most of the behavior: [meeting requests](../../specs/meeting-requests/spec.md), [meeting feasibility](../../specs/meeting-feasibility/spec.md), [email delivery](../../specs/email-delivery/spec.md) and the admission and redaction parts of [chat workspaces](../../specs/chat-workspaces/spec.md). Two things block implementation: decisions the plan assigns to this phase, and conflicts between owning documents, one of which is a requester Google sign-in path that does not exist.

## What Changes

- **Public intake and the booking link.** `/{handle}` accepts a request from a ready host. Request creation issues a random UUID booking link stored as a hash, with a thirty-day lifetime, `Referrer-Policy: no-referrer`, no indexing and the generic unavailable view with **Resend my booking link**. `/{handle}/SKILL.md` stops saying intake is closed.
- **Guest identity and timezone.** **Continue with Google** through a new request-bound Google OAuth flow with its own OAuth client and callback, separate from host sign-in, recording identity and availability-only Calendar access as two grants bound to the request. **Continue without Google** with a compact name and email card. The browser's IANA zone is shown beside times with a selector, and an explicit choice survives reload and Google return.
- **Request lifecycle.** Gathering, negotiating and awaiting-host-approval states, seven-day and window-end expiry, and withdrawal. Booking, booked and declined arrive with Phase 4.
- **Contact proof and email.** A Cloudflare Email Service adapter with delivery evidence and frozen dispatch identity; six-digit contact verification codes; the bounded link resend.
- **Conversation protection.** Credential redaction of conversation input and the conversation admission budgets with recoverable throttling, for host and requester conversations alike.
- **Feasibility.** A deterministic engine for full intervals, date-specific offsets, overnight windows, busy and focus constraints, the weekly limit as a preference, both travel legs through Google Routes with host buffers, and the shared 18-second deadline; model ranking of valid candidates only.
- **Requester conversation.** The shared requester audience with `read_request` (requester projection), `draft_request_review`, `evaluate_candidates` and `read_booking_status`, the `requester.md` fragment, authored English and Korean clarification questions, the candidate times card, **Choose this time**, the exact proposal version and **Agree to this proposal**.

## Decisions to settle

The plan assigns D1–D6 to Phase 3; designing them raised D7–D12. Each one changes what a teammate builds, so none of them is settled by this proposal alone: the [design](design.md) records the options and the reasoning, the delta specs are written against the recommendation, and the **Teammate review** box in the plan stays open until the team signs each one off. A different choice changes the named delta and design section before any lane codes.

## Conflicts resolved here

| Conflict | Resolution |
|---|---|
| **Requester Google sign-in has no account-free path.** The only Google path, `completeGoogleSignIn` → `ensureHostAccount`, creates a host account, and [`chat-workspaces`](../../specs/chat-workspaces/spec.md#requirement-google-only-mvp-host-login) fixes `/auth/callback` to return to `/app`. [`host-admission`](../../specs/host-admission/spec.md#requirement-requesters-remain-account-independent) requires requesters to stay account-free | A separate, application-owned Google OAuth flow that never touches Supabase Auth: started from `/{handle}` or `/booking/[bookingId]`, returning to `/connections/google/callback`, bound to one intake or request, recording identity prefill and an availability-only Calendar grant against the request. The new `requester-calendar-access` capability states it ([design 3](design.md#3-requester-google-consent)) |
| **Unavailable booking page.** The `chat-workspaces` scenario "Request link without authority" forbids recovery controls; [`meeting-requests`](../../specs/meeting-requests/spec.md#requirement-accessible-link-resend) requires a resend control on the unavailable view | MODIFIED `chat-workspaces` "Conversation-first entry": the view offers only the generic link resend, still with no credential-paste field |
| **Local messaging.** [`messaging-environments`](../../specs/messaging-environments/spec.md#requirement-preserve-admitted-environment-authority) admits standalone local execution; [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md#local-development-and-deployment) and the plan deny it. The [foundation design](../application-foundation/design.md#open-questions) asks for a fix before the first transport | MODIFIED `messaging-environments` per D9, and Lane B's first task changes the gate before the Cloudflare adapter exists. Agent configuration and the plan are corrected to name the loopback exception |
| **Conversational public page.** The [page list](../../../documentations/user_experience/04_page_list.md#primary-pages) P08 and the [guest booking flow](../../../documentations/user_experience/06_guest_booking_flow.md#steps) describe a conversational intake on `/{handle}` that gathers every field | D11: `/{handle}` gathers purpose, identity and timezone without a model, and the conversation continues at the booking link. Both documents are corrected |
| **Online meeting link phase.** Plan Phase 3 lists "who creates an online meeting link"; the plan's decision table assigns it to the Phase 4 proposal | Phase 3, because requester agreement in this phase already covers the proposal's link plan (D6). The decision table and PRD section 10 are corrected |

## Capabilities

### New Capabilities

- `requester-calendar-access`: the request-bound Google flow for requesters: its own callback and browser binding, identity prefill and the Google-verified contact, an availability-only Calendar grant recorded separately, calendar selection, request-bound lifetime and revocation, and failures that pause evaluation instead of reading as free time. The PRD's [guest identity section](../../../documentations/02_product_requirements.md#guest-identity-timezone-and-optional-google-connection) and AC-27 describe the intent; no capability spec holds the contract.

### Modified Capabilities

- `meeting-requests`: the booking link may be kept sealed for resend (D10); contact verification gains its numbers (D3) and is required before agreement (D12); request creation gains bounds (D7); the proposal gains its online meeting link plan (D6).
- `meeting-feasibility`: route estimates gain their geography and freshness rules (D1) and manual allowances their scope and granularity (D2).
- `email-delivery`: delivery evidence accepts recipient acceptance with an application dispatch identity when Cloudflare returns no message ID (D4).
- `chat-workspaces`: the unavailable booking view offers link resend.
- `messaging-environments`: local execution is denied except toward a loopback stand-in (D9).

## Impact

- **New code:** `lib/server/{requests,intake,booking-links,requester-google,requester-calendar,contact-verification,link-resend,email-delivery,cloudflare-email,conversation-admission,redaction,feasibility,routes-client,evaluation}*.ts`, `lib/contracts/{request,feasibility,requester}*.ts`, `agent/tools/request.ts` (one resolver for request discussions), `agent/instructions/requester.ts`, the `/{handle}` intake and `/booking/[bookingId]` pages, `/connections/google/{start,callback}`, `/api/requests/*` and `evals/`.
- **Schema:** private tables for requests, booking links, intake transactions, requester grants, proposals and agreements, evaluations, route estimates, verification challenges, email deliveries, resend issuance and admission windows, plus the request expiry schedule, generated through pg-delta.
- **Systems:** a second web OAuth client for requesters in the Google Cloud project `findmeatime`, with the redirect URIs `https://findmeatime.com/connections/google/callback`, `https://release.findmeatime.com/connections/google/callback` and `http://localhost:3000/connections/google/callback`; the Google Cloud project enables the Routes API with a server key restricted to it; Cloudflare onboards `findmeatime.com` for Email Sending and issues one token; Vercel Production sets the existing `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_EMAIL_API_TOKEN`, `CLOUDFLARE_EMAIL_FROM` and `GOOGLE_MAPS_API_KEY` and gains `GOOGLE_REQUESTER_CLIENT_ID`, `GOOGLE_REQUESTER_CLIENT_SECRET` and `REQUESTER_GOOGLE_ENABLED`; tests use `CLOUDFLARE_EMAIL_API_URL` and `GOOGLE_ROUTES_API_URL` for stand-ins; a migration on the shared project `anelszynxtvxoxqvzgqt` after a shown dry run.
- **Documents:** the plan's decision table and Phase 3 boxes, PRD section 10, [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md), [provider setup](../../../documentations/technical_specification/03_provider_setup.md), the [page list](../../../documentations/user_experience/04_page_list.md), the [guest booking flow](../../../documentations/user_experience/06_guest_booking_flow.md#open-decisions), `.env.example` and the acceptance record, with the Korean mirrors regenerated.
- **Tracking:** the tracking-issue rule proposed in PR #20 has not reached `main`, so this change has no tracking issue yet.
