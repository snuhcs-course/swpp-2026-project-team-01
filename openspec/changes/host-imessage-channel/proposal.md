# Proposal

## Why

Phases 1 to 5 and 7 give the host the web workspace and personal agents, and give the requester the web and email. The PRD targets iPhone hosts (2026-10-07 audience decision) and asks for an opt-in private iMessage conversation in which a linked host receives request summaries, discusses and revises a proposal, approves or declines it, and runs setup ([FR-26 to FR-28](../../../documentations/02_product_requirements.md#host-imessage-channel), AC-16 to AC-18, the [linking paragraph in section 10](../../../documentations/02_product_requirements.md#10-dependencies-and-open-decisions)). The [implementation plan](../../../documentations/technical_specification/06_implementation_plan.md#phase-6--host-imessage-channel) makes this Phase 6.

Phase 0 retired the iteration-1 `imessage-agent` spec and the `host-imessage-assistant` change: one was an echo responder, the other a service-sent welcome over prototype tables that do not exist here, and both contradicted the PRD's host-sent link code ([OpenSpec status](../../README.md)). Only two main specifications mention iMessage at all: [chat workspaces](../../specs/chat-workspaces/spec.md) (messaging backpressure and the redaction of linking proofs) and [messaging environments](../../specs/messaging-environments/spec.md) (no delivery outside production). Nothing specifies how a sender is bound, what an inbound message may do, how decisions are made in text, or how messages go out. This change specifies all of it, with one product addition the user decided on 2026-10-23: **Connect iMessage** opens the Messages app in one tap with the link message already written.

## What Changes

- **Adapter (Lane A).** A transport spike compared eve's native Photon channel with an application-owned adapter on durable receipt, acknowledgment, exact sender identity and recovery. The application-owned adapter is chosen: `agent/channels/photon.ts` is a custom eve channel whose only route, `POST /photon/webhook`, verifies Photon's signature and stores a minimized receipt and one `imessage_receipt` job before answering `200`. Outbound text goes through one transport module, `lib/server/photon.ts`, behind the messaging gate: Photon's Spectrum SDK in production and a loopback stand-in locally and in tests.
- **Linking card (Lane B).** **Connect iMessage** in `/app` asks the server for a one-time link code and at once opens Messages addressed to the service's line with the exact link message in the input, so the host only taps send. Where Messages cannot open, the inline card shows the number, the code, **Copy** and a QR code that opens the same deep link on a phone. When the host's message arrives, the card shows the masked sender and **Confirm and link**; nothing is bound before that click. **Send me a code instead** is the fallback: the host enters a number, receives a six-digit code from the service and types it into a protected field. The connected card offers **Unlink** and the optional **Add to contacts**.
- **Channel and commands (Lane C).** A linked host's messages reach the same discussions as `/app`: setup by default, or the private discussion of a request the host selected with `request <reference>`. Exact commands (`help`, `requests`, `request <reference>`, `setup`, `review`, `changes`, `share`, `dismiss`, `approve`, `decline` and `confirm` with their references) are parsed and executed as application commands before any model turn. When a forwarded message's turn ends, the assistant's final text is sent back in the same conversation. Unlinked senders and group conversations get no session and no private data.
- **Summaries and outcomes.** A linked host receives, in the linked conversation, a summary when a request arrives, when a proposal awaits approval (with the exact approve and decline commands) and when a booking is confirmed or could not be made. A failed or uncertain delivery is shown in `/app`, where the host can always continue.
- **Setup over iMessage.** `setup` enters the shared setup discussion; answers in plain text update the same draft as `/app`; `review` sends the authored settings review with its reference, and only `confirm <reference>` on the current review saves the settings.

## Decisions

The plan assigns four decisions to Phase 6: the adapter and sender identifier format, line provisioning and the daily new-conversation allowance, code expiry and resend limits, and the `sms:` deep-link body format. The user decided the product scope and the one-tap deep link on 2026-10-23 (D3, D4). Designing the rest raised D5–D14. The implementing session took them on 2026-10-23 under the user's instruction to log every decision and keep it changeable; they are listed in the [decision log](../../../documentations/technical_specification/08_decision_log.md#phase-6--host-imessage-channel). None has had teammate review yet; the plan's **Teammate review** box covers them. The [design](design.md) records the reasoning and the rejected options.

| # | Decision | Choice |
|---|---|---|
| D1 | Adapter ([design 1](design.md#1-the-transport-spike-and-the-adapter)) | An application-owned adapter: a custom eve channel that only hosts the signed receiver, a durable receipt and job before the `200`, the application's own selection and session index, and one isolated outbound transport (Spectrum SDK `@spectrum-ts/core` and `@spectrum-ts/imessage` 12.14.0). Rejected: eve's native `photonIMessageChannel`, which acknowledges a webhook after an in-process dispatch with no durable record, keeps one eve session per iMessage thread outside the session index, cannot hold a message back under admission limits without dropping it, and sends replies with no outbox or uncertainty record |
| D2 | Sender identifier format ([design 1](design.md#1-the-transport-spike-and-the-adapter)) | Photon's `message.sender.id`: an E.164 number such as `+15551234567`, or the Apple ID email a host sends from. It is normalized (an email lower-cased), stored as a keyed hash for lookup and sealed for replies and the masked display, and compared exactly; a number is never parsed from message text or the space ID. Only `space.type = "dm"` counts. The format is taken from Photon's webhook documentation and the SDK; a real device has not shown it yet |
| D3 | Linking scope (user, 2026-10-23) | The PRD's design: the host sends a one-time link code from their own iMessage, so Thyme's first message is a reply (no junk banner, no new-conversation allowance spent); binding happens only after **Confirm and link** on the masked sender in the authenticated browser; **Send me a code instead** is the fallback. Google stays the only way to create or enter a host account. Teammate draft PR #23's outbound-first design is not adopted ([design 4](design.md#4-linking-by-a-host-sent-code)) |
| D4 | One-tap deep link (user, 2026-10-23; [design 5](design.md#5-the-one-tap-deep-link)) | Tapping **Connect iMessage** creates the code and then opens Messages at once: `sms:<number>&body=<text>` on iOS and iPadOS, `sms:<number>?body=<text>` on Android, with the text percent-encoded. Desktops and other browsers get the inline card with the number, the code, **Copy** and a QR code of the iOS deep link. Opening Messages never counts as linking |
| D5 | Link code ([design 4](design.md#4-linking-by-a-host-sent-code)) | `FMAT-` and ten Crockford base32 characters, the family email linking already uses, so existing redaction removes it everywhere. The message is `Link my Find Me a Time account: FMAT-…`. Valid 15 minutes, hashed and sealed, at most 5 per host per hour; a new code replaces a pending one; the host has 15 minutes after the message arrives to confirm |
| D6 | Fallback code limits and the new-conversation allowance ([design 6](design.md#6-the-fallback-code)) | Six digits, valid 10 minutes, hashed; 3 sends per attempt at least 60 seconds apart; 5 sends per host per rolling 24 hours; 5 wrong entries void the code; at most 20 fallback sends per line per rolling 24 hours (`PHOTON_FALLBACK_DAILY_LIMIT`), since Photon caps new conversations per line per day without a published number. Fallback use is counted |
| D7 | Line provisioning ([design 2](design.md#2-receiver-and-receipts)) | One Photon project with one line, its number in `PHOTON_LINE_NUMBER`, and one webhook whose ID (`PHOTON_WEBHOOK_ID`) and signing secret (`PHOTON_WEBHOOK_SECRET`) the receiver checks. Provisioning the line and registering the webhook are operator steps, blocked on the user |
| D8 | Exact commands and references ([design 8](design.md#8-exact-commands)) | Commands match the whole message, case-insensitively, after trimming. A request reference is six Crockford characters derived from the request ID; a review reference is `<request>-<version>`; a suggestion reference is `<request>-S<n>`; a settings reference is the first eight characters of the setup proposal hash. Approval, decline, sharing and settings confirmation run through the command pipeline as the linked host, keyed by the receipt, so a replayed message never repeats a decision. Free text, including "yes", never approves |
| D9 | Outbound delivery ([design 3](design.md#3-the-transport-and-the-outbox)) | One `imessage_outbox` row per message, text sealed and frozen before dispatch, sent by an `imessage_send` job. A send that began and lost its answer is recorded `uncertain` and never repeated, because Photon offers no idempotency key we can check; a refusal before sending retries up to five times. Host-private messages are suppressed if the binding ended before dispatch |
| D10 | Unlinked senders ([design 7](design.md#7-what-an-inbound-message-may-do)) | A direct message without a valid link code from a sender with no binding gets one fixed reply pointing to `/app`, at most once per sender per 24 hours; group conversations, outbound echoes and reactions get nothing |
| D11 | iMessage in the shared transcript ([design 9](design.md#9-forwarding-and-replies)) | A forwarded message is stored as `[iMessage] …`, so the web transcript and the assistant both know where it came from; the host instructions say that iMessage shows no cards, so the assistant asks in text and names the command to send |
| D12 | Host summaries ([design 10](design.md#10-summaries-and-outcomes)) | New request, proposal awaiting approval, booking confirmed, booking not confirmed and booking still pending, each recorded in the domain transaction as one job per event and frozen from that event's records; the awaiting-approval summary ends with the exact `approve` and `decline` commands for its reference |
| D13 | Add to contacts ([design 11](design.md#11-add-to-contacts)) | An optional action on the connected card that queues one native contact-card share in the linked conversation; the card shows queued, accepted, failed or uncertain and never claims the card was saved |
| D14 | Retention ([design 13](design.md#13-retention)) | A receipt's sealed text is cleared when it is processed and the receipt deleted after 30 days; outbox text is cleared when a message reaches a final state; link attempts are deleted 30 days after they end; a binding is kept until unlinked and deleted 30 days later |
| D15 | iMessage start before sign-in (user, 2026-10-23; [design 14](design.md#14-the-link-screens-the-app-link-step-and-the-imessage-start-d15d18)) | `/?flow=imessage` offers **Onboard with iMessage**: a code attempt with no host, owned by the browser through an HttpOnly cookie whose secret is stored as a keyed hash, bounded at 5 starts per source address and 100 across the service per hour; Google sign-in in that browser gives the attempt to the host, and **Confirm and link** in `/app` binds it |
| D16 | The /app link step, and no service-sent first message (user, 2026-10-23; [design 14](design.md#14-the-link-screens-the-app-link-step-and-the-imessage-start-d15d18)) | Right after sign-in, before the conversation, a host who has not linked sends Thyme the message from one full screen made from draft PR #23's phone check; **Set up here in web chat** skips it and is remembered. **Send me a code instead** is not offered, since Photon's shared lines refuse a first message to a number that has not written (2026-10-20 spike) |
| D17 | A Mac ([design 14](design.md#14-the-link-screens-the-app-link-step-and-the-imessage-start-d15d18)) | A Macintosh user agent without touch points gets **Open Messages on this Mac** (the iOS deep-link form) beside the QR code and **Copy**; the line and the body filled in on the user's Mac on 2026-10-23 |
| D18 | The ink screens (user, 2026-10-23; [design 14](design.md#14-the-link-screens-the-app-link-step-and-the-imessage-start-d15d18)) | The landing and the link step use the landing redesign's ink design in English and Korean (a `lang` cookie); the Calendar box, unchecked, signs in with identity only (`?calendar=0`); the rest of the app keeps DESIGN.md's Thyme theme |
| D19 | Carrying on in iMessage (user, 2026-10-23; [design 17](design.md#17-carrying-on-in-imessage-the-sign-in-link-the-welcome-and-the-calendar-link-d19)) | Thyme's reply to a code from the iMessage start carries a sign-in link (the attempt ID and an HMAC over it and the sender's hash) that works in any browser while the attempt awaits **Confirm and link**; Google sign-in from it gives the attempt to that host, and confirmation still happens on the masked sender. Confirm and link sends a welcome by where the host stands: PR35's line when ready, else the Calendar link (`/auth/sign-in?consent=calendar&return=imessage`) or the first setup question, and a plain reply continues setup. Signing in from the Calendar link brings one "back from Google" message to the linked conversation. Messaging stays production-only |

## Conflicts resolved here

| Conflict | Resolution |
|---|---|
| **Open Messages as a second step.** The PRD's linking paragraph, the page list's *Channel link*, the interfaces, the host onboarding flow (H11), the frontend architecture and the provider setup describe **Connect iMessage** expanding a card on which the host then taps **Open Messages** | D4 (the user, 2026-10-23): **Connect iMessage** opens Messages itself; the card is the fallback where Messages cannot open, with a QR code added. The owning documents are updated |
| **Adapter left open.** The PRD, the agent configuration and the provider setup leave native channel versus application-owned adapter to a spike | D1, with the spike's evidence in design 1; the agent configuration's channel row and open decision are updated |
| **Teammate draft PR #23.** It proposes that the host enters a number, Thyme texts it first, and a two-digit reply links the number | D3: not adopted, because its first message is unsolicited (junk banner, the line's new-conversation allowance), which the PRD's inbound-first choice exists to avoid. Its signature check, durable inbound events and send limits are reused (design 2, design 6). Its screens are kept (D16): the user decided on 2026-10-23 that the link step after sign-in and the landing follow them, on this change's host-sent code |
| **Settings confirmation in iMessage.** The host onboarding flow says the iMessage settings confirmation "needs its own reviewed change before implementation" | This is that change: `confirm <reference>` on the current review (design 12) |

## Capabilities

### New Capabilities

- `host-imessage-channel`: the signed receiver and receipts, linking by a host-sent code with browser confirmation and the one-tap deep link, the fallback code, unlinking, what an inbound message may do, exact commands, forwarding into the shared discussions and replies, summaries and outcomes, setup over iMessage, the outbox and its failure display, **Add to contacts**, and retention.

### Modified Capabilities

None. This change closes scenarios that the main specs already state, without changing their text:

| Specification | Closed in this change | Deferred, and where |
|---|---|---|
| [`chat-workspaces`](../../specs/chat-workspaces/spec.md) | "Messaging backpressure" and "Authority expires during delay" for iMessage; the iMessage half of "Mixed scheduling and credential text" | None |
| [`messaging-environments`](../../specs/messaging-environments/spec.md) | "Preview with copied provider credentials", "Preview wakeup against a configured database" and "Direct provider adapter invocation" for iMessage | None |
| [`durable-jobs`](../../specs/durable-jobs/spec.md) | Receipt and send jobs under the existing fencing | None |

## Archive order

This change only adds a capability and depends on Phases 2 and 4. It can archive after `host-onboarding` and `host-review-and-booking`; archiving those first keeps the main specs' history in delivery order.

## Impact

- **New code:** `agent/channels/photon.ts`; `lib/server/{photon,photon-receiver,imessage-links,imessage-receipts,imessage-commands,imessage-outbox,imessage-notices}.ts`; `lib/contracts/imessage.ts`; `/api/host/imessage` routes; the linking and connected cards in `/app`.
- **Changed code:** `vercel.ts` routes `/photon/*` to the agent service; the session-owner hook wakes waiting iMessage replies; the job registry gains `imessage_receipt` and `imessage_send`; the request start, agreement and booking settlement enqueue host summaries; the host instructions gain an iMessage fragment.
- **Schema:** `imessage_receipts`, `imessage_links`, `imessage_bindings` and `imessage_outbox`, with row-level security and no client grants, and a cleanup function on the existing schedule pattern, generated through pg-delta.
- **Dependencies:** `@spectrum-ts/core` and `@spectrum-ts/imessage` 12.14.0 (MIT), loaded only by the production transport; `uqr` for the QR code.
- **Systems:** Photon Spectrum. Provisioning a line, registering the webhook, texting any real number, the shared-project migration and the production deploy are left to the user (decision log, "Blocked on the user").
- **Documents:** the plan's Phase 6 boxes, the [PRD](../../../documentations/02_product_requirements.md) linking paragraph, the [page list](../../../documentations/user_experience/04_page_list.md), the [interfaces](../../../documentations/user_experience/03_interfaces.md), the [host onboarding flow](../../../documentations/user_experience/05_host_onboarding_flow.md), the [frontend architecture](../../../documentations/technical_specification/02_frontend_architecture.md), the [provider setup](../../../documentations/technical_specification/03_provider_setup.md#photon), the [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md), the [backend architecture](../../../documentations/technical_specification/01_backend_architecture.md), the decision log and the acceptance record, with their Korean mirrors; `.env.example`.
