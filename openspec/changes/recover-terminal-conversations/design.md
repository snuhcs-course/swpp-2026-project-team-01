# Design

## Context

See [proposal.md](proposal.md). The current channel accepts an input before resolving the stored runtime identity. A failed canonical workflow therefore leaves later input pending and returns reconciliation-pending. Eve 0.71.3's documented `Session` handle cannot resume terminal sessions; reset/create produces a different ID. Its channel address resolver alone cannot distinguish a terminal session from unavailable state. The retained event stream provides terminal events and usage; the new code must verify that evidence before transitioning.

Supabase currently stores one `runtime_session_id` per logical `conversation_scopes` row. Inputs retain grant/client identity, and tool retry keys derive from logical scope, message and operation. Model reservations and settlement check the runtime ID, but `ConversationTools` currently validates the call ID/session shape without passing session identity to the SQL tool boundary. Recovery must close that gap before allowing a successor.

## Goals / Non-Goals

**Goals:** recover already failed canonical sessions and prevent avoidable future configuration failures from permanently ending a conversation; retain logical scope, authorized history, accepted work and accounting across a fenced transition.

**Non-Goals:** repair unknown or still-running workflows by force, reset quotas, reconstruct private credentials from history, introduce a second agent engine, or reinterpret chat as human scheduling approval.

## Decisions

1. **Application-owned runtime generations.** Add a private ledger of runtime generations, terminal evidence, finalized stream tails, accumulated reported usage and idempotent recovery transitions. Preserve the logical conversation ID and current grants. Backfill existing bindings as generation zero; do not rewrite accepted inputs or historical migrations. Clearing the canonical pointer alone was rejected because it loses history and execution ownership.
2. **Explicit authorized recovery.** A same-origin browser action submits only logical conversation, observed generation and retry UUID. Runtime/session IDs and terminal claims come from the server. Inspect the exact saved runtime's bounded terminal stream and current channel ownership; unavailable evidence fails closed. Persist evidence and advance once under scope/recovery locks, rechecking the same generation and current grant after waits. A recovered generation may await its first normal delivery; recovery without pending input must not manufacture a model message.
3. **Fence every execution boundary before activation.** Propagate server-owned session/generation identity through tool RPCs, including readiness reads before and after provider I/O. Require a matching bound successor for recovered scopes; reject legacy calls lacking execution identity on those scopes. Preserve generation-zero compatibility during additive rollout. Model reservations, inbox delivery, dispatch and settlement use the same generation check. Current grants remain separate from runtime ownership.
4. **Continue the original inbox.** A pending message retains its ID, grant, client retry fingerprint, ordering, mutation keys and reservations. Recovery cannot reuse an expired participant grant or reset attempts. Completed/failed inputs retain their receipts and are not automatically replayed. A lease and compare-and-set binding handle concurrent first delivery and lost dispatch responses. Unknown successor creation remains pending recovery, not permission to create another successor.
5. **Preserve history through generation-aware projection.** Retain each retired runtime's immutable stream tail and map it into one logical cursor space. Browser replay and encrypted agent-history cursors resolve through the authorized generation ledger; support previously issued cursors. Recheck authority across every read and preserve stable projected event identity for deduplication. Keep generation-zero turn IDs unchanged and prefix successor turn IDs with their generation, because eve restarts its session-local turn numbering; retain original event IDs. Use a bounded, server-authored, audience-safe continuity context for the successor, with paged historical reads for omitted older context; never silently drop the archive or treat old assistant text as a command. Eve's supported delivery `context` field can carry the bounded context without fabricating a user input.
6. **Keep provider configuration failures at the turn boundary.** Normalize known model authentication/configuration failures into safe application failures before eve classifies them as terminal, while retaining reservations and bounded transient retries. Do not attach raw provider errors as causes that restore terminal classification or leak bodies. This prevention does not replace recovery for existing failed workflows. Carry reported session usage across generations and enforce remaining session limits as well as unchanged durable allowances; inability to establish required usage/evidence cannot authorize a reset.
7. **Truthful UI and operations.** Distinguish terminal recovery from network reconnect. Keep current discussion and history visible, allow the explicit recover action, and read authoritative status after uncertainty. No model, agent-client tool or messaging prose can trigger a session replacement. Structured controls remain available during failure. Successful credential provisioning alone is not recovery evidence.

## Risks / Trade-offs

- A terminal event is mistaken for missing state → require a trusted bounded terminal read for the exact stored generation and a current-ownership check; test stale, active and unavailable negatives.
- Old deployment calls bypass new ownership checks → reject identity-free runtime tool calls on recovered scopes before enabling the browser action; test actual obsolete-call shapes.
- Recovery races a tool, revocation or dispatcher → use consistent transaction lock order, generation comparisons and current-authority checks after waits; test both orderings and uncertain acknowledgments.
- History or context crosses an audience → scope all generation lookup and projection to the current logical conversation; use safe text/lifecycle projections and existing byte limits, not raw framework history.
- New generations reset token limits → retain terminal usage and durable work accounting; verify limit exhaustion across recovery and refuse unsupported evidence rather than inventing usage.

## Migration Plan

Generate an additive pg-delta migration for the private generation/recovery ledger and fenced RPCs; review grants and rebuild the disposable local database. Deploy backward-compatible readers and generation-zero handling first, then activate recovery only after every execution path is fenced. Never deploy the diagnostic fixture to the public alias. Verify a controlled managed diagnostic with an already terminated session, preserved prior history, pending input, concurrent recovery and revocation, then cancel/remove only its exact synthetic records and preview. Deploy the production implementation through the existing verified archive workflow and inspect release health/guards. Roll back activation without deleting generation history; a pre-recovery application that cannot read recovered scopes must fail closed rather than resetting them.

## Continuity context implementation bounds

The private builder reads one recent 100-event retired-history window, with a five-second total I/O deadline and at most 64 KiB of projected source events. It emits at most 16 KiB of UTF-8 JSON containing authored historical-data guidance, logical archive/excerpt ranges, omission markers and whole user/completed-assistant messages. Older and excluded messages remain in authorized archive pages; source-byte limits expose an exact next cursor. The builder never reads the successor or promotes archived tool/delta/error metadata into context. Current participant and execution-generation checks must wrap both initial and paged reads. The supported eve delivery context is now installed once with the first successor input. Model-accessible historical paging remains part of task 2.1.

## Successor creation protocol

Eve's public channel API creates a session only through a cold-start send, so the database cannot learn its runtime ID before that send. A private `conversation_successors` row reserves the original pending input and one creation key for the recovered generation. `claim` returns a 90-second lease; an expired lease can rotate only before creation starts. Atomic `start` returns permission to send exactly once. Repeated calls, including retries after a lost start acknowledgment, return no permission. Once started, lease expiry leaves creation uncertain and never allocates a second key or authorizes another cold-start send.

The delivery hook supplies the captured runtime ID and server-owned creation key to `bind`. This operation rechecks the original input grant and current generation after all locks, then atomically records the same runtime in the scope and generation ledger plus one redacted audit entry. A late original delivery may bind after its dispatch lease expires because that expiry never issued a replacement creation permit. Exact binding retries retain the same runtime; another runtime, retired generation or expired/revoked original participant cannot bind. Binding does not accept a new message, alter original input/grant fields or refund model charges. The primitive remains private even to the service role; the authenticated adapter uses the service-only runtime wrapper. The shared sender uses fixed handles after binding and retries one unavailable binding acknowledgment with the same identity. If original authority expires before creation starts and dispatch settles that input, a separately authorized new input may replace the unstarted preparation with a new key/lease. This neither revives the original input nor refunds charges. Started or uncertain creation cannot be reassigned; later input remains pending reconciliation.
