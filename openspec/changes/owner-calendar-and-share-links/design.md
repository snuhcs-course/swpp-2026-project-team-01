# Design

> 후속 변경: `selected-slots-and-meeting-approval`에서 호스트의 공개 범위·길이·후보 선택과 Google 일정 수락/초대를 추가했다. 이 문서의 수락 제외·읽기 전용·자동 구간 생성 설명은 당시 기준이며 현재 동작은 후속 변경을 따른다.

## Context

기존 앱은 Google Calendar 읽기 전용 연결과 규칙 기반 후보 추천을 지원한다. 소유자 화면은 링크 생성 버튼과 받은 요청 목록만 제공한다. 이번 변경은 사용자의 항목 1–3을 구현하며, 항목 4의 받은 요청 검토/수락 동작은 유지한다.

## Goals / Non-Goals

- 목표: 실제 주간 캘린더, 규칙 기반 빈 시간 표시, 조건 확인, 이름 있는 링크와 상세/상태 관리.
- 제외: LLM 연결, 개인 선호 편집, 빈 시간 블록 편집, 캘린더 쓰기, 받은 요청 승인, 외부 배포.

## Decisions

### 캘린더와 빈 시간

소유자 전용 GET /api/calendar/events가 기본(primary) 캘린더의 이번 주 월요일부터 3주를 조회한다. 일정 제목·시간·장소·종일 여부는 소유자 화면에만 응답하며 저장하지 않는다. 요청자 조회에는 제목과 참석자를 포함하지 않는다. 모든 날짜 계산은 Asia/Seoul 기준이다. 종일 일정은 상단, 시간 지정 일정은 24시간 그리드에 표시하고 겹친 일정은 나란히 배치한다.

빈 시간은 내일부터 14일의 월–금 09:00–20:00에서 바쁜 일정 전후 15분을 제외한 30분 이상 구간이다. Google에서 한가함으로 설정한 일정은 표시하되 충돌로 취급하지 않는다. 공휴일은 별도로 제외하지 않는다. 화면에는 AI 모델이 아직 연결되지 않았음을 밝힌다. 요청의 장소가 정해지면 기존 0/15/45분 이동 여유 규칙과 상대방 캘린더를 다시 적용한다.

### 링크의 공개 시간과 수명

POST /api/share는 이름(1–80자)을 검증하고 최신 소유자 캘린더로 공개 구간을 계산해 저장한다. 새 링크는 생성 당시 공개 기간/구간을 유지하며 날짜가 자동 연장되지 않는다. 실제 후보는 저장된 구간 전체에 들어가야 하며 양쪽 최신 캘린더 검사를 통과해야 한다. 기간이 지나면 새 링크를 만든다.

기존 링크에는 기간/구간을 강제로 채우지 않는다. 기존처럼 요청 시점부터 향후 14일 규칙을 사용하며 상세에는 현재 빈 시간과 이 차이를 안내한다. 기존 링크 이름은 ‘미팅 요청’이다.

### 링크 주소와 접근 제어

code_hash는 기존처럼 조회용으로 유지한다. 새 링크는 encrypted_code를 추가 저장해 소유자가 주소를 다시 복사할 수 있다. 암호문은 서버에서만 복호화한다. 이전 링크의 해시에서는 주소를 복원할 수 없으므로 복사 불가 안내를 표시한다.

GET /api/share와 PATCH/DELETE /api/share/[id]는 서명된 소유자 세션과 owner_google_sub 일치 여부를 확인한다. 토큰·암호문·코드 해시는 응답에 포함하지 않는다. RLS와 기존 service_role 전용 접근을 유지한다.

### 닫기와 삭제

닫기는 active=false, 다시 열기는 active=true로 변경한다. 삭제는 deleted_at과 active=false를 저장하며 링크 목록에서 숨긴다. 기존 요청은 GET /api/requests에 남는다. 공개 페이지, 요청자 OAuth 콜백, 요청 제출에서 상태·삭제·만료를 확인한다. DB BEFORE INSERT 트리거는 해당 링크에 FOR SHARE 잠금을 잡고 상태를 확인하여 닫기/삭제 중 이미 진행된 요청도 직렬화한다.

## Risks / Trade-offs

- 새 Google 일정은 새로고침 전까지 화면에 반영되지 않는다. 요청 시에는 최신 일정을 재조회한다.
- 공개 구간은 미팅 장소 미정의 15분 여유를 기준으로 한 잠정 구간이며 실제 후보를 보장하지 않는다.
- 기본 캘린더만 표시한다. 추가 캘린더·휴일 캘린더 자동 통합은 포함하지 않는다.
- 창을 오래 열어두면 자정 이후 날짜 범위를 새로고침해야 한다.
- 소프트 삭제는 받은 요청을 보존하기 위한 선택이다. 계정/개인정보 삭제 기능과 다르다.

## Migration Plan

선언형 스키마에 추가 열·제약·트리거를 작성하고 pg-delta로 새 마이그레이션을 생성한다. 기존 열과 기록을 제거하지 않는다. 로컬 재생성 확인 후 연결된 기존 Supabase 프로젝트에 dry-run을 거쳐 적용한다. 받은 요청의 화면 구성과 승인 기능은 변경하지 않는다.
