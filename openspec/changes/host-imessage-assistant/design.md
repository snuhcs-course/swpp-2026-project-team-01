# Design

## Context

See [proposal.md](proposal.md) for motivation and the [host onboarding delta](specs/host-imessage-onboarding/spec.md) for behavior. The app is a Next.js server backed by Postgres/Supabase. Real accounts use a session cookie (`src/server/session.ts`); demo mode can select seeded users and therefore cannot authorize a real phone send. The standalone Spectrum echo script has been removed; the web app still has no phone field, messaging tables, or inbound route. Booking mutations already go through owner-scoped commands with revision and calendar checks; this change does not call them.

Photon's [Spectrum iMessage guide](https://photon.codes/docs/spectrum-ts/providers/imessage/connection-and-routing) documents `imessage(app).user(number)`, `space.create(user)`, and `space.send(text)` for starting a direct conversation. Its [webhook guide](https://photon.codes/docs/webhooks/overview) documents signed JSON delivery to a public HTTPS URL. The [SDK webhook handler](https://photon.codes/docs/spectrum-ts/webhooks) invokes its callback after acknowledging the HTTP request; that behavior does not meet this change's durable-before-ack requirement, so the API route will verify and persist the raw request synchronously before acknowledging.

## Goals / Non-Goals

**Goals:** Give the future **Text me** UI a stable command/status contract, one safe Photon welcome send, and a durable path to identify a host's reply. Make that complete path runnable and verifiable with a real authenticated host and test iPhone before the new UI exists. Keep Photon transport behind a provider interface so host onboarding and later scheduling services do not depend on Spectrum types.

**Non-Goals:** Build the onboarding screen, create guest messaging, generate booking summaries, interpret free-form host commands, or mutate requests from texts. The product's existing [onboarding PRD](../../../documentaions/availability_onboarding/product_requirement_document.md) excludes host request-handling AI; later messaging policy needs its own change.

## Decisions

### 1. Use a database outbox and a separate outbound worker

`POST /api/host/imessage/connection` (name proposed for the future UI contract) requires `APP_MODE=real` and `requireActor(request)`. It normalizes an E.164 phone number, claims a pending connection and creates one welcome outbox job in the same transaction, then returns a status; it never waits for Photon. `GET` returns only the caller's masked number and status. `POST /api/host/imessage/connection/retry` requests one eligible resend. Repeated submit/retry calls use the connection and a client operation key to avoid duplicate jobs.

A separate Node.js worker polls the outbox, constructs the managed Spectrum iMessage provider using `SPECTRUM_PROJECT_ID` and `SPECTRUM_PROJECT_SECRET`, creates/gets a DM for the destination, persists its conversation ID and line identity, and then calls `space.send`. Persisting the routing identity before the send lets a fast reply be matched even if the send acknowledgement is uncertain. The provider adapter returns application-level send results and normalized inbound identifiers; booking code never imports Photon. The worker runs outside a Next.js request so a long-lived gRPC connection can be managed independently. Direct send from the `Text me` route was rejected because a timeout or process restart would make duplicate clicks and uncertain delivery hard to reconcile. Photon documents [outbound DM creation and line routing](https://photon.codes/docs/spectrum-ts/providers/imessage/connection-and-routing).

The installed Spectrum user resolver may not expose a recipient's messaging service before the first send. Therefore the worker starts with the channel confirmation gate off and refuses to send until an operator confirms with Photon that the project and authorized test recipient cannot fall back to SMS/RCS. `SPECTRUM_IMESSAGE_CHANNEL_CONFIRMED=true` records that operator decision; it is not a provider-side guarantee or recipient lookup.

### 2. Keep phone ownership pending until a matching reply

Store `host_phone_connections` with `host_id`, normalized `phone_e164`, state (`pending`, `sent`, `failed`, `uncertain`, `connected`, `expired`), `space_id`, `line_id`, timestamps, and revision. Add unique constraints for one active connection per host and one active claimant per number; enforce them transactionally. A host with a different already-connected number must use a future replace/disconnect flow, not silently transfer the identity. Recommended English welcome copy: `Welcome to Find Me a Time! Please reply to this message so that I know I've reached you.` This is draft UX copy; the spec requires its meaning rather than this exact wording. The `Text me` API reports queue acceptance separately from Photon acceptance and phone connection.

The worker stores the DM's opaque space ID and line before the send. A signed inbound text connects the host only when `message.sender.id` matches the unverified number, `space.id` and `space.phone` match that DM, `space.type` is `dm`, and the claim is unexpired. This includes a send whose acknowledgement is uncertain but whose reply proves the recipient received it. Require a non-empty reply; no keyword is needed. This follows the prototype's reply-to-finish interaction without claiming that delivery alone proves phone control. Compare against the provider sender field, never parse a number out of message text or a chat GUID. If Photon changes a conversation ID, fail closed and require a new onboarding attempt. Phone number is an account identifier, not booking authorization by itself.

### 3. Use a signed webhook inbox for inbound receipt and dedupe

`POST /api/photon/webhook` runs in the Node runtime and reads the original body bytes. Verify `X-Spectrum-Signature` against the per-webhook secret over `v0:<timestamp>:<rawBody>`, reject timestamps outside five minutes, and compare signatures in constant time. These are Photon's documented [verification rules](https://photon.codes/docs/webhooks/verifying-signatures). Check the registered `X-Spectrum-Webhook-Id`, event shape, platform, direction, and required IDs; tolerate unknown additive fields/event types. Persist a minimal `photon_inbound_events` record with a unique `(webhook_id, message_id)` key, normalized routing data, content type, processing state, and bounded text needed for later routing before returning 2xx. Duplicate valid deliveries return 2xx without a second side effect. Database failure returns 5xx so Photon can retry. Never log bodies, phone numbers, secrets, or raw webhook payloads.

A short inbox processor claims unprocessed events transactionally, matches the connection, and updates it once. Webhook persistence and later processing are separated so an application crash after acknowledgement still leaves work to resume. Add a separate `host_imessage_messages` table keyed by host and conversation, with direction, stable message ID, text, and timestamp. Copy matched inbound text into it exactly once and clear the text from the inbox after processing; discard unmatched bodies. Store accepted outbound welcome text there using its outbox job ID and provider message ID when available. Only matched host text can change phone connection state; no inbound event invokes a booking service. Photon's [event schema](https://photon.codes/docs/webhooks/events) defines the sender, DM space/line, direction, and stable message ID; [delivery guidance](https://photon.codes/docs/webhooks/delivery) is at-least-once with finite retries. Calling `app.webhook()` directly was rejected here because its callback is fire-and-forget after the response and would not guarantee durable receipt.

### 4. Make retries bounded and remove the old echo worker

Track each outbound attempt in `photon_outbound_attempts` with connection ID, purpose, state, provider message ID when known, and failure category. Allow at most three definitive failed attempts per connection, with cooldown/backoff. A transport timeout after a send begins has an `uncertain` outcome; do not automatically resend or let the host retry until an operator reconciles it, because Photon may have delivered the welcome. The status API exposes a safe reason and retry eligibility. Remove the old echo script and command; the new outbound worker and webhook are the only planned Photon runtime paths for host onboarding.

### 5. Verify the full flow without the onboarding UI

Provide the repeatable real-mode setup and operator flow directly in the response to the user requesting this change, rather than in a Markdown file. It must cover the database migration; the existing real host sign-in and authenticated session; server-only Spectrum project credentials, webhook ID and signing secret; starting the outbound worker; publishing `POST /api/photon/webhook` at a public HTTPS URL and registering that URL in the Photon project; and an authorized test recipient. Do not add a test-only authentication bypass or ask operators to paste credentials into tracked files.

The response must show how to submit the host's E.164 phone number to `POST /api/host/imessage/connection` with that session, poll `GET /api/host/imessage/connection`, and inspect the phone and server states separately: queued/pending, Photon-accepted/sent, and reply-confirmed/connected. The operator then checks that exactly one welcome arrives on their iPhone, replies in the same DM, and observes `connected` plus one stored inbound message. Include failure checks for a rejected send, unreachable or invalid webhook, and repeated API or webhook delivery. Distinguish a message received by the phone from the server's recorded send status; either alone does not prove the reply path works. If Photon cannot guarantee iMessage instead of SMS/RCS for the test recipient, stop at the channel rollout gate rather than claiming an iMessage end-to-end pass.

## Risks / Trade-offs

- **Photon delivery/line constraints** → Start with an authorized test recipient and inspect line, quota, and provider response; persist the line for later matching. Shared-line and multi-line behavior are described in [Photon routing](https://photon.codes/docs/spectrum-ts/providers/imessage/connection-and-routing).
- **Webhook acknowledgement before side effects** → Commit inbox receipt first, then process from the durable inbox; monitor pending/failed records. Photon has finite delivery retries, so endpoint and DB availability matter.
- **Timeout after a possible send** → Mark `uncertain` and require reconciliation before resend; the UI must not report success as a verified connection.
- **Recipient service ambiguity** → Use the iMessage provider only; do not add SMS/RCS fallback code. If Photon identifies the destination as a non-iMessage service, fail the send. If Photon cannot guarantee channel selection before send, treat that as a rollout gate and resolve the policy before production activation.
- **Phone number privacy and reuse** → Restrict queries to the session owner, mask the number in status responses, retain only the minimum inbound data, and require an explicit future replacement/disconnection flow. Current scope cannot solve recycled numbers or long-term re-verification.

## Migration Plan

1. Add the new tables, uniqueness rules, and RLS/no-Data-API-grants following `supabase/schemas/scheduler.sql` and a migration; update typed schema only where this app uses Drizzle rather than raw SQL.
2. Add server-only Photon and webhook settings, deploy the signed HTTPS endpoint, register its URL in Photon, and keep the host `Text me` command disabled until the webhook is reachable. The webhook secret is separate from the project secret and must not be committed.
3. Deploy the outbound worker and API contract; run the documented UI-free end-to-end check with an authorized real host and test iPhone, inspect sent/connected/failed states and duplicate-delivery behavior, then connect the UI when it is merged.
4. Remove the legacy echo script, command, and run instructions. For rollback, stop new outbox sends and disable the host command; retain inbox/outbox rows for reconciliation, remove the Photon webhook registration if no longer used, and leave guest/booking routes untouched.
