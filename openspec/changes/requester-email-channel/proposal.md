# Proposal

## Why

Phases 3 and 4 give a requester a complete web journey: one guest thread from the host's public page to the booking link, agreement, the host's approval and a confirmed event. The [implementation plan](../../../documentations/technical_specification/06_implementation_plan.md#phase-7--requester-email-channel) makes Phase 7 the email path: a requester can start a request by writing an email, continue it in the same email thread, move to the booking link for the browser steps, and receive the status notices in that thread.

The main specifications already fix the ingress boundary. [Requester email ingress](../../specs/requester-email-ingress/spec.md) requires a fenced, signed receiver that stores a deduplicated receipt and one job before acknowledging, and that grants nothing. [Email delivery](../../specs/email-delivery/spec.md) keeps AgentMail for conversational email with retained provider identity and bounded idempotent retry, and promises email-originated requesters their notices in their thread. [Messaging environments](../../specs/messaging-environments/spec.md) already denies conversational email outside production and local loopback. What no specification holds yet is what happens after the receipt: how a thread is bound to a request, what a sender must prove, how the booking page links a thread, how replies go back, and how long any of it is kept. The [interfaces](../../../documentations/user_experience/03_interfaces.md#protected-requester-email-linking) describe **Continue by email**, **Check email link** and **Unlink email** and say the address scheme, reply verification, linking and unlinking "still need design". This change designs them.

## What Changes

- **Signed receiver (Lane A).** `agent/channels/agentmail.ts` is a custom eve channel with one route, `POST /agentmail/webhooks/{receiverId}`, routed to the agent service in `vercel.ts`. It verifies the Svix signature of the raw body against the receiver's secret within a five-minute window, checks that the operator-registered receiver is enabled and matches the configured secret and inbox, and stores one receipt (minimized locators and the payload's SHA-256, no body, sender or header) and one `email_receipt` job in a single transaction before answering `204`. A retry of the same event reuses them; the same event, message or Svix identity with different evidence is refused with `409` and changes nothing. Other event types are acknowledged and dropped. The operator registers, replaces and disables receivers through the administrator CLI.
- **Thread binding and forwarding (Lane B).** The `email_receipt` job reads the message from AgentMail with the runtime key, requires authenticated sender evidence, and then either binds or forwards. A new thread whose subject names a ready host's handle starts a request; a new thread carrying a pending link code from the request's confirmed contact links that request; a message in a bound thread from its bound address becomes an accepted input of the request's existing requester discussion, so web and email share one guest thread and one session (Phase 3 D13). Everything else is dropped without a reply.
- **Replies in the same thread.** When the turn that served an email message ends, the assistant's final text is frozen and sent as a reply to that message through AgentMail with an `Idempotency-Key`, in the same thread. Link confirmations, start refusals and closed-request notices are fixed application texts.
- **Continue by email.** The booking page offers **Continue by email** below contact confirmation. With a confirmed contact it shows a one-time linking message to send, as shown, from that address in a new email to the product inbox; **Check email link** refreshes the status; **Unlink email** ends the binding at once, also during a receiver outage; an uncertain command offers **Retry same linking action** with the same retry key.
- **Thread notices.** A request with a bound thread receives the Phase 4 status notices (new version, decline, expiry, booking still pending) in that thread as well as by Cloudflare email.

## Decisions

The plan assigns four decisions to Phase 7: custom channel versus Chat SDK adapter, inbox allocation under the current account limit, forwarded-link handling and thread retention. Designing them raised D5–D11. The implementing session took them on 2026-10-22 under the user's instruction to log every decision and keep it changeable; they are listed in the [decision log](../../../documentations/technical_specification/08_decision_log.md#phase-7--requester-email-channel). None was reviewed by a teammate yet; the plan's **Teammate review** box covers them. The [design](design.md) records the reasoning and the rejected options.

| # | Decision | Choice |
|---|---|---|
| D1 | Custom channel versus Chat SDK adapter ([design 1](design.md#1-the-channel-and-the-receiver)) | A custom eve channel, `agent/channels/agentmail.ts`, that hosts only the signed receiver route. It never calls `from(thread).send()`: the application job forwards verified text as an accepted input of the request's existing requester discussion, so email and web share one session, admission, redaction, model limits and the session index. Rejected: the Chat SDK bridge, which has a Gmail adapter but no AgentMail adapter and would read a mailbox rather than our inbox; a channel-owned session per thread, which would give one request two sessions and bypass the application's index and admission |
| D2 | Inbox allocation under the three-inbox account limit ([design 2](design.md#2-one-shared-inbox)) | One product inbox, `findmeatime@agentmail.to`, for every host and request, named by `AGENTMAIL_INBOX_ID`. A new thread names its host by `@handle` in the subject; the public host page offers a prefilled `mailto:` link. Replies route by the thread binding. Rejected: an inbox per host (three at most, and creating one is an irreversible provider action per host); an inbox per request; plus-addressing, which AgentMail does not document |
| D3 | Forwarded-link handling ([design 5](design.md#5-what-a-message-must-prove)) | A link code binds only as the first message of a new thread, from the request's confirmed contact, with authenticated sender evidence, before it expires. The same code arriving any other way (another sender, an unauthenticated message, an existing thread, after expiry) voids it without binding or reply. In a bound thread only messages from the bound address are forwarded; a forwarded copy, a new recipient or a CC forwards nothing. Booking links and link codes are redacted before text reaches the model. Rejected: binding on the From address alone, which is a sender claim |
| D4 | Thread retention ([design 9](design.md#9-retention)) | Receipts keep locators and a payload hash only and are deleted 30 days after receipt. A binding stops forwarding when its request closes and is deleted 30 days after the request's creation, when the booking link's receipt window ends. Reply texts and sealed notice links are cleared when a reply reaches a final state. The provider's own copy of the thread stays in the AgentMail inbox; deleting provider threads is left to Phase 8's retention rules |
| D5 | Sender authentication ([design 5](design.md#5-what-a-message-must-prove)) | A message counts only when AgentMail delivered it as `message.received` without the `unauthenticated` or `spam` labels and its `authentication_results` show `dmarc: pass`, or `dkim: pass` with `dkim_domain` equal to the From domain. Rejected: trusting the From header; AgentMail's own `unauthenticated` label alone, which accepts unaligned SPF |
| D6 | Starting a request by email ([design 3](design.md#3-starting-by-email)) | An authenticated new thread naming a ready host creates the request already identified, with the sender's display name and address as an unconfirmed contact (as a typed address on the identity card is), the host's timezone and the message's language, and sends the Phase 3 creation email with the booking link and **Confirm this address**. Creation bounds (Phase 3 D7) count per keyed hash of the sender address. A thread naming no ready host gets one fixed reply and creates nothing. Rejected: a draft that waits for identity, which email cannot collect without the card |
| D7 | Linking from the booking page ([design 4](design.md#4-continue-by-email)) | Needs a confirmed contact. The code is `FMAT-` and ten Crockford base32 characters (50 bits), valid 30 minutes, stored as a hash and a sealed copy so a reload shows it again while pending; a new code replaces a pending one; binding replaces any earlier thread of the request. The linking message never reaches the model; the thread gets a fixed confirmation. At most 5 codes per request per hour |
| D8 | Replies ([design 6](design.md#6-replies)) | One plain-text reply per forwarded message after its turn ends, with the turn's final assistant text, frozen before dispatch and sent with `Idempotency-Key` equal to the reply ID. An uncertain dispatch is retried with the same key for up to 23 hours (AgentMail keeps keys 24 hours), then recorded uncertain and never sent again. A turn without final text sends a fixed fallback. A footer points to the booking link for choosing times and agreeing |
| D9 | Unlinking ([design 4](design.md#4-continue-by-email)) | **Unlink email** ends the binding in the database only, so it works while AgentMail or the receiver is down; later messages in that thread forward nothing and get no reply |
| D10 | Receiver registration ([design 1](design.md#1-the-channel-and-the-receiver)) | `npm run admin -- email-receiver register --inbox <id> --webhook <id>` records an enabled receiver with the fingerprint of `AGENTMAIL_WEBHOOK_SECRET` and disables the inbox's previous one; `email-receiver disable` turns it off. The webhook URL carries the receiver ID. Creating the webhook at AgentMail stays an operator step |
| D11 | Messages the channel does not forward ([design 5](design.md#5-what-a-message-must-prove)) | Over-long messages (the chat limit) get one fixed reply asking for a shorter message; a closed request's thread gets one fixed closed notice per binding; attachments are never fetched; messages from our own inbox are ignored. Admission limits leave the receipt's job pending and retried, so mail is delayed, not dropped |

## Conflicts resolved here

| Conflict | Resolution |
|---|---|
| **Whose inbox.** The [guest booking flow](../../../documentations/user_experience/06_guest_booking_flow.md#email-differences) says a requester "writes to the host's conversational inbox"; the account allows three inboxes and one is selected | D2: one product inbox, with the host named in the subject; the flow document is corrected |
| **Contact before the booking link.** The guest flow sends the booking link "after contact verification"; Phase 3 D3 sends it in the creation email whether or not the address is confirmed | D6 follows Phase 3 D3: the creation email goes to the sender's address with the booking link and the confirmation link; the thread never carries the booking link before the address is confirmed |
| **Interfaces still open.** The [interfaces](../../../documentations/user_experience/03_interfaces.md#integration-choices-and-scope) leave the address scheme, reply verification, thread linking and unlinking undecided | D2, D3, D5, D7 and D9; the document is updated |
| **Agent configuration.** The [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md#channels) lists the AgentMail channel as resolving the thread and forwarding the text itself, and leaves the custom-channel question open | D1: the channel is the receiver, and forwarding runs in the application job; the table and the open decision are updated |

## Capabilities

### New Capabilities

- `requester-email-threads`: binding an AgentMail thread to a request (started by email or linked from the booking page), sender authentication, forwarding into the request's discussion, replies in the same thread, unlinking, the messages that are not forwarded, and retention.

### Modified Capabilities

- `requester-email-ingress`: the receiver's route, registration and secret check, the receipt's contents and the five-minute signature window (D10, D1), as added requirements.
- `email-delivery`: thread notices for requests with a bound thread, and the conversational reply's idempotency horizon (D8).
- `meeting-requests`: requests started by email (D6) and the **Continue by email** controls on the booking page (D7, D9).

This change also closes scenarios that the main specs already state, without changing their text:

| Specification | Closed in this change | Deferred, and where |
|---|---|---|
| [`requester-email-ingress`](../../specs/requester-email-ingress/spec.md) | "Former consumer delivers"; "Concurrent retries and lost response"; "Changed retry"; "Inspect ingress effects" | Real AgentMail delivery: blocked on the inbox (below) |
| [`email-delivery`](../../specs/email-delivery/spec.md) | "Conversational delivery retry"; the thread half of "Requester status notifications" | Live inbox evidence (blocked, below) |
| [`messaging-environments`](../../specs/messaging-environments/spec.md) | "Preview with copied provider credentials" and "Direct provider adapter invocation" for conversational email | None |

## Archive order

Phases 3 and 4 are not archived yet. This change only adds requirements, so it can archive in any order after the phases it builds on; archiving Phases 3 and 4 first keeps the main specs' history in delivery order.

## Impact

- **New code:** `agent/channels/agentmail.ts`; `lib/server/{agentmail,agentmail-receiver,email-receipts,email-threads,email-links,email-replies}.ts`; `lib/contracts/email-link.ts`; `/api/requests/{bookingId}/email-link`; the **Continue by email** card; the `email-receiver` operator commands.
- **Changed code:** `vercel.ts` routes `/agentmail/*` to the agent service; the session-owner hook wakes a waiting reply when a turn ends; `booking-notices.ts` adds thread notices; the job registry gains `email_receipt` and `email_reply`; the requester instructions say that email continues at the booking link for times and agreement; the public host page shows the email start link when the inbox is configured.
- **Schema:** `email_receivers`, `email_receipts`, `email_threads`, `email_links` and `email_replies`, each with row-level security and no client grants, and a cleanup function on the existing pg_cron schedule pattern, generated through pg-delta.
- **Systems:** AgentMail, with the runtime key's `inbox_read`, `message_read` and `message_send` permissions. Creating `findmeatime@agentmail.to` (blocked by the three-inbox limit), registering the webhook at AgentMail, the shared-project migration, the production deploy and any real email to people outside the team are left to the user (decision log, "Blocked on the user").
- **Documents:** the plan's Phase 7 boxes, [provider setup](../../../documentations/technical_specification/03_provider_setup.md#agentmail), [agent configuration](../../../documentations/technical_specification/04_agent_configuration.md), the [interfaces](../../../documentations/user_experience/03_interfaces.md), the [guest booking flow](../../../documentations/user_experience/06_guest_booking_flow.md), the decision log and the acceptance record, with their Korean mirrors; `.env.example`.
