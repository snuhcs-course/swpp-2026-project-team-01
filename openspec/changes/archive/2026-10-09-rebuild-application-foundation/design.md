# Design

## Context

See [proposal](proposal.md). The implementation begins from scaffolds and retained SQL, not a working application. The user's full implementation/deployment instruction includes incremental commits; retain `feat/reconstruct-application` in the main checkout.

## Goals / Non-Goals

**Goals:** verified principals, audience-safe contracts, shared operation guards, executable runtime integration and a complete release ledger.

**Non-Goals:** duplicate the pending Calendar, setup, feasibility or booking implementations; claim compatibility from installed dependencies.

## Decisions

- MVP host login uses Supabase Google OAuth with PKCE through the existing server-only cookie adapter. The start endpoint accepts no email, provider or return URL from the client; identity scopes and account selection are fixed. The callback returns only to `/app`, and cancellation, wrong-browser and replay failures have a recoverable Google sign-in message. Disable the Email provider in the deployed Supabase Auth configuration while preserving Cloudflare transactional mail, waitlist contact fields and existing identity/admission records. Calendar authorization remains separate. Local database fixtures may use admin-created users/passwords; these are test setup, not product login methods.
- Use root shared TypeScript source with Zod-validated public contracts. Next.js request/cookie handling stays in the web adapter. A generic client-supplied actor object is never authority. Browser PKCE/refresh credentials stay in HttpOnly cookies; Route Handlers verify original tokens and persist refresh cookies. A narrow service-only browser RPC derives host identity/email from current Auth records. Guest fragments are exchanged for request-specific cookies and removed from URLs; closed reads stay receipt-only. Same-origin mutation checks and private/no-store responses guard these adapters. Browser chat uses a cookie-authenticated allowlisted gateway, absolute NDJSON cursors and stable-ID uncertain-send retries. Revocation aborts reads and removes visible history. Calendar callbacks now restore the fixed authorized host/request workspace through the Calendar change; guided setup and calendar selection remain pending.
- Keep the retained SQL as a migration baseline. Review the privileged command entry and verify it locally before adapting it; add migrations for changed behavior instead of overwriting history.
- Use opaque application-owned conversation bindings. Public runtime routes must fail closed until a verified binding and current access checks exist. Separate host-private and requester-facing contexts; disable shared runtime memory. Deliberate host access to shared discussion uses only the shared-safe context, as required by the frontend architecture.
- Store `conversation_scopes` for host setup, host-private request review and explicitly shared request discussion. Scope IDs locate contexts; they never authenticate a caller. Each participant receives a separate internal execution grant, omitted from browser projections.
- Verify host JWTs against the selected Supabase Auth service, then check the referenced `auth.sessions` row, user status and current host admission in the service-only access RPC. Ignore user-editable metadata. Guest credentials are request-bound opaque-token hashes checked against current request state. Closed guest access remains receipt-only through the separate existing receipt boundary.
- Recheck persisted execution grants before runtime output/tool effects; logout, host revocation, guest rotation/expiry/closure and scope retirement deny continuation. A revoked grant cannot be recreated from the same authority key. Custom ingress freezes authenticated messages in a service-only inbox. The delivery hook binds the canonical runtime session, and checkpointed channel state deduplicates delivery; a database receipt alone never suppresses an uncheckpointed input.
- Execute model tools through a service-only conversation RPC that locks current authority and performs the domain command in the same transaction. Derive request/actor from the binding, allowlist operations by audience, and filter shared outputs even on idempotent replay. Use the active eve caller and a server-derived conversation/message/operation retry key. Human decisions, confirmed settings and provider outcomes are absent from model tools. Check wall-clock expiry after lock waits; logout and a tool effect must have a definite transaction order.
- Permit one pending input per conversation and cap the initial inbox at 200 messages. Enforce current access before delivery, per streamed event, and every two seconds while idle; renew streams after 45 seconds with an absolute event cursor. Expose only text and safe lifecycle events. Default runtime controls remain denied. Recover lost dispatch from due inbox rows through a service-only RPC: five claims per sweep, 90-second fenced leases, five-minute uncertain-send retries, and current-grant checks before sending. A minute Supabase Cron wake-up uses environment-specific Vault URL/secret entries; unconfigured local/preview databases perform no network activity. Retain its named schedule in the desired schema because pg-delta tracks cron jobs; later migrations must not remove recovery.
- The local process-kill test accelerates the bundled Workflow inline ownership lease from 860 to five seconds in an isolated fixture. Production defaults remain unchanged; managed recovery latency requires separate evidence.
- Pin eve and template revisions and verify their separate Next.js/eve builds under the compatibility change. Runtime placement/persistence is selected from actual bundled documentation and crash tests, not legacy topology.
- Main specs already settle seven-day request expiry, maximum thirty-day guest credentials, seven-day invitations, stable host handles and English/Korean intake. Preserve these obligations; broader follow-up, localization and retention policies remain release decisions.
- The pending setup change already includes browser-entered six-digit OTP. Implement that delta; obsolete documentation references to reconciling the old LINK flow do not revive it.

## Risks / Trade-offs

- Runtime APIs change → read installed docs, pin versions and keep adapter tests.
- Existing production consumers may still run → inventory and fence each transport before live event processing.
- Local credentials exist but linking metadata does not → verify the selected project and configure explicit targets before remote changes.

## Migration Plan

Commit the ownership/acceptance ledger first, then runtime and foundation slices with tests. Publish no private runtime path without authorization. Preserve provider resources, prior migrations and uncertain effect records. Feature changes retain their existing owners and cannot be marked done until replacement evidence passes.

## Public intake adapter

The manual public handle page now delegates to service-only `fmat_public_intake`. Before exposing a profile or creating a request, the server reads live Calendar metadata and verifies all selected conflict calendars plus the writable destination; database checks fence results against account/admission revocation, changed rules and replaced/revoked connections. Refresh remains encrypted and conditional on the prior ciphertext. An anonymous per-handle HttpOnly proof is established before submission, with a separate non-secret attempt identifier for stale-tab checks. SQL stores only its hash, serializes concurrent submissions, and uses the existing request command with immutable input. Recovering a committed request does not require another provider read and returns only the request ID, original credential expiry and closed flag. Cookies never extend the database credential deadline. Explicit new intake keeps previous receipt cookies; an uncertain submission cannot silently rotate its proof. Optional identity, verified-contact recovery, complete request actions and release acceptance remain pending under their owning changes.

## Request detail review adapter

Model extraction now creates a guest-scoped partial draft through `details_propose`; the former `details_update` model operation is denied. One pending review per request stores immutable normalized proposed values, base revision, clarifications and a message-derived retry identity. The protected browser Apply/Dismiss adapter rechecks current guest authority before accessing even cached decisions. Applying requires the exact review and base revision, explicit confirmation and a stable decision UUID; unresolved questions and superseded or stale drafts fail. The domain command preserves existing proposal invalidation and contact-verification reset. Calendar failure is not cleared by unrelated details. Browser reload and lost-response retry recover the saved review, and actual-runtime post-commit interruption verifies one draft with no scheduling mutation. This is part of task 3.2; complete negotiation, verification, proposals and booking remain pending.

## Explicit request closure

A service-only request lifecycle adapter provides minimal status and explicit guest withdrawal/host decline. Current credentials, ownership, request revision and immutable decision UUID are rechecked under the request lock; host authority does not depend on a live Calendar connection. Exact same-actor/same-input retries after closure return only minimal terminal status. Closure revokes guest mutation/Calendar authority and clears current proposal/evaluation pointers. Legacy generic closure commands and their cached replays are retired. Booking status or any potentially creating/confirmed attempt prevents closure and preserves event identity/reservations; the response never claims an existing event was cancelled. Browser controls sit outside chat, require a separate confirmation, freeze uncertain retry input, read current status after lost responses, and unmount conversation/decision controls on closure or booking-pending status. Full booking-time revalidation and live approval/booking acceptance remain with the booking change.
