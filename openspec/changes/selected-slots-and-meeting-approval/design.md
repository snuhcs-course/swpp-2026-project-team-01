# Design

## Context
현재 공개 구간은 자동 계산해 저장하며 미팅 길이는 요청자가 선택한다. 읽기 전용 OAuth와 미확정 요청만 지원한다.

## Goals / Non-Goals
목표는 링크 공개 범위/길이/시간 후보 선택, 주간 시간표 및 호스트의 명시적 수락이다. LLM 연결, Gmail 권한, 자동 수락, 초대 수신 보장, 기존 Google 일정 수정/취소는 제외한다.

## Decisions
- 공개 범위는 내일부터 향후 14일 안에서 날짜·평일·09:00–20:00을 좁힌다. 미팅 길이는 30/45/60/90/120/180/240분이다. 30분 간격 시작과 소유자 전후 15분 여유를 적용한다.
- 가능한 서로 겹치지 않는 후보를 날짜에 분산해 최대 5개 제시한다. 5개 미만이면 실제 가능한 수를 알리고 2개 미만이면 생성 불가. 임의 시간은 추가하지 않는다.
- 후보 미리보기는 소유자·조건·후보·발급 시각을 HMAC 서명한다. 생성 시 서명/소유자/15분 유효기간/2–5개 선택/최신 캘린더를 다시 확인한다. 브라우저 입력만 신뢰하지 않는다.
- 새 링크는 호스트의 고정 길이 및 선택한 정확한 시작/종료만 저장한다. 기존 링크는 이전 길이 선택 및 구간 동작을 유지한다.
- 요청 제출은 새 링크에서 호스트가 선택한 구체적 시간만 양쪽 캘린더와 장소 조건으로 재검사한다. 반환 후보 최대 3개라는 기존 제한은 유지한다.
- 소유자 Google 로그인에는 calendar.events.owned 쓰기 범위를 추가한다. 기존 계정에는 재동의 버튼을 제공하며 요청자는 읽기 전용을 유지한다. 토큰 응답의 실제 scope를 저장해 UI에 반영한다.
- 수락 API는 세션과 링크 소유권을 확인하고 DB의 짧은 트랜잭션으로 요청과 소유자를 잠근다. 한 소유자당 하나의 confirming 작업만 허용하고 작업별 임대/attempt UUID로 중복 클릭을 제어한다. 외부 Google 호출 동안 DB 트랜잭션을 유지하지 않는다.
- 후보 하나를 고정한 뒤 Google의 결정적 이벤트 ID(요청 UUID 기반)로 기존 등록을 먼저 조회한다. 없으면 양쪽 최신 캘린더 충돌을 확인해 insert(sendUpdates=all, 참석자=저장된 요청자 이메일)한다. 이미 생성된 경우 같은 이벤트로 DB만 복구한다. 통신 결과가 불명확하면 confirming을 유지해 다른 시간으로 중복 등록하지 않는다.
- Google의 자동 캘린더 추가/이메일 수신은 상대 계정 설정의 영향을 받는다. UI는 Google에 초대 발송을 요청했다는 사실만 표시한다.

## Risks / Trade-offs
외부에서 동시에 Google 캘린더를 수정하는 경우 조회와 생성 사이의 경쟁을 완전히 차단할 수 없다. 앱 내 같은 소유자의 수락은 직렬화한다. 확정 처리 중 서버 종료 시 같은 요청의 결과 확인/재시도로 복구하며 다른 요청은 먼저 해당 작업을 끝내도록 안내한다. 이미 만들어진 이벤트가 외부에서 변경/삭제되면 calendar_conflict 상태로 전환해 자동 재생성하지 않으며 다른 요청의 수락을 막지 않는다. 링크 삭제/상태 변경도 같은 소유자 행 잠금을 사용한다. confirming 요청이 있는 링크 삭제는 차단해 복구 경로를 유지한다.

## Migration Plan
추가 컬럼, 기간/길이 제약, 수락 상태와 RPC를 선언형 스키마에 작성하고 pg-delta로 생성한다. 로컬 재생성, 원격 dry-run 후 기존 프로젝트에 적용한다. 기존 링크/요청 데이터는 보존한다.
