# Legacy request API assertion audit

Date: 2026-10-09. Source: `5c305d9^:supabase/functions/api/routes/requests_test.ts` (15 named tests). The retired Hono endpoints are replaced by same-origin browser routes, authenticated conversation ingress and shared services. This audit maps behavior; it does not claim endpoint or response compatibility.

## Evidence owners

- [Request boundary unit tests](../../lib/server/identity/request-boundaries.test.ts): strict review decisions, authorization before evaluation and contact-code projection.
- [Public intake integration](../../tests/integration/public-intake.test.ts): request-bound continuation, concurrent/lost submissions and reordered JSON retries.
- [Review integration](../../tests/integration/request-review.test.ts) and [review window locks](../../tests/integration/request-review-windows.ts): inert drafts, explicit decisions, current authority, immutable replay outcomes and elapsed-time validation.
- [Availability integration](../../tests/integration/availability-evaluation.test.ts): provider ordering, proposal selection and hard constraints that preferences cannot waive.
- [Contact verification](../../tests/integration/contact-verification.test.ts) and [recovery integration](../../tests/integration/requester-recovery.test.ts): protected proof, neutral recovery and limits.
- [Conversation runtime](../../tests/runtime/conversations.test.ts): accepted-input deduplication, process restart, settled replay and authority revocation. This existing suite was inspected, not rerun for this test-only increment.
- [Booking approval integration](../../tests/integration/booking-approval.test.ts): verified host/session, exact version and attributable approval. It passed in the preceding booking audit; this increment does not claim a new live booking run.

## Assertion map

| Retired assertion | Current evidence and disposition |
|---|---|
| Requester message returns inert review without applying/agreement | **Preserved, asynchronous interface.** Conversation ingress accepts a durable message; the runtime proposes one pending review without changing request revision. Review integration separately confirms the original details remain until explicit apply. Drafting or applying details records no requester agreement, host approval or event. The response is no longer a synchronous combined message/model/request object. |
| Review requires request ownership and explicit confirmation | **Preserved.** New unit tests reject false confirmation, caller patch/request/actor/decision claims and copied credentials before SQL. Real integration denies foreign request credentials; the apply operation requires a saved review bound to current guest authority. |
| Stale review cannot overwrite a later revision | **Preserved.** Review integration rejects a mismatched expected revision without mutation. SQL separately compares an unapplied review's base revision to current request revision; lock tests validate windows after waiting and preserve the pending review on failure. Already committed replay has the separate behavior below. |
| Confirmed review applies only scheduling fields | **Review boundary strengthened; editable fields expanded.** Apply accepts only review ID, revision, confirmation and retry key, never a caller patch. Current product intake includes requester name/email, so the saved draft can propose those fields for explicit review; the old blanket contact-field ban is not preserved. Purpose-only integration preserves the existing name. Contact edits use domain invalidation and do not supply verification proof. The [meeting-request contract](../../openspec/specs/meeting-requests/spec.md) owns current collection/review behavior. |
| Creation retry ignores JSON object key order | **Preserved, credentials moved out of response JSON.** New actual intake assertion reverses all detail keys and recovers the same continuation with no Google read or extra request. Browser-issued intake/request cookies carry the random proof; the old deterministic token response is not the API. Changed details under the same proof still conflict. |
| Review retry returns saved result before later revision check | **Exactly-once effect preserved; response projection changed.** New integration applies two reviews, then replays the first. It returns the first review's applied status/result revision with current request revision/details. The current latest review is unchanged and only two detail mutations exist. It does not return an obsolete full request snapshot. Current authority is rechecked even for committed replay. |
| Malformed review windows fail before applying | **Preserved.** Contract tests explicitly reject null/array windows, extra hidden fields and February 30, in addition to offset-free dates. Real review tests reject past/too-short windows and expiry during lock waits without creating or applying a review. |
| Saved message retry recovers when model claim is stale | **Replaced by durable runtime settlement.** Current ingress uses message identity and an independently persisted runtime outcome, not the retired synchronous `model_claim` revision fallback. Runtime tests recover one review after process restart, reject changed-text retries and perform no new model work on settled replay. The old response shape and claim sequence are retired. |
| Unauthorized guest cannot trigger provider evaluation | **Preserved.** New service test rejects the initial request read and asserts zero availability/ranking calls. Actual availability integration verifies guest token/target denial and initial stale revision without provider work. |
| Verification start exposes no plaintext code in SQL or response | **Preserved and scoped.** New unit coverage decrypts the synthetic private SQL ciphertext to verify a six-digit code, checks the exact request/challenge-scoped HMAC, and asserts there is no plaintext code field or secret material in the public result. Actual integration verifies protected challenge persistence, attempt limits and lost-response retries. |
| Recovery is neutral for unavailable/mismatched contact | **Preserved, status renamed.** Actual recovery integration returns exactly `{status:"accepted"}` for unavailable, unverified and mismatched contact, creating no challenge for those cases. The old `pending` label is replaced; no account or request details are disclosed. |
| Recovery throttling remains neutral | **Preserved.** Cooldown and sixth hourly request return the same accepted projection while challenge count remains bounded. This differs from contact-verification limits, which are visible only to the authorized request owner. |
| Proposal retry makes no new provider call | **Preserved, selection boundary moved.** Current proposal creation selects a previously published candidate; it cannot accept an arbitrary slot or fabricate evaluation. New actual evaluator integration snapshots busy/event/route/ranking call counts and verifies exact committed selection replay returns the same result with all counts unchanged. |
| Preference exception cannot waive a hard conflict | **Preserved.** Actual availability integration first confirms a private soft-preference exception, then evaluates a busy interval and rejects confirming an exception against that conflicting evidence. Private decisions do not reach requester projections. |
| Approval source comes only from verified host and current explicit version | **Preserved, stricter input handling.** Booking integration rejects caller `confirmationSource`, false confirmation, stale revision/version and wrong host/session. Current SQL writes the authenticated-web source from the verified route/credential path. The old route silently ignored forged extra claims; current strict schemas reject them. |

## Limits

The new tests plus inspected current suites provide explicit dispositions for these 15 named assertions. They do not close the wider legacy inventory, certify free-form model narration, prove live provider/device/client journeys or establish complete release readiness. Contact collection in reviewed drafts, current-state replay projection and asynchronous message settlement are deliberate current contracts, not byte-for-byte equivalence with the retired routes. The [implementation plan](04_implementation_plan.md) retains the remaining gates.
