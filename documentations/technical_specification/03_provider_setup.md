Schema changes flow in one direction:

1. A teammate edits the desired SQL under `supabase/schemas/` on a topic branch.
2. Generating the migration with pg-delta needs Docker for its shadow database. A teammate whose machine has Docker generates and commits the migration in the same pull request; the full `supabase start` stack is not required for generation.
3. Teammates apply the branch's migrations to their own sandbox with `supabase db push` and reset the sandbox with `supabase db reset --linked` when switching branches or when history diverges. Shared fixtures live in `supabase/seed.sql` so a reset restores them.
4. After review and merge, the [`Deploy shared Supabase`](../../.github/workflows/deploy-shared.yml) workflow prints `supabase db push --dry-run`, pushes the migrations to the shared project, writes the worker URL and secret into Vault when both GitHub secrets are set, and runs `supabase config push`. The push applies every setting `supabase/config.toml` declares, so review a change to that file as a change to the hosted project. The site URL and redirect allowlist come from the `SUPABASE_AUTH_SITE_URL` and comma-separated `SUPABASE_AUTH_ADDITIONAL_REDIRECT_URLS` variables: GitHub repository variables in CI and the root `.env` for local `supabase start`. ## Google identity and Calendar

The MVP requires Google-only host login through Supabase Auth. Host sign-in and requester **Continue with Google** each request identity and Calendar scopes on one consent screen, yet identity login, host eligibility, host Calendar consent, requester identity prefill, requester Calendar consent and personal-agent OAuth remain separate authorization boundaries. Pass the Calendar scopes and offline access through Supabase Auth, read the granted scopes from Google's token information endpoint because Google lets users uncheck scopes and Supabase does not pass them through, and store the provider refresh token server-side at sign-in since Supabase returns it only then and does not refresh provider tokens. Keep that token, sealed, even when the host unchecked the Calendar scopes or they could not be read: Google returns a refresh token only on the first consent, so sign-in does not force `prompt=consent` on every visit, and a host who grants Calendar later still has a token on file. The stored scopes record only Calendar scopes Google reported, and a later consent that omits them revokes nothing. Do not enable email/password, email OTP or magic-link host login.

### Host sign-in values

Recorded 2026-10-19 by the [foundation change](../../openspec/changes/application-foundation/design.md#12-authentication-details).

- **OAuth client.** One web OAuth client in the Google Cloud project `findmeatime` serves every environment. Its ID and secret are `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`: the root `.env` for the local stack, and the `GOOGLE_CLIENT_ID` GitHub variable and `GOOGLE_CLIENT_SECRET` GitHub secret for the shared project, which the deploy workflow writes with `supabase config push`.
- **Scopes.** Supabase Auth requests `openid`, `email` and `profile`; the application adds `https://www.googleapis.com/auth/calendar.calendarlist.readonly` (calendar list) and `https://www.googleapis.com/auth/calendar.events` (read events on selected calendars and create the booking event), with `access_type=offline`. They are defined in [`lib/contracts/google-scopes.ts`](../../lib/contracts/google-scopes.ts) with the API methods each one authorizes. `calendar.events.freebusy` was requested until 2026-11-02 and dropped because nothing called it: free/busy-only calendars are left out, since their events cannot be read. The requester flow asks for `calendar.calendarlist.readonly` and `calendar.events.readonly` ([`lib/server/requester-calendar.ts`](../../lib/server/requester-calendar.ts)). The Google Cloud consent screen declares exactly these scopes, and no Gmail scope.
- **Authorized redirect URIs** in the OAuth client, one per Supabase Auth server:

  | Environment | Redirect URI |
  |---|---|
  | Local stack | `http://127.0.0.1:54321/auth/v1/callback` |
  | Shared `anelszynxtvxoxqvzgqt` (release origin) | `https://anelszynxtvxoxqvzgqt.supabase.co/auth/v1/callback` |

  Each teammate's sandbox adds its own `https://<ref>.supabase.co/auth/v1/callback`.
- **Supabase site URL and redirect allowlist.** Supabase Auth returns only to allowlisted application callbacks. The shared project uses site URL `https://findmeatime.com`, the canonical origin, and allowlist `https://release.findmeatime.com/auth/callback`, `https://findmeatime.com/auth/callback` and `http://localhost:3000/auth/callback`, set through the `SUPABASE_AUTH_SITE_URL` and `SUPABASE_AUTH_ADDITIONAL_REDIRECT_URLS` GitHub variables. The local stack uses `http://localhost:3000` and `http://localhost:3000/auth/callback` from the root `.env`. A sandbox applies the same two variables with `supabase config push --project-ref <sandbox ref>` after confirming the ref.
- **Application callback.** `/auth/callback` always returns to `/app` on the origin the request came to; a cancelled, replayed or other-browser return establishes no session and lands on `/app?sign_in=failed`.
- **More than one origin.** One deployment can serve `https://findmeatime.com` (`APP_ORIGIN`, the canonical origin) and other origins such as `https://release.findmeatime.com`, listed comma-separated in `APP_ALLOWED_ORIGINS`. Each listed origin signs in, returns from Google, passes the cross-site Origin check and gets Secure cookies (on https) on its own; its pages cannot post to another listed origin. A request addressed to an unlisted host, in the URL or a forwarded header, is refused with 421 and never redirected. Add every listed origin's `/auth/callback` to `SUPABASE_AUTH_ADDITIONAL_REDIRECT_URLS`, or Supabase Auth sends that origin's sign-ins to the site URL.
- **Email login.** `[auth.email] enable_signup = false` disables the email provider, so email/password, OTP and magic-link requests fail with `email_provider_disabled` and send no mail. The hosted Cloudflare SMTP configuration is outside `config.toml` and unchanged by the push.
- **Runtime Calendar access.** Since Phase 2 the web and agent services also read `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (the same client) to refresh a host's stored grant when setup reads calendars or analysis runs. Set both in Vercel Production; leave them unset in Preview, where Calendar steps then report unavailable configuration. `GOOGLE_OAUTH_TOKEN_URL` and `GOOGLE_CALENDAR_API_URL` point tests and local runs at a stand-in and are ignored on the production deployment. A host who declined the Calendar scopes reconnects through `/auth/sign-in?consent=calendar`, which needs no extra redirect URI. Requester **Continue with Google** uses the same client by default. Its grants are delete-only: closure, link expiry and **Disconnect** delete the stored token and never call Google's revocation endpoint, so sharing the client never removes a host's Calendar grant. The host client therefore also needs the redirect URIs `https://findmeatime.com/connections/google/callback`, `https://release.findmeatime.com/connections/google/callback` and `http://localhost:3000/connections/google/callback`, and the `calendar.events.readonly` scope on the consent screen. `GOOGLE_REQUESTER_CLIENT_ID` and `GOOGLE_REQUESTER_CLIENT_SECRET` are optional; when set, the web service and the job worker use that client instead, and it needs the same redirect URIs. `GOOGLE_REQUESTER_AUTH_URL` and `GOOGLE_TOKEN_INFO_URL` point tests and local runs at the stand-in and are ignored on the production deployment.
- **Publishing status.** **Testing**, as the user reported on 2026-10-20; Calendar scope verification not yet submitted. While the OAuth app is in **Testing**, Google issues refresh tokens that expire after seven days and only listed test users can sign in; move it to **In production** (unverified, 100-user cap) before Phase 2 relies on stored grants, and submit Calendar scope verification early in Phase 2.

Checks must record OAuth application ownership/publishing state and Google app verification for the sensitive Calendar scopes, exact callback URLs, least permissions, host versus request-bound state, cancellation/replay/wrong-browser denial, refresh, disconnect/reconnect and readable failures. Host calendar roles require actual metadata/write permission. Requester consent is availability-only and requires no host eligibility or account. Keep encrypted grants server-side and reveal neither participant's private events to the other.

## Photon

Photon Spectrum is the iMessage transport. The Phase 6 spike chose an application-owned adapter over eve's native `photonIMessageChannel` on durable receipt, acknowledgment, exact sender identity and recovery ([`host-imessage-channel` design 1](../../openspec/changes/host-imessage-channel/design.md#1-the-transport-spike-and-the-adapter), D1): the native channel answers the webhook after an in-process dispatch with nothing stored, keeps one eve session per iMessage thread and has no outbox. The receiver at `{origin}/photon/webhook` (routed to the agent service) checks `X-Spectrum-Webhook-Id` against `PHOTON_WEBHOOK_ID` and `X-Spectrum-Signature` (`v0=` and the hex HMAC-SHA256 of `v0:{X-Spectrum-Timestamp}:{raw body}` under `PHOTON_WEBHOOK_SECRET`, within 300 seconds), and stores a receipt before answering `200`. Outbound messages use the Spectrum SDK (`@spectrum-ts/core` and `@spectrum-ts/imessage` 12.14.0) with `PHOTON_PROJECT_ID` and `PHOTON_PROJECT_SECRET`; tests and local runs point `PHOTON_API_URL` at a loopback stand-in instead. One project with one line (D7): its number is `PHOTON_LINE_NUMBER`, and `PHOTON_FALLBACK_DAILY_LIMIT` (default 20) caps the fallback code's new conversations per line per rolling day. The sender identifier (D2) is Photon's `message.sender.id`, an E.164 number or an Apple ID email, compared exactly and stored only hashed and sealed; only direct conversations (`space.type = "dm"`) on iMessage count: Photon delivers every platform enabled on the project, WhatsApp Business included, to the one webhook, and the receiver acknowledges and ignores any event whose `platform` is not iMessage. These facts come from Photon's documentation, the SDK and eve's bundled adapter; provisioning the line, registering the webhook and checking the identifier on a real iPhone are operator steps still open.

### First message and host onboarding

Photon's deliverability guidance makes inbound-first the default: an authenticated active host taps **Connect iMessage**, which gets a one-time link code and at once opens Messages with the line's number and the link message in the input (iOS expects `sms:<number>&body=<text>` while Android expects `sms:<number>?body=<text>`; desktops get the inline card with the number, the code, **Copy** and a QR code of the iOS deep link, and a Mac also gets **Open Messages on this Mac**; verify the prefilled input and the QR code on a real iPhone), sends the code from their own iMessage, and confirms the masked sender in the initiating browser, so the service's first message is a reply. The service-sent six-digit fallback is not offered ([`host-imessage-channel`](../../openspec/changes/host-imessage-channel/proposal.md#decisions) D16): in the 2026-10-20 spike Photon's shared lines refused every first message to a number that had not written first (`Target not allowed for this project`), so the service never texts first. The landing's iMessage start (`/?flow=imessage`, D15) gets the same code before sign-in, owned by the browser through the `fmat_imessage_start` cookie, and Thyme's reply to it carries a sign-in link (`/imessage/continue`, D19) signed with the token key, so it needs no further Photon variable. Either start binds only after Google sign-in and **Confirm and link**; an iMessage-first introduction without a code leads to the browser handoff and grants no private access. Test wrong/expired/replayed codes on both paths, a code sent from a different number, resend limits, uncertain delivery, browser binding and unlinking. Keep codes outside the web transcript and model context (the channel consumes the inbound link message before any model turn) and show masked sender/status only.

Verify request selection, private discussion, revision and exact-proposal approval/decline on a controlled iPhone. Unsupported recipients/groups must not receive private state. Record actual device/client versions; transport send success alone cannot establish device receipt or attribution.

### Shared lines and registered users

The production project is on Photon's Free plan, whose iMessage lines are shared: a shared line delivers only messages from registered project users and sends only to them ([troubleshooting](https://photon.codes/docs/spectrum-ts/troubleshooting/imessage), issue #94). Every iMessage link start therefore asks for the person's number first and registers it as a shared user through `POST https://spectrum.photon.codes/projects/{projectId}/users/` with the project credentials. The code is then addressed to the `assignedPhoneNumber` Photon returns, kept on the attempt as `imessage_links.line_number` ([`imessage-number-registration`](../../openspec/changes/imessage-number-registration/proposal.md#decisions) D1, D2). `PHOTON_LINE_NUMBER` only turns iMessage on. The Free plan allows 10 registered users and Pro 100 ([pricing](https://photon.codes/pricing)); a full project refuses new numbers. Read the registered users with `photon spectrum users ls --project <id>`. A dedicated line (Business) has no such list.

Every WhatsApp link start (the host's link step and Connect WhatsApp card, `/?flow=whatsapp` and the guest's **Get updates in WhatsApp**) registers the entered number the same way since 2026-11-04 ([`guest-whatsapp-link`](../../openspec/changes/guest-whatsapp-link/proposal.md#decisions) D3), so each WhatsApp start also spends a project user. The `assignedPhoneNumber` in the answer is an iMessage pool number and is discarded: a WhatsApp attempt keeps no `line_number` (a check enforces it), and its code is addressed to `PHOTON_WHATSAPP_NUMBER`. Whether Photon requires, accepts or ignores this registration for WhatsApp Business senders on the Free plan has not been verified.

## Telegram

Telegram is the transport of the host Telegram channel, proposed on 2026-11-04 in the [`host-telegram-channel` change](../../openspec/changes/host-telegram-channel/proposal.md#decisions). Its webhook, records and Bot API transport (Lane A) are implemented; linking and the channel's behavior (Lanes B and C) are not, so a Telegram update is stored and then ignored. It uses the Telegram Bot API directly, not Photon (D1). Photon's Telegram provider, `@spectrum-ts/telegram` 12.14.0, registers the bot's webhook at Photon's relay and delivers updates to the application over a persistent WebSocket (`wss://fusor-ws.spectrum.photon.codes/v1/subscribe`), which a Vercel Function cannot hold.

- **Bot.** `@findmeatime_bot`, created by the user with [@BotFather](https://t.me/BotFather) on 2026-11-04. The token is the bot's only credential; `/revoke` in @BotFather replaces it.
- **Variables.** `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` (`findmeatime_bot`) and `TELEGRAM_WEBHOOK_SECRET` (32 or more random URL-safe characters) on Vercel Production only, under the messaging gate; tests point `TELEGRAM_API_URL` at a loopback stand-in. The user keeps the token and username in the main checkout's `.env` for local runs.
- **Webhook.** `https://findmeatime.com/telegram/webhook`, registered by `npm run telegram:webhook` with `setWebhook` (`secret_token`, `allowed_updates` `message`, `callback_query` and `my_chat_member`, `max_connections` 10) and `setMyCommands`, then checked with `getWebhookInfo`, printed without the token. The script reads `TELEGRAM_BOT_TOKEN` and `TELEGRAM_WEBHOOK_SECRET` from the environment or the root env files, and refuses any origin but `https://findmeatime.com` and any `TELEGRAM_API_URL` that is not a loopback stand-in. Telegram sends the secret in `X-Telegram-Bot-Api-Secret-Token` and signs nothing else. It retries an unanswered update for up to 24 hours.
- **Limits.** About one message per second to one chat and 30 per second overall; 4,096 characters per message; 64 bytes of `callback_data`; messages can be edited for 48 hours. A bot can message a user only after the user started it, and gets `403` once the user blocks it.
- **Privacy.** Bot chats are not end-to-end encrypted and stay on Telegram's servers; the card and the privacy policy say so.

Never set the bot's token, register its webhook or send a Telegram message from an agent session without the user's approval.

## Model access and runtime

Keep model configuration server-side and call OpenAI directly with the team's own API key; the AI Gateway is not used. The model is `gpt-5.6-terra`, decided 2026-10-19 and recorded in the [foundation design](../../openspec/changes/application-foundation/design.md#5-model-route-and-model). Confirm the model ID, price and tool support against the team's key in the foundation change, while enforcing the agreed [model limits](../../openspec/specs/model-execution/spec.md). Test invalid/refused outputs, provider deadlines, rate/credit failures, durable usage accounting and private-data filtering using synthetic context. A model failure never advances scheduling state or creates approval.

The optional guest calendar screenshot path uses the same `gpt-5.6-terra` model through the web server's Responses API call. Set `CALENDAR_OCR_API_KEY` on the web runtime to use a separately scoped key, or let it use the existing server-only `OPENAI_API_KEY`; neither belongs in browser variables. `CALENDAR_OCR_ENABLED` defaults to `false` and must be set to `true` for that environment after the [provider activation gate](#environment-and-activation-checklist), a model-access and budget check, a synthetic day/week image test and review of the updated public privacy notice. The request sends one validated image and the guest's IANA timezone, uses `store: false`, a 30-second deadline and a strict date/time-only output schema, and keeps the image and raw provider response out of request storage and logs. When disabled, without a key or on provider failure it offers manual entry. The request-scoped endpoint does not make an external call until an authorized guest explicitly selects **Read screenshot**.

The agent service accepts only two credentials on `/eve/v1` (foundation design decision 7): a 60-second internal bearer the web service signs with `EVE_INTERNAL_SIGNING_KEY` to create a session, send its current accepted input or read one session's record when reconciling a missed turn end, and the browser's Supabase session cookie to stream its own current session. The agent service signs bearers too: when a session goes idle, its session-owner hook signs a send bearer for the discussion's next accepted input and posts it to its own `/eve/v1` route, so it needs `EVE_AGENT_URL` or `APP_ORIGIN` to reach itself. So far that self-call has been exercised only under `eve dev` in the integration tests, not in a deployment. Set the same `EVE_INTERNAL_SIGNING_KEY` (at least 32 characters) for both services of an environment, with a different value in Production and in Preview, and never expose it to a browser. The bearer also names the deployment environment that signed it and, for a send, the SHA-256 of its message, but only distinct keys keep a Preview deployment from minting Production bearers. The agent service also needs `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` to check the session index and the browser's session. Locally, `npm run dev` starts both services from the root env files, with `.env.local` overriding `.env`; set them to the local stack values from `supabase status -o env` or the teammate's sandbox, never to the shared or release project. The web service reaches the agent at `EVE_AGENT_URL`, `http://127.0.0.1:2000` for a local `eve dev`; deployments leave it unset and use `APP_ORIGIN`, whose `/eve/v1` routes the composed project sends to the agent service.

## Operations runbook

The [`operations-and-release` change](../../openspec/changes/operations-and-release/design.md) adds these operator steps. Every command runs from a checkout with `npm run admin --`, names exactly one environment (`--local` for the local stack, or `--project <ref>` with the operator's own `SUPABASE_ACCESS_TOKEN` through the Management API) and an `--operator` name, and never prints credentials, recipients, payloads or message text. The operator on rotation (D3) runs them.

### Daily diagnostics

- `npm run admin -- diagnostics snapshot --operator <name> --project <ref>` prints ten categories: exhausted, lease-expired and overdue jobs; bookings whose write may exist (`bookings_uncertain`) and reservations older than 15 minutes; uncertain transactional emails and thread replies; uncertain or failed iMessage sends; failed conversation sessions; and inputs unanswered after 10 minutes. Each shows its count, its oldest timestamp and up to 20 identifiers (`--samples` lowers it; `--json` prints the object). It changes nothing, an expired lease included, and an empty snapshot is not proof that providers or deliveries work.
- `npm run admin -- diagnostics rejections --operator <name> --project <ref>` prints the authorization-denial and stale-action counts of the current and preceding 23 UTC hours. They are recorded only while `DIAGNOSTICS_REJECTIONS=1` is set on the deployment, only for failures that reached the command pipeline, and a bucket stops at 10,000 and says so. A rise in denials points to probing or a broken client; a rise in stale actions to people acting on old proposals.

### Recovery

- **Exhausted job.** Fix the cause first (a provider outage, a revoked credential), then `npm run admin -- recover job --job <id> --reason <text> --operator <name> --project <ref>` with `--attempts 1` to `10` (default 3). Only an exhausted job is accepted; it becomes pending and due now, under a new fence. Handlers already refuse to repeat a side effect: a delivery found dispatching becomes uncertain instead of being sent again, and a booking found dispatching is reconciled.
- **Booking whose write is uncertain** (`bookings_uncertain`). `npm run admin -- recover booking --booking <id> --reason <text> --operator <name> --project <ref>` publishes one reconciliation job when none is pending or running. It reads the event by its fixed ID and confirms the booking, or inserts the same frozen payload, which Google refuses if the event exists. A party's **Check booking status** does the same. The command never marks a booking confirmed or failed and never releases its reservation.
- **Uncertain email, thread reply or iMessage.** No command resends it: the delivery contracts forbid a second send of a message that may have arrived. If the person needs the information, answer them through support.

Both commands print the environment and the action and ask for the typed ID unless `--yes` is given. Every recovery is recorded in `app.operator_operations` with the operator, the action, the target, the state found, the reason and the environment.

### Backup restoration

- **Drill.** `npm run restore:drill` (add `-- --keep` to inspect the result) runs inside the local stack's database container. It builds `fmat_drill_source` from the local schema and migration history, fills it with the synthetic fixture `scripts/fixtures/restore-drill.sql`, backs it up with `pg_dump --format=custom`, restores the backup into the empty `fmat_drill_restored` with `pg_restore`, and compares every table's row count and row hash, the migration history and constraint validity, then runs the diagnostics snapshot on the restored copy. It prints counts and hashes only, checks that the local database did not change, and drops both databases. Run it before the release and after every change that adds migrations; the [acceptance record](07_acceptance_record.md#phase-8--operations-and-release) holds the last run.
- **Hosted backup.** Restore only into a **new** project, never over a live one: either Supabase's daily backup or point-in-time restore into a new project from the dashboard, or a `supabase db dump` file restored with `pg_restore` into a new project's database. Compare the restored project with the drill's checks before pointing anything at it. Real backups hold personal data: keep them in the provider, never copy them to a laptop or into Git. Restoring is the repository owner's step (D3).

### Retention and deletion

- **Retention** runs by itself: `pg_cron` job `app-retention` calls `app.cleanup_retained_records(1000)` at minute 17 of every hour. It deletes closed requests with everything under them 90 days after closure; completed jobs, command outcomes, link-resend records, admission windows and agent protocol attempts after 30 days; exhausted jobs and model reservations after 90 days; and operator audit rows after a year, at most 1,000 rows per rule per run. The earlier rules stay: Calendar analyses, sign-up and creation attempts and drafts after 24 hours, email and iMessage records after 30 days, requester grants at closure. Check it with `select * from cron.job_run_details where jobid = (select jobid from cron.job where jobname = 'app-retention') order by start_time desc limit 5`. That history is kept 7 days: at minute 47 of every hour, job `app-cron-history` deletes runs that ended more than 7 days ago, or that a restart interrupted and started more than 7 days ago. Later runs reuse the space freed, so the database size in the dashboard stops growing rather than dropping.
- **Deletion on request.** Verify the request came from the address on the account, then run `npm run admin -- delete-host --host <handle-or-id> --reason <text> --operator <name> --project <ref>` or `npm run admin -- delete-request --request <id> --reason <text> --operator <name> --project <ref>`. For a requester, find the request from the booking link they send: `select request_id from app.booking_links where link_hash = encode(sha256(convert_to(lower('<bookingId>'), 'UTF8')), 'hex')` (the hash `hashBookingId` in `lib/server/booking-links.ts` computes). A host keeps only a suspended, nameless account row with its handle history, so the handle is never assigned to anyone else; `restore` refuses it, and the same Google account later signs up afresh. Both commands refuse while a booking write may exist; reconcile it with `recover booking` first. Calendar events already created, the person's own mail, AgentMail threads, Photon conversations and OpenAI's abuse logs are outside the database; say so in the reply.
- **Notice.** [`/privacy`](../../apps/web/app/privacy/page.tsx) states these rules for hosts and requesters in English and Korean. Change it in the same pull request as any retention or provider change.

### Performance check

`npm run perf:check -- --origin <origin> [--handle <handle>] [--samples 20]` sends sequential `GET` requests to `/`, `/SKILL.md`, `/llms.txt`, `/eve/v1/health` and, with `--handle`, the host page, and fails a route whose p50 is over 800 ms or whose p95 is over 2,000 ms (D4). It reads public pages only. Run it against both origins after each production deploy; approval-to-booking and first-reply times have no tool yet and are reported as not measured.
