Schema changes flow in one direction:

1. A teammate edits the desired SQL under `supabase/schemas/` on a topic branch.
2. Generating the migration with pg-delta needs Docker for its shadow database. A teammate whose machine has Docker generates and commits the migration in the same pull request; the full `supabase start` stack is not required for generation.
3. Teammates apply the branch's migrations to their own sandbox with `supabase db push --remote` and reset the sandbox with `supabase db reset --linked` when switching branches or when history diverges. Shared fixtures live in `supabase/seed.sql` so a reset restores them.
4. After review and merge, the [`Deploy production`](../../.github/workflows/deploy-production.yml) workflow runs on every push to `main`. It pushes the migrations, the worker's Vault entries and the hosted configuration to the shared project, then deploys Vercel Production; [Deploying to the shared environment](#deploying-to-the-shared-environment) below gives the steps, the order and every secret and variable it reads. The push applies every setting `supabase/config.toml` declares, so review a change to that file as a change to the hosted project. The site URL and redirect allowlist come from the `SUPABASE_AUTH_SITE_URL` and comma-separated `SUPABASE_AUTH_ADDITIONAL_REDIRECT_URLS` variables: GitHub repository variables in CI and the root `.env` for local `supabase start`. The insert trigger and the every-minute `pg_cron` sweep post to `WORKER_URL` with `WORKER_SECRET` and do nothing while either Vault entry is missing, as in every sandbox. When the release split moves this row to `findmeatime-dev` (D13), change `VERCEL_PROJECT_ID` and the origin the workflow checks.

### Deploying to the shared environment

The shared test environment is the shared Supabase project `anelszynxtvxoxqvzgqt` together with the Vercel **Production** deployment of `findmeatime-release` on `https://findmeatime.com` and `https://release.findmeatime.com`. A branch reaches it only by merging into `main`: the [`Deploy production`](../../.github/workflows/deploy-production.yml) workflow deploys **every** push to `main`, so a merge is a deployment. Follow these steps for every branch; nobody needs to ask the person who set the environment up. A teammate other than the author has not yet followed them end to end ([#141](https://github.com/snuhcs-course/swpp-2026-project-team-01/issues/141)).

**One-time access.** Read access to the repository's Actions runs (`gh run list`) is enough for the normal path. The manual fallback below also needs a Vercel login with access to the `justdodos-projects` team (`vercel whoami`, `vercel teams ls`); ask the repository owner for it.

**1. Before opening the pull request.**

- *Migrations.* Generate and review them with the [pg-delta workflow](../../AGENTS.md#supabase-schema-changes) and apply them to your own sandbox with `supabase db push --remote` (step 3 of the schema flow above). Never push a branch's migrations to the shared project. Between the migration push and the Vercel deploy the **current** app runs on the **new** schema for a few minutes, so a migration must keep working with the app already on `main`: add columns, tables and functions in one pull request, and drop or rename what the old app reads only in a later one, after the app that stopped reading it is deployed.
- *Hosted Auth configuration.* `supabase config push` applies every setting `supabase/config.toml` declares to the shared project on the merge, so treat a change to that file as a change to production.
- *Environment variables.* The web and agent services are two services of the one Vercel project, composed by [`vercel.ts`](../../vercel.ts) with `withEve`; there is no separate eve deployment, and both read the project's variables. Add each new name to [`.env.example`](../../.env.example), then have the repository owner set it on `findmeatime-release` for Production and, where Preview needs it, Preview (`vercel env add <NAME> production`; `vercel env ls production` lists the names). A deployment reads the values present when it builds, so set a variable **before** the merge; one set afterwards needs a redeploy (step 3). On 2026-11-14 the Telegram webhook answered `401` until a redeploy after its variables were set ([acceptance record](07_acceptance_record.md#phase-10--host-telegram-channel)).
- *A Preview, if wanted.* The Vercel project has no Git connection, so a pull request gets no Preview. `vercel deploy` without `--prod` from the branch makes one by hand. A Preview uses the Preview variables, whose `DATABASE_URL` points at the shared project, sends no email or iMessage and runs no job worker. Do not preview a branch whose migrations are not yet on `main`: the shared schema does not have them. Use a sandbox instead.

**2. Merge.** After review and passing checks, merge the pull request into `main`. `Deploy production` then runs in this order, and a failed step stops everything after it:

1. **Supabase**, the reusable [`Deploy shared Supabase`](../../.github/workflows/deploy-shared.yml) workflow: `supabase link`, `supabase db push --remote --dry-run` (the pending migrations), `supabase db push --remote --yes`, the worker URL and secret into Vault (`supabase db query --remote --yes`), then `supabase config diff --remote` and `supabase config push --remote --yes`. Supabase CLI 3 targets the local stack unless `--remote` is given and refuses a write to a hosted project in CI without `--yes`, so every hosted step carries both.
2. **Vercel**, only after the Supabase job succeeds: `npm ci`, then `vercel deploy --prod` from the clean checkout (Vercel builds remotely; [`.vercelignore`](../../.vercelignore) keeps env files out), then a check that `https://findmeatime.com/eve/v1/health` answers.

The runs share one concurrency group and do not cancel a run in progress, but GitHub cancels a queued run when a newer push queues behind it; the newer run deploys the newer revision with every migration, since each step is a no-op when nothing is pending.

**3. Check it landed.**

- `gh run list --workflow deploy-production.yml --limit 5` shows the run for your merge commit; `gh run watch <run-id>` follows it, and `gh run view <run-id> --log-failed` shows why one failed.
- The **Vercel** job's summary names the commit and the deployment URL. The **Show pending migrations** step of the **Supabase** job lists what was pushed; a later run reports the remote database up to date.
- `curl -fsS https://findmeatime.com/eve/v1/health` succeeds, and the pages your change touches answer on both origins.
- To redeploy without a new commit, for example after a variable change, start the workflow on `main`: `gh workflow run deploy-production.yml --ref main`.
- Record a deployment that produces acceptance evidence in the [acceptance record](07_acceptance_record.md), with the revision, the run or deployment ID, the commands and the results.

## Google identity and Calendar

The MVP requires Google-only host login through Supabase Auth. Host sign-in and requester **Continue with Google** each request identity and Calendar scopes on one consent screen, yet identity login, host eligibility, host Calendar consent, requester identity prefill, requester Calendar consent and personal-agent OAuth remain separate authorization boundaries. Pass the Calendar scopes and offline access through Supabase Auth, read the granted scopes from Google's token information endpoint because Google lets users uncheck scopes and Supabase does not pass them through, and store the provider refresh token server-side at sign-in since Supabase returns it only then and does not refresh provider tokens. Keep that token, sealed, even when the host unchecked the Calendar scopes or they could not be read: Google returns a refresh token only on the first consent, so sign-in does not force `prompt=consent` on every visit, and a host who grants Calendar later still has a token on file. The exception is a sign-in that links an iMessage conversation (the iMessage start, Thyme's sign-in link or `return=imessage`): it sends `prompt=consent` and `include_granted_scopes=true`, because a Google account that authorized this client before would otherwise sign in with no refresh token and be asked for Calendar again in iMessage ([`imessage-onboarding-calendar-consent`](../../openspec/changes/imessage-onboarding-calendar-consent/proposal.md) D1, #407). Any other sign-in that asks for Calendar records in an HTTP-only `fmat_auth_consent` cookie that it skipped the consent screen; when its callback finds every Calendar scope granted but no usable grant (no refresh token, or one Google rejected), it goes straight on to `/auth/sign-in?consent=calendar`, so only a host who would otherwise be asked again sees a second Google screen (D3). The stored scopes record only Calendar scopes Google reported, and a later consent that omits them revokes nothing. Do not enable email/password, email OTP or magic-link host login.

### Host sign-in values

Recorded 2026-10-19 by the [foundation change](../../openspec/changes/archive/2026-11-24-application-foundation/design.md#12-authentication-details).

- **OAuth client.** One web OAuth client in the Google Cloud project `findmeatime` serves every environment. Its ID and secret are `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`: the root `.env` for the local stack, and the `GOOGLE_CLIENT_ID` GitHub variable and `GOOGLE_CLIENT_SECRET` GitHub secret for the shared project, which the deploy workflow writes with `supabase config push`.
- **Scopes.** Supabase Auth requests `openid`, `email` and `profile`; the application adds `https://www.googleapis.com/auth/calendar.calendarlist.readonly` (calendar list) and `https://www.googleapis.com/auth/calendar.events` (read events on selected calendars and create the booking event), with `access_type=offline`. They are defined in [`lib/contracts/google-scopes.ts`](../../lib/contracts/google-scopes.ts) with the API methods each one authorizes. `calendar.events.freebusy` was requested until 2026-11-02 and dropped because nothing called it: free/busy-only calendars are left out, since their events cannot be read. The requester flow asks for `calendar.calendarlist.readonly` and `calendar.events.readonly` ([`lib/server/requester-calendar.ts`](../../lib/server/requester-calendar.ts)). The Google Cloud consent screen declares exactly these scopes, and no Gmail scope.
- **Authorized redirect URIs** in the OAuth client, one per Supabase Auth server:

  | Environment | Redirect URI |
  |---|---|
  | Local stack | `http://127.0.0.1:54321/auth/v1/callback` |
  | Shared `anelszynxtvxoxqvzgqt` (release origin) | `https://anelszynxtvxoxqvzgqt.supabase.co/auth/v1/callback` |

  Each teammate's sandbox adds its own `https://<ref>.supabase.co/auth/v1/callback`.
- **Supabase site URL and redirect allowlist.** Supabase Auth returns only to allowlisted application callbacks. The shared project uses site URL `https://findmeatime.com`, the canonical origin, and allowlist `https://release.findmeatime.com/auth/callback`, `https://findmeatime.com/auth/callback` and `http://localhost:3000/auth/callback`, set through the `SUPABASE_AUTH_SITE_URL` and `SUPABASE_AUTH_ADDITIONAL_REDIRECT_URLS` GitHub variables. The local stack uses `http://localhost:3000` and `http://localhost:3000/auth/callback` from the root `.env`. A sandbox applies the same two variables with `supabase config push --remote=<sandbox ref>` after confirming the ref.
- **Application callback.** `/auth/callback` always returns to `/app` on the origin the request came to; a cancelled, replayed or other-browser return establishes no session and lands on `/app?sign_in=failed`.
- **More than one origin.** One deployment can serve `https://findmeatime.com` (`APP_ORIGIN`, the canonical origin) and other origins such as `https://release.findmeatime.com`, listed comma-separated in `APP_ALLOWED_ORIGINS`. Each listed origin signs in, returns from Google, passes the cross-site Origin check and gets Secure cookies (on https) on its own; its pages cannot post to another listed origin. A request addressed to an unlisted host, in the URL or a forwarded header, is refused with 421 and never redirected. Add every listed origin's `/auth/callback` to `SUPABASE_AUTH_ADDITIONAL_REDIRECT_URLS`, or Supabase Auth sends that origin's sign-ins to the site URL.
- **Email login.** `[auth.email] enabled = false` disables the email provider, so email/password, OTP and magic-link requests fail with `email_provider_disabled` and send no mail. The hosted Cloudflare SMTP configuration is outside `config.toml` and unchanged by the push.
- **Runtime Calendar access.** Since Phase 2 the web and agent services also read `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (the same client) to refresh a host's stored grant when setup reads calendars or analysis runs. Set both in Vercel Production; leave them unset in Preview, where Calendar steps then report unavailable configuration. `GOOGLE_OAUTH_TOKEN_URL` and `GOOGLE_CALENDAR_API_URL` point tests and local runs at a stand-in and are ignored on the production deployment. A host who declined the Calendar scopes reconnects through `/auth/sign-in?consent=calendar`, which needs no extra redirect URI. Requester **Continue with Google** uses the same client by default. Its grants are delete-only: closure, link expiry and **Disconnect** delete the stored token and never call Google's revocation endpoint, so sharing the client never removes a host's Calendar grant. ## Operations runbook

The [`operations-and-release` change](../../openspec/changes/archive/2026-11-24-operations-and-release/design.md) adds these operator steps. Every command runs from a checkout with `npm run admin --`, names exactly one environment (`--local` for the local stack, or `--project <ref>` with the operator's own `SUPABASE_ACCESS_TOKEN` through the Management API) and an `--operator` name, and never prints credentials, recipients, payloads or message text. The operator on rotation (D3) runs them.

### Daily diagnostics

- `npm run admin -- diagnostics snapshot --operator <name> --project <ref>` prints ten categories: exhausted, lease-expired and overdue jobs; bookings whose write may exist (`bookings_uncertain`) and reservations older than 15 minutes; uncertain transactional emails and thread replies; uncertain or failed iMessage sends; failed conversation sessions; and inputs unanswered after 10 minutes. Each shows its count, its oldest timestamp and up to 20 identifiers (`--samples` lowers it; `--json` prints the object). It changes nothing, an expired lease included, and an empty snapshot is not proof that providers or deliveries work.
- `npm run admin -- diagnostics rejections --operator <name> --project <ref>` prints the authorization-denial and stale-action counts of the current and preceding 23 UTC hours. They are recorded only while `DIAGNOSTICS_REJECTIONS=1` is set on the deployment, only for failures that reached the command pipeline, and a bucket stops at 10,000 and says so. A rise in denials points to probing or a broken client; a rise in stale actions to people acting on old proposals.
- `npm run admin -- diagnostics usage --operator <name> --project <ref>` prints, for iMessage, WhatsApp and Telegram, the hosts with an active binding, the inbound messages, the requests whose guest linked the channel and the bookings confirmed on them, per UTC day for the last 14 days (`--periods` up to 90). `--by week` groups them into ISO weeks from Monday (8 by default, up to 52), summing the days and giving the busiest day's active hosts; `--until <YYYY-MM-DD>` ends the report earlier; `--json` prints the object. The counts come from `app.channel_usage_days`, which the hourly `app-channel-usage` pg_cron job recounts for the last 7 days from the receipts, bindings and bookings, so they outlive the 30-day deletion of those rows ([`channel-usage-report` design](../../openspec/changes/archive/2026-11-23-channel-usage-report/design.md)). It prints counts and dates only and changes nothing. A period marked not recorded, or partly recorded, was missed (before the first count or while pg_cron was down), not a period without activity; a request does not record the channel it started in, so guest links are the closest measure.

### Recovery

- **Exhausted job.** Fix the cause first (a provider outage, a revoked credential), then `npm run admin -- recover job --job <id> --reason <text> --operator <name> --project <ref>` with `--attempts 1` to `10` (default 3). Only an exhausted job is accepted; it becomes pending and due now, under a new fence. Handlers already refuse to repeat a side effect: a delivery found dispatching becomes uncertain instead of being sent again, and a booking found dispatching is reconciled.
- **Booking whose write is uncertain** (`bookings_uncertain`). `npm run admin -- recover booking --booking <id> --reason <text> --operator <name> --project <ref>` publishes one reconciliation job when none is pending or running. It reads the event by its fixed ID and confirms the booking, or inserts the same frozen payload, which Google refuses if the event exists. A party's **Check booking status** does the same. The command never marks a booking confirmed or failed and never releases its reservation.
- **Uncertain email, thread reply or iMessage.** No command resends it: the delivery contracts forbid a second send of a message that may have arrived. If the person needs the information, answer them through support.

Both commands print the environment and the action and ask for the typed ID unless `--yes` is given. Every recovery is recorded in `app.operator_operations` with the operator, the action, the target, the state found, the reason and the environment.

### Backup restoration

- **Drill.** `npm run restore:drill` (add `-- --keep` to inspect the result) runs inside the local stack's database container. It builds `fmat_drill_source` from the local schema and migration history, fills it with the synthetic fixture `scripts/fixtures/restore-drill.sql`, backs it up with `pg_dump --format=custom`, restores the backup into the empty `fmat_drill_restored` with `pg_restore`, and compares every table's row count and row hash, the migration history and constraint validity, then runs the diagnostics snapshot on the restored copy. It prints counts and hashes only, checks that the local database did not change, and drops both databases. Run it before the release and after every change that adds migrations; the [acceptance record](07_acceptance_record.md#phase-8--operations-and-release) holds the last run.
- **Hosted backup.** Restore only into a **new** project, never over a live one: either Supabase's daily backup or point-in-time restore into a new project from the dashboard, or a `supabase db dump` file restored with `pg_restore` into a new project's database. Compare the restored project with the drill's checks before pointing anything at it. Real backups hold personal data: keep them in the provider, never copy them to a laptop or into Git. Restoring is the repository owner's step (D3).

### Retention and deletion

- **Retention** runs by itself: `pg_cron` job `app-retention` calls `app.cleanup_retained_records(1000)` at minute 17 of every hour. It deletes closed requests with everything under them 90 days after closure, except a request matched to an account that still exists, which is kept as that account's history ([`guest-account-history`](../../openspec/specs/guest-account-history/spec.md)); completed jobs, command outcomes, link-resend records, admission windows and agent protocol attempts after 30 days; exhausted jobs and model reservations after 90 days; operator audit rows after a year; and account emails 30 days after they finish, at most 1,000 rows per rule per run. The earlier rules stay: Calendar analyses, sign-up and creation attempts and drafts after 24 hours, email and iMessage records after 30 days, requester grants at closure. Check it with `select * from cron.job_run_details where jobid = (select jobid from cron.job where jobname = 'app-retention') order by start_time desc limit 5`. That history is kept 7 days: at minute 47 of every hour, job `app-cron-history` deletes runs that ended more than 7 days ago, or that a restart interrupted and started more than 7 days ago. Later runs reuse the space freed, so the database size in the dashboard stops growing rather than dropping.
- **Self-service deletion.** A host deletes their own account in Settings ([`self-service-account-deletion`](../../openspec/changes/archive/2026-11-24-self-service-account-deletion/design.md)): `host_accounts.deletion_due_at` holds the due time, and a `host_deletion` job runs `app.operator_delete_host` then, recorded in `operator_operations` with operator `self-service`. Signing in clears it. Find pending ones with `select id, deletion_due_at from app.host_accounts where deletion_due_at is not null`. A `host_deletion` job that keeps failing with `booking_pending` waits on a booking write: reconcile it with `recover booking`. Point a host who writes to support and can still sign in to Settings.
- **Deletion on request.** For anyone who cannot sign in, and for requests: verify the request came from the address on the account, then run `npm run admin -- delete-host --host <handle-id-or-google-address> --reason <text> --operator <name> --project <ref>` (an account that only books with others has no handle; name it by the Google address the request came from) or `npm run admin -- delete-request --request <id> --reason <text> --operator <name> --project <ref>`. For a requester, find the request from the booking link they send: `select request_id from app.booking_links where link_hash = encode(sha256(convert_to(lower('<bookingId>'), 'UTF8')), 'hex')` (the hash `hashBookingId` in `lib/server/booking-links.ts` computes). A host keeps only a suspended, nameless account row with its handle history, so the handle is never assigned to anyone else; `restore` refuses it, and the same Google account later signs up afresh. Deleting an account also withdraws the requests it sent to other hosts that are still open and cancels the meetings it booked with them that have not started, through one `account_requests_close` job; run `npm run jobs:dev` locally, or let the worker take it ([`guest-account-history`](../../openspec/specs/guest-account-history/spec.md)). Both commands refuse while a booking write may exist; reconcile it with `recover booking` first. Calendar events already created, the person's own mail, AgentMail threads, Photon conversations and OpenAI's abuse logs are outside the database; say so in the reply.
- **Notice.** [`/privacy`](../../apps/web/app/privacy/page.tsx) states these rules for hosts and requesters in English and Korean. Change it in the same pull request as any retention or provider change.

### Performance check

`npm run perf:check -- --origin <origin> [--handle <handle>] [--samples 20]` sends sequential `GET` requests to `/`, `/SKILL.md`, `/llms.txt`, `/eve/v1/health` and, with `--handle`, the host page, and fails a route whose p50 is over 800 ms or whose p95 is over 2,000 ms (D4). It reads public pages only. Run it against both origins after each production deploy; approval-to-booking and first-reply times have no tool yet and are reported as not measured.
