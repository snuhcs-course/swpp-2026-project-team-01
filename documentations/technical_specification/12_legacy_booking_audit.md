# Legacy booking assertion audit

Date: 2026-10-09. Historical source: `5c305d9^:supabase/functions/_shared/modules/`. This map covers all 24 named tests in `booking/durable_test.ts` (2), `booking/index_test.ts` (16) and `booking_runtime/index_test.ts` (6).

## Current evidence

The [booking integration](../../tests/integration/booking-approval.test.ts) executes the current worker against local Auth/PostgreSQL with controlled Calendar HTTP. Its helpers cover [dispatch](../../tests/integration/booking-dispatch.ts), [fresh evaluation](../../tests/integration/booking-evaluation.ts), [revalidation](../../tests/integration/booking-revalidation.ts), [worker recovery](../../tests/integration/booking-worker.ts), [withdrawal](../../tests/integration/booking-withdrawal.ts), [reconnection](../../tests/integration/booking-recovery.ts), [lease expiry](../../tests/integration/booking-lease.ts), [competition](../../tests/integration/booking-competition.ts) and [43 process-kill cases](../../tests/integration/booking-crashes.ts).

[Worker unit tests](../../lib/server/booking/worker.test.ts) now explicitly reject injected job context before I/O and preserve the claimed lease and SQL fingerprint during saved-event lookup. [Provider tests](../../lib/server/calendar/booking.test.ts) verify the actual HTTP adapter and strict evidence projection. The [availability integration](../../tests/integration/availability-evaluation.test.ts) exercises confirmed receipts through the replacement snapshot/evaluator; the retained historical SQL `evaluation_read` tests alone are not evidence for that replacement.

## Retired command integration (2026-10-10)

Source: `5c305d9^:scripts/tests/booking-integration.ts`, all 648 lines, including its twelve reported check groups. This was a local SQL/handler integration with injected providers, not a live Google or mail journey. The replacement distributes these obligations across independently scoped suites; running only the booking suite does not verify all setup and conversation prerequisites.

| Historical check | Replacement evidence and differences |

It distinguishes a consumed challenge during an already dispatched send from one consumed before dispatch; the former cannot erase possible delivery. |

It does not restore the retired script's permissive actor inputs, direct candidate persistence, exact failure-code vocabulary or setup shortcuts. The remaining request/onboarding command scripts and unresolved online-travel policy still require separate disposition.

## Verification limits

These mappings cover the named assertions above, not every historical implementation branch or all 34 legacy files. Controlled providers and local database tests do not prove live Google consent, event creation, participant delivery, native-device or named-client acceptance. Those gates remain open in the [implementation plan](04_implementation_plan.md). Worker return values, failure codes, strict lease input and persisted evaluation replace the retired handler API; this audit does not claim wire compatibility.
