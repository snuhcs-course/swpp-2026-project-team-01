## 2. Working model

- **One change, one branch, one pull request.** Each phase below is one or more OpenSpec changes. Branch names reuse the change name, for example `feat/application-foundation`. Start every session on the task's own branch so AI usage is attributed correctly.
- **Specs first, then code, then archive.** A change is proposed with its delta specs and tasks, reviewed, implemented with tests, verified, and only then archived into `openspec/specs/`. Pending deltas never become main-spec text early.
- **Schema changes flow one way.** Desired SQL under `supabase/schemas/`, a reviewed pg-delta migration generated by a teammate with Docker in the same pull request, applied to personal sandboxes with `supabase db push`, and pushed to the shared project only by CI on merge. Studio edits are forbidden.
- **Evidence is attached to acceptance scenarios.** Fixtures prove logic; controlled provider, device and named-client checks prove integrations. Neither substitutes for the other. Tokens, personal text and raw transcripts stay out of tracked evidence.
- **Messaging is denied outside production.** Preview and local deployments cannot send email or iMessage, so channel acceptance runs only against the identified production deployment with authorized recipients. Local runs may reach only a loopback stand-in provider, as the [Phase 3 proposal](../../openspec/changes/requester-intake-and-feasibility/proposal.md#conflicts-resolved-here) corrects the messaging-environments contract to say.
- **Reference repositories first.** Before designing or implementing a module, read the files listed for its phase in section 5 and follow their architecture, style and tests wherever our contracts do not say otherwise. Name the repository and revision followed in the pull request.

Team parallelism: Phase 0 and Phase 1 are serial because everything depends on them. From Phase 2 onward, the four-person team can run two or three changes side by side; the dependency table in section 4 shows what can overlap.

## 4. Phases

Each phase lists its scope, the specs it must satisfy, the decisions that must be settled inside it, and the evidence that closes it. Phase numbers are delivery order, not priority.

Scope items are checkboxes so the implementing agent or teammate can mark them done in the pull request that lands them. Within a phase, items are grouped into **lanes**: a lane is a set of items one person or agent can carry on its own branch without waiting on the other lanes, apart from the named prerequisite and join point. Lanes do not change scope; they only say what may run side by side.

### What runs in parallel

Three kinds of parallelism are available, from safest to most coordination-heavy:

1. **Lanes inside a phase.** Listed under each phase above. Each lane is one branch and one pull request, or a few small ones. Lanes touch different modules, so merge conflicts stay in shared contracts under `lib/contracts/`, which the skeleton owner reviews.
2. **Pure domain lanes ahead of their phase.** Phase 3 Lane C (feasibility engine), Phase 4 Lane B (booking job against a fixture request) and Phase 5 Lane A (authorization server) have no UI or provider dependency beyond Phase 1's skeleton and command pipeline. They can start while the preceding phase's conversation work is still in progress.
3. **Whole phases side by side.** Phases 2 and 3 overlap once Phase 1 is joined, because host onboarding and requester intake share only the readiness guard. Phases 5, 6 and 7 are independent of one another after Phase 4. Phase 8 Lanes B, C and D can start after Phase 4 while Lane A waits for real work to inspect.

Things that must stay serial:

- Phase 1's skeleton before any lane, and Phase 1's join before Phase 2 or 3 begins in earnest.
- Phase 1 Lane B's schema baseline before any other migration, since it defines the namespaces, roles and RLS every later table inherits.
- Each phase's OpenSpec proposal before its lanes start coding, and the Phase 6 proposal before any iMessage code, since the retired artifacts must not be extended.
- Proposal, delta specs and tasks reviewed before implementation, and verification before archive, for every change.

Suggested split for four people, one branch each, revised at every join:

| Stage | Person 1 | Person 2 | Person 3 | Person 4 |
|---|---|---|---|---|
| Phase 0 | Link fixes and checker | iMessage artifact decision and Phase 6 proposal draft | Runtime decisions and Phase 1 proposal | Teammate setup, worktree pruning |
| Phase 1 | Skeleton, then Lane A | Lane B | Lane C | Phase 2 and Phase 3 proposals, then Phase 3 Lane C early start |
| Phases 2 and 3 | Phase 2 Lane A | Phase 2 Lanes B and C | Phase 3 Lanes A and D | Phase 3 Lanes B and C |
| Phase 4 | Lane A | Lane B | Lane C | Phase 5 Lane A early start, Phase 5 to 7 proposals |
| Phases 5 to 7 | Phase 5 Lanes B and C | Phase 5 Lane A, then Phase 8 Lane C | Phase 6 all lanes | Phase 7 both lanes |
| Phase 8 | Lane A | Lane C | Lane D and client re-acceptance | Lane B |

The Docker-equipped teammate generates migrations for whichever lane needs one that week. Whoever holds the skeleton reviews every change to `lib/contracts/` and the agent directory layout so lanes do not diverge.

## 6. Reuse from iteration 1

The [transplant guide](../transplant/en/transplant-guide.md) describes a prototype on a different stack: KST-only time handling, Drizzle, Ollama, an invite-only contact model and a client-first ranking rule. Its code is not copied. The following ideas are carried into the phases above because the current documents already require the same behavior:

- Calendar normalization rules: busy unless cancelled, declined or transparent; merge copies only by provider identity; all-day events block time but never anchor travel; ambiguous place-plus-link never decides attendance mode (Phase 2 analysis, Phase 3 feasibility).
- Idempotent operation hook with a frozen command and a "check result" recovery path instead of resubmission (Phase 1 command pipeline and card actions).
- Source-fingerprinted corrections that show "needs re-check" when the source changes (Phase 2 note-like exclusions).
- "Analysis is evidence, never policy" wording and the thin-data message (Phase 2 suggestions).
- Explanations generated from code-computed bases, never written by the model as unverified numbers (Phase 3 candidate explanations).

Not carried: the travel-table heuristic (replaced by Google Routes with buffers), the mutual-contact gate (hosting is open), pending requests that never block, in-app-only events (we write to Google Calendar), and Korean-only UI.

## 8. Risks

| Risk | Effect | Mitigation |
|---|---|---|
| The eve composition does not meet the authorization, reconnection and restart check | Runtime choice reopens late | Phase 1 is the bounded proof; a replacement is an explicit design decision, never a silent second engine |

## 9. Definition of done for each change

- Proposal, delta specs and tasks reviewed by a teammate other than the author.
- The pull request names the reference repository files and revisions followed, and copied code keeps its upstream license notice.
- Unit tests beside modules, integration tests under `tests/integration/`, browser journeys under `tests/e2e/`, and database grant and concurrency tests under `supabase/tests/` for the touched behavior; `npm run check` and the app build, lint, typecheck and test commands pass in CI.
- Documentation updated in the same pull request: the owning product, UX, technical or provider document, `.env.example` for new variables, and the Korean mirror regenerated for changed English documents.
- Acceptance scenarios touched by the change closed with attached evidence or explicitly listed as still pending.
- No placeholder notes, skipped tests or unimplemented branches left behind.
- Change archived with `openspec archive` and the main specs synced after verification.
