# Find Me a Time — 백엔드 아키텍처

상태: Phase 1과 2 구현 완료, 이후 단계는 제안 상태

날짜: 2026-10-19

기반: [PRD](../02_product_requirements.md), [기술 개요](../04_technical_specification.md), [기능 계약(capability contracts)](../../openspec/specs/)

## 배포 구조

인증(Auth)과 내구성 있는 스케줄링 상태에는 Supabase를, 웹 경계에는 Next.js를, 대화 실행에는 eve를 사용합니다. 웹 서비스와 에이전트 서비스를 별도로 빌드하는 구조를 의도한 방향으로 두며, 기반 검증(foundation spike) 단계에서 영속성(persistence), 디스패처 소유권, 워커 배치, 배포 라우팅을 선택해야 합니다. 이 검증 전에는 별도의 워커나 브리지 앱을 가정하지 않습니다.

사람의 대기 상태와 수락된 작업은 내구성 있는 상태에 저장합니다. 프로세스 메모리, HTTP 응답, 프레임워크 체크포인트만으로는 합의, 승인, 공급자 효과(provider effect)의 유일한 기록이 될 수 없습니다. 모델 공급자는 서버 측에서 선택하고 테스트해야 하며, [모델 실행](../../openspec/specs/model-execution/spec.md) 및 [워크스페이스 메시지 수락](../../openspec/specs/chat-workspaces/spec.md) 계약의 수치 한도를 그대로 유지해야 합니다.

## 데이터베이스 출발점

선택된 프로젝트에는 [공급자 설정](03_provider_setup.md#supabase-project)에 기록된 대로 Phase 1과 Phase 2 마이그레이션이 들어 있습니다. 관리형 ID(identity), Vault 시크릿, 설치된 확장은 인프라일 뿐이며, 호스트 자격(eligibility), 참여자 권한 부여(grant), 대화 바인딩, 스케줄링 정책을 제공하지 않습니다.

스키마 기준선은 애플리케이션 객체를 Data API가 노출하지 않는 비공개 `app` 스키마에 두고, 모든 테이블에 정책 없이 RLS를 활성화하며, `anon`과 `authenticated`의 기본 권한(default privileges)을 회수합니다. 역할 매트릭스와 그 pgTAP 테스트는 [`supabase/README.md`](../../supabase/README.md)에 설명되어 있습니다. 새 테이블과 함수는 이 기준선을 따릅니다. 각 역할로 직접 접근과 RPC 권한 검사를 테스트하고, 관리형 Auth/Storage/Vault 테이블은 수정하지 않으며, 사전 설치된 확장에 대한 전제 조건은 의도적으로 명시합니다.

런타임 기반(runtime foundation)은 격리된 합성(synthetic) 저장소를 사용하며, 테스트 전용 주체(principal)는 프로덕션과 분리합니다. 재사용 가능한 제품 영속성은 검토를 거친 애플리케이션 마이그레이션 체인을 통해 도입합니다. 호스팅 환경의 스키마/API를 활성화하거나 실제 효과를 일으키기 전에 대상 자격 증명을 식별하고, 경쟁하는 소비자(consumer)를 펜싱(fencing)해야 합니다.

## 모듈 경계

| 모듈 | 책임 |
|---|---|
| 신원/호스트 자격 | 검증된 호스트 신원, 활성 호스트 계정, 공유 자격-준비도 가드(eligibility-and-readiness guard), 요청 범위의 게스트, 현재 권한 부여, 채널 바인딩, 철회 |
| 온보딩 | 재개 가능한 초안, 캘린더 역할, 명시적 선호, 준비도, 안정적 핸들 |
| 요청/대화 | 접수(intake), 리비전이 있는 상태, 수명주기, 정규 행위자/리소스/대상(actor/resource/audience) 바인딩 |
| 실현 가능성 | 결정적(deterministic) 가용성, 하드 규칙, 버퍼, 이동, 제한된 평가 |
| 제안/결정 | 불변 버전, 공유 합의, 비공개 예외, 귀속 가능한 현재 호스트 승인 |
| 예약 | 내구성 있는 신원/예약(reservation), 최종 재검증, 공급자 생성 및 조정(reconciliation) |
| 전달 | 고정된 수신자/내용, 공급자 디스패치 식별자, 정확한 전달 상태 |
| 운영 | 비식별 진단, 한도, 소비자 소유권, 감사되는 복구, 백업/복원 |

웹, MCP, CLI, 채널 어댑터는 얇게 유지하며 모두 동일한 권한 검사를 거친 작업을 호출합니다. 공급자 어댑터는 좁은 포트(port)를 구현합니다. 도메인 모듈은 브라우저 쿠키나 프레임워크 고유의 요청 타입에 의존하지 않으며, [소스 구성](02_frontend_architecture.md#source-organization)이 향후 레이아웃을 정의합니다.

## 권한 부여 아키텍처

비공개 데이터나 모델 컨텍스트를 선택하기 전에 먼저 인증합니다. Google 로그인을 완료하면 활성 상태의 호스트 계정이 생성되며, 호스트 자격은 Google 로그인 및 캘린더 동의와 별도로 검증합니다. 도메인 계층의 공유 자격-준비도 가드 하나가 이를 결정합니다. 호스트 설정, 캘린더 연결, 모든 호스팅 작업에는 활성 호스트 계정이 필요하며, 공개 예약 프로필에는 추가로 완료된 설정이 필요합니다. 완료된 설정이란 확인된 규칙, 시간대, 고유한 핸들, 쓰기 가능한 예약 대상 캘린더를 뜻합니다. 이 단일 가드는 나중에 초대 조건을 추가할 수 있는 지점이기도 합니다. 남용 방지 수단은 가입 및 핸들 변경에 대한 속도 제한(rate limit), 예약된 핸들(reserved handle), 운영자의 정지이며, 구체적인 한도는 호스트 계정 변경의 설계에서 정합니다. 운영자는 호스트 정지와 복원, 비공개 진단, 감사되는 복구를 위해 별도의 관리자 CLI를 사용합니다. 요청자의 지속 접근(continuation)은 하나의 요청에만 권한을 부여하며, 공개 핸들과 ID는 비공개 접근 권한을 주지 않습니다. 개인 에이전트에 대한 권한 부여에는 현재 소유자/리소스/범위(scope) 검사와 철회가 필요합니다. 운영자 권한은 사용자와 그들의 에이전트로부터 분리됩니다.

상태를 변경하는 트랜잭션 안에서 관련 권한과 기대 리비전을 다시 확인하며, 블로킹 대기 이후의 만료도 여기에 포함합니다. 공급자 I/O의 경우 결과를 커밋하기 전에 컨텍스트를 다시 확인합니다. 허용된 대상(audience)에게만 투영(projection)하며, 서버 측 필터링은 직렬화와 모델 컨텍스트 구성보다 앞서 수행합니다. 대화 도구는 대상별로 등록하므로, 그 대상이 써서는 안 되는 도구는 거부되는 것이 아니라 아예 없습니다([권한 계층](04_agent_configuration.md#permission-layers)). 기본/원시(raw) 런타임 엔드포인트는 닫힌 상태로 실패(fail closed)해야 합니다.

### MCP OAuth 및 CLI

[에이전트 클라이언트 인가](../../openspec/specs/agent-client-authorization/spec.md)의 리소스별 토큰, 명시적 범위 동의, PKCE, 정확히 등록된 콜백, 디스커버리, 현재 권한 부여 검사, 리프레시/철회 의미 체계를 사용합니다. Supabase 로그인이나 캘린더 토큰은 이 경계를 대체할 수 없습니다. SDK 픽스처에서 인증이 성공했다고 해서 특정 이름의 클라이언트가 동작한다는 증거가 되지는 않습니다.

[`agent-access` 변경](../../openspec/changes/agent-access/design.md)은 인가 서버를 웹 서비스에 내장합니다. 나열된 각 오리진이 그 자체로 발급자(issuer)이고, `/mcp`는 호스트 리소스, `/{handle}/mcp`는 준비된 호스트 한 명의 요청자 리소스이며, 액세스 토큰은 `AGENT_TOKEN_SIGNING_KEY`로 서명한 Ed25519 JWT이고, 코드, 리프레시 패밀리, 권한 부여, 클라이언트는 비공개 `app` 스키마에 둡니다. MCP 핸들러는 무상태이며 현재 및 핸드셰이크 프로토콜 리비전을 제공하고, 도구는 재시도 키를 권한 부여에 결합한 채 명령 파이프라인을 통해 웹과 동일한 명령 및 프로젝션을 호출합니다. 호스트의 승인과 거절은 `/app`에서의 클릭으로 남습니다.

계정 없는 요청자의 부트스트랩: `/{handle}/mcp`의 동의 페이지는 해당 호스트를 보여 주고 하나의 미래 요청에 대한 권한을 부여합니다. `create_request`는 재시도 시에도 정확히 하나의 요청만 생성하고, 예약 링크를 요청자 본인의 이메일로 보내며, 권한 부여를 그 요청으로 영구히 제한합니다. 두 CLI는 [CLI 방향](05_cli.md)에 설명되어 있습니다.

## 명령 및 조회 파이프라인

각 명령은 검증된 의도, 리소스 ID, 기대 리비전, 안정적인 재시도 식별자를 담습니다. 제안에 대한 결정은 현재 버전을 명시합니다. 신원, 범위, 사람 확인 증거는 서버 측에서 도출하며, 호출자가 넘긴 불리언 값과 모델의 주장은 증거가 아닙니다.

권한 확인, 검증, 문서화된 순서의 잠금, 재확인, 도메인 전이 적용, 내구성 있는 작업의 게시를 원자적으로 수행합니다. 멱등성(idempotency) 입력을 고정합니다. 정확히 같은 재시도는 같은 결과를 반환하고, 내용이 바뀐 재시도는 충돌로 처리합니다. 조회는 대상(audience)에 안전한 투영과 소유자에 묶인 안정적인 페이지네이션을 사용합니다. 오류 출력은 타인의 리소스 존재 여부나 시크릿을 드러내지 않아야 합니다. [애플리케이션 명령](../../openspec/specs/application-commands/spec.md)을 따릅니다.

## 호스트 설정과 캘린더 분석

활성 호스트의 초안은 확정된 정책과 분리해서 유지합니다. 명시적 선택을 우선하고, 다음으로 승인된 증거, 마지막으로 라벨이 붙은 시작용 기본값을 사용합니다. 제한적이며 공개된 증거를 사용해 실제로 보이는 캘린더를 추천하고, 충돌 캘린더는 쓰기 가능한 예약 대상 캘린더와 따로 검토하며, 확인한 경우에만 저장합니다. 저장된 충돌 캘린더는 과거/다음 4주에 걸쳐 자동으로 분석하되 [분석 보존](../../openspec/specs/calendar-analysis-retention/spec.md) 규칙의 제한을 받으며, 시작 시각 및 요일 분포, 참석자 이메일 도메인별로 나눈 주간 미팅 부하, 메모성 이벤트 분류, 가장 빈번한 지역과 장소를 각각 표본 수와 함께 산출합니다. 빈 시간, 반복되는 장소, 분류 결과는 제안의 근거일 뿐이며 호스트가 확인하기 전에는 선호가 되지 않습니다. 확정된 주당 미팅 상한은 하드 제약이 아니라 실행 가능성 판단에 적용되는 선호 규칙입니다.

모드/장소는 명시적으로 묻습니다. 대면/둘 다 가능 모드에는 이동수단 또는 이동 1회당 정책과 추가 버퍼가 필요하며, 온라인 전용에서는 이 항목들을 생략합니다. 캘린더 메타데이터, 초안/규칙 리비전, 현재 권한은 최종 설정 확인 시점에도 유효해야 합니다. 호스트 발송 연결 코드 방식의 iMessage 연동과 비공개 채널에서의 답변/설정 확인은, 새로 작성될 소유 변경(owning change)이 검토되기 전까지 제안된 델타로 남습니다. 오래된 제안은 명시적 값을 덮어쓰지 않습니다.

## 요청 수명주기와 실현 가능성

[미팅 요청](../../openspec/specs/meeting-requests/spec.md)을 유지합니다. 즉 계정 없이 가능한 영어/한국어 접수 완료, 검토된 추출, 현재의 불변 제안, 보호된 지속 접근, 종료를 보존합니다. 처리 가능한 요청은 생성 7일 후 또는 요청된 시간 범위의 종료 시점 중 더 이른 때에 만료됩니다. 무작위 예약 링크가 요청자의 유일한 자격 증명이며 최대 30일간 유지됩니다. 요청이 종료되면 변경 및 OAuth 권한이 제거되고, 만료 전에는 허용된 최소한의 종료 영수증(terminal receipt)에 대한 접근만 남습니다.

하나의 동의 화면이 둘을 함께 요청하더라도 선택적 Google 신원과 캘린더 동의를 별개의 권한 부여로 기록하고, 둘 다 요청 권한과 구분합니다. 변경되었거나 수동으로 입력한 참석자 주소에는 증명이 필요하며, 이메일이 일치한다는 이유로 요청을 병합하지 않습니다. 요청자 캘린더에 실패가 발생하면, 재연결되거나 명시적인 수동/에이전트 가용성이 이를 대체할 때까지 그에 의존하는 평가를 일시 중지합니다.

[미팅 실현 가능성](../../openspec/specs/meeting-feasibility/spec.md)을 따릅니다. 전체 시간 구간, 날짜별 시간대/DST, 야간 시간 범위, 바쁨/집중 시간 제약, 양쪽의 대면 이동 구간을 평가합니다. 알 수 없거나 실패한 경로 데이터를 이동 시간 0으로 해석해서는 안 됩니다. 호스트의 예외는 선호만 면제할 수 있습니다. 온라인 이동과 경로 지리/이동수단은 최종 동작이 승인되기 전에 해당 변경에서 해결합니다. 모델은 유효한 후보에 순위를 매기고 명확화 질문을 제안할 뿐이며, 하드 제약을 완화하거나 확정된 정책을 작성할 수 없습니다.

## 승인, 예약, 복구

공유 세부 사항에 대한 요청자의 합의와, 해당하는 비공개 예외를 포함한 현재 제안에 대한 귀속 가능한 호스트 승인이 필요합니다. 변경이 생기면 영향을 받는 결정은 무효가 됩니다. 채널이나 클라이언트가 정확한 사람의 귀속을 확립할 수 없다면 보호된 웹 검토를 사용합니다. 자연어로 된 동의만으로 보호된 확인 계약을 우회해서는 안 됩니다.

생성 전에 예약 신원, 선택된 대상 캘린더, 공급자에서 유효한 이벤트 식별자, 고정된 페이로드, 예약(reservation), 시도(attempt)를 영속화합니다. 같은 호스트에 대한 동시 요청을 조율하고, 디스패치 직전에 실현 가능성을 다시 확인합니다. 불확실한 쓰기는 보류 상태로 남고 조정(reconciliation)이 결과를 확정할 때까지 예약을 유지합니다. 명확히 거부된 재시도에는 현재 결정과 새로운 재검증이 필요합니다. 전달/읽음 확인(receipt)만으로 예약이 이루어졌다고 주장해서는 안 됩니다.

영수증, 확인 이메일, 캘린더 이벤트는 확정된 이벤트 데이터로부터 생성하며, 비공개 대화 자격 증명을 공유 이벤트 설명에 넣지 않습니다. 전달 실패는 독립적으로 복구할 수 있어야 하며 또 다른 이벤트를 만들어서는 안 됩니다. [확인 설계](../user_experience/03_interfaces.md#booking-confirmation-email-and-calendar-invitation)를 참고하십시오. 승인된 예약과 알림의 상세 동작은 해당 변경이 시작되기 전에 보류 중인 명세로 다시 작성해야 합니다.

## 작업, 인박스, 아웃박스

인증된 공급자 입력은 확인 응답(acknowledge)을 보내기 전에 내구성 있게 기록합니다. 공급자 ID로 중복을 제거하고, 수신자 세대(receiver generation), 검증된 발신자/스레드 바인딩, 선택된 요청/대상을 고정합니다. 전달된(forwarded) 링크, 표시 이름, 인용된 주장은 권한을 부여하지 않습니다. 하나의 전송 수단(transport)에는 의도한 소비자가 하나여야 하며, 경쟁하는 배포는 활성화 전에 펜싱해야 합니다.

작업(job)은 도메인 전이와 함께 원자적으로 게시합니다. [내구성 있는 작업](../../openspec/specs/durable-jobs/spec.md)의 제한된 리스(lease), 소유권 펜싱, 복구 가능한 깨우기(wake-up), 재전달에 안전한 완료를 사용합니다. 발신 작업은 디스패치 전에 경로, 수신자, 내용을 고정합니다. 각 공급자의 실제 멱등성 윈도를 확인하며, 불확실성이 그 윈도를 넘어서면 무작정 재전송하지 않고 조정하거나 감사되는 복구 결정을 요구합니다.

### 이메일 공급자 방향

Cloudflare는 연락처 인증 및 복구 메시지와 예약 확정 알림을 전달합니다. AgentMail은 요청자 대화용 인박스, 스레드, 답장을 담당합니다. Google 전용 호스트 로그인을 위해 MVP 배포에서는 Auth 이메일 로그인을 비활성화해야 하며, 현재 호스팅 설정은 이번 스키마 점검으로 검증되지 않았습니다. 트랜잭션 이메일 설정은 호스트 로그인과 독립적입니다. 호스트 비공개 이메일은 초기 릴리스 범위 밖에 있습니다.

### iMessage

Photon Spectrum이 선택된 전송 수단 방향입니다. 호스트가 보낸 일회용 연결 코드는 모델 턴 이전에 채널이 소비하고 인증된 브라우저에서 확인되면 그 발신자를 활성 호스트에 바인딩합니다. 코드는 로그인 전에 랜딩에서 시작할 수도 있으며, 어느 시작이든 Google 로그인과 브라우저 확인 이후에만 바인딩됩니다. Photon의 공유 회선은 먼저 문자를 보낸 적 없는 번호로 가는 첫 메시지를 거부하므로 서비스가 보내는 대체 코드는 제공하지 않습니다([`host-imessage-channel`](../../openspec/changes/host-imessage-channel/proposal.md#decisions) D15, D16). 연동되지 않은 발신자와 그룹 발신자에게는 비공개 상태를 보여주지 않습니다. 디스패치 전에 명시적인 요청 선택을 고정하며, 모호한 답장은 요청을 선택하거나 제안을 승인하지 않습니다. 연동 해제는 이후의 접근을 철회합니다. 연락처 카드 저장은 선택 사항이며 신원 증명이 되지 않습니다. 6단계 스파이크는 애플리케이션 자체 어댑터를 선택했습니다. 수신을 확인 응답하기 전에 영수증을 저장하는 서명된 수신기와, 결과가 불확실한 전송은 절대 반복하지 않는 발신함(outbox)입니다 ([`host-imessage-channel` 설계 1](../../openspec/changes/host-imessage-channel/design.md#1-the-transport-spike-and-the-adapter)).

같은 회선이 게스트에게도 쓰입니다([`guest-flow-completion` 설계 1–5](../../openspec/changes/guest-flow-completion/design.md#1-guest-linking)). 요청이 소유한 연동 코드를 예약 페이지에서 확인하면 호스트 바인딩과 별개인 `requester_imessage_bindings` 행이 만들어지므로, 한 번호가 호스트이면서 여러 요청의 게스트일 수 있습니다. 메시지는 회선이 그 번호로 마지막으로 보낸 메시지를 따라갑니다. 게스트 알림이나 답장 뒤라면 그 요청의 요청자 논의에 `[iMessage] …`로 들어가고 턴의 최종 텍스트가 답장이 되며, 호스트 메시지 뒤라면 호스트 경로를 탑니다. 게스트 알림은 같은 알림 작업과 발신함을 거쳐, 이벤트의 레코드로부터 예약 링크 없이 고정됩니다. 거절되거나 만료된 요청의 대화에 온 메시지는 수정된 요청 하나를 만들고(`requests.revised_from_request_id`, 고유, 한 체인에 최대 10개) 바인딩이나 이메일 스레드를 그곳으로 옮깁니다.

## 운영과 검증

시크릿, 비공개 텍스트, 공급자 자격 증명은 추적되는 증거와 사용자 로그에 남기지 않습니다. 읽기 전용 비공개 진단과 보호된 감사 복구는 별도의 운영자 권한으로 제공합니다. 합성 데이터로 채운 상태를 격리된 데이터베이스에 복원해 백업을 검증합니다. 로컬/프리뷰/릴리스 환경을 분리하고, 프리뷰의 전달은 기본적으로 펜싱합니다.

각 변경이 반영될 때마다 트랜잭션, 권한 부여/RLS, 호스트 2명/요청자 2명 간 격리, 오래된 결정, 동시 쓰기, 누락된 깨우기, 프로세스 종료, 유실된 공급자 응답, 철회된 권한 부여, 모델 한도, 안전한 투영을 테스트합니다. 픽스처와 함께 새로운 공급자/디바이스/클라이언트 증거가 필요합니다.

## 미결 기술 결정

런타임 배치는 [기반 설계](../../openspec/changes/application-foundation/design.md)에서 제안되며 1단계(Phase 1) 종료 시점에 확정됩니다. OAuth 구현/클라이언트 버전, 규칙/이동 정책, 미팅 링크/캘린더 이벤트 소유권, 전송 수단 할당, 보존, 측정 가능한 한도는 아직 열린 결정 사항입니다. 이 문서는 테이블/RPC 이름, 정확한 엔드포인트 내부 구현, 실행 가능한 명령을 규정하지 않습니다.
