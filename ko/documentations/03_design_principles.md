# Find Me a Time — 설계 원칙

날짜: 2026-10-19\
상태: 제품 방향. 구현 범위는 별도로 검증해야 합니다.

이 원칙은 웹 앱, 대화형 에이전트, 개인 에이전트 연동, 명령줄 도구 전반에서 새 기능과 검토를 이끄는 지침입니다. [원 페이저](01_one_pager.md) 및 [제품 요구사항](02_product_requirements.md)을 보완합니다. 세부 동작은 기능(capability) 명세에 속하며, 구현 변경은 저장소의 OpenSpec 워크플로를 따릅니다.

우리의 AI 일정 조율 에이전트의 이름은 **Thyme**입니다. 어시스턴트의 채팅 정체성, 소개, 대화 속 언급에는 Thyme을 사용합니다. **Find Me a Time**은 계속 제품 이름입니다.

[시각 디자인 가이드](../DESIGN.md)는 Thyme의 식물 모티프 정체성, 종이 질감(paper material), 색상, 타이포그래피, 컴포넌트 스타일링 방향을 담당합니다. 이 상호작용 원칙은 계속해서 제품이 어떻게 동작하는지를 규정합니다.

## 1. 에이전트는 사용자의 작업을 수행할 수 있다

우리의 에이전트는 명시적으로 문서화된 사람 전용 작업을 제외하고, 사용자가 제품에서 할 수 있는 모든 일을 할 수 있어야 합니다. 사용자는 원하는 결과를 채팅으로 설명하면 에이전트가 이를 수행하도록 할 수 있어야 하며, 단지 에이전트에 해당 도구가 없다는 이유로 양식으로 보내져서는 안 됩니다.

- 정보를 읽거나 절차를 설명하는 데 그치지 않고, 설정과 이후 변경을 포함한 모든 사용자 대상 기능에 대해 에이전트에게 인가된 연산을 제공합니다.
- 채팅과 대화형 컨트롤은 동일한 기반 상태, 권한, 검증, 작업 결과를 대상으로 동작합니다. 한쪽 화면에서 한 변경은 다른 쪽에서도 보여야 합니다.
- 행위하는 사용자의 권한과 범위를 적용합니다. 사용자 기능 동등성은 에이전트에게 관리자 접근 권한이나 다른 사용자를 대신해 행동할 권한을 부여하지 않습니다.
- 서비스가 작업을 확인한 뒤에만 완료를 보고합니다. 작업을 끝낼 수 없으면 무엇이 남았는지 설명하고 이어갈 방법을 제공합니다.
- 모든 사람 전용 예외에는 명시적인 사유를 기록합니다. 도구의 부재는 구현상의 공백이지 영구적인 예외가 아닙니다.
- 거절이 아니라 제외합니다. 요청자가 호스트 캘린더를 읽는 것처럼 다른 대상이 절대 가져서는 안 되는 기능은 그 대상의 대화에 아예 등록하지 않습니다. 이런 부재는 설계이지 구현상의 공백이 아니며, [권한 계층](technical_specification/04_agent_configuration.md#permission-layers)에 목록이 있습니다.

예를 들어 “충돌 확인에는 내 개인 캘린더와 수업 캘린더를 사용하고, 새 미팅은 내 개인 캘린더에 넣어 줘”라는 요청에서, 캘린더가 모호하지 않고 접근이 인가되어 있다면 에이전트가 이 선택을 한 번에 설정할 수 있어야 합니다. 이름이나 의도한 예약 캘린더가 불분명하면 초점을 좁힌 질문을 해야 합니다.

### 사람의 결정과 동의

기능 동등성은 기존의 동의 및 승인 요건을 그대로 유지합니다. 에이전트는 작업을 준비하고 유효한 사용자 결정을 실행하거나 전달할 수 있지만, 그 결정을 만들어 낼 수는 없습니다.

기존 경계에는 Google 로그인과 공급자 동의, 개인 에이전트에 대한 접근 권한 부여, 현재 미팅 제안에 대한 호스트의 명시적 승인이 있습니다. 선호 조건 제안은 예약을 승인하지 않습니다. 필수적인 선호 조건 검토와 확인은 그대로 적용됩니다. 이러한 경계는 [제품 요구사항](02_product_requirements.md)과 [인터페이스](user_experience/03_interfaces.md)를 참조하십시오.

전체 예외 목록은 기능별로 명세해야 합니다. 사람 전용 단계를 추가로 만들어 내지 말고, 이 원칙을 기존 확인 요건을 없애는 것으로 취급하지 마십시오.

## 2. 선호 조건은 먼저 제안한다

에이전트는 사용자에게 설정을 채우라고 요청하기 전에 유용한 설정을 먼저 제안해야 합니다. 일반적인 경험은 추천을 검토하고 “좋아요”라고 말하거나, 대화로 수정하거나, 간결한 대화형 컨트롤로 조정하는 것입니다.

1. 사용자가 밝힌 선호 조건과 인가된 맥락을 사용해 구체적인 추천안을 준비합니다.
2. 제안한 선택지를 간단히 설명합니다. 필요한 경우 사용자의 명시적 선택, 추론에 따른 제안, 시작용 기본값을 구분합니다.
3. 해당 기능이 요구하는 검토와 확인 규칙을 따르는 범위에서, 사용자가 명확하고 최신인 제안을 채팅 또는 동등한 대화형 동작으로 수락하게 합니다.
4. 정보가 부족하면 초점을 좁힌 질문을 하나 합니다. 설문을 처음부터 다시 시작하지 말고 답변을 바탕으로 추천안을 갱신합니다.
5. 요청이 있거나 선택을 정하는 데 필요할 때 세부 설정 컨트롤을 보여 줍니다. 직접 편집할 수 있도록 유지하되, 기본적인 첫 단계로 삼지는 않습니다.
6. 저장된 내용을 확인해 주고, 대화와 컨트롤이 일관되게 유지되도록 합니다.

예를 들어 “평일 오전 10시–오후 5시, 30분 미팅, 15분 여유 시간을 제안합니다. 괜찮으신가요?”라고 물을 수 있습니다. 사용자는 “네”라고 답하거나, “오후만”이라고 답하거나, 조정 컨트롤을 열 수 있습니다. 이 값은 예시일 뿐 제품의 기본값이 아닙니다.

“네”는 식별 가능한 현재 제안을 가리켜야 합니다. 제안이 바뀌었거나 지시 대상이 모호하면, 적용하기 전에 확인합니다. 제안이 확정된 선호 조건을 조용히 덮어써서는 안 되며, 이용할 수 없는 데이터에 대한 동의를 추정해서도, 필수적인 최종 검토를 우회해서도 안 됩니다. 현재 계약상 보호된 확인 화면이 필요한 경우, 에이전트는 해당 검토를 준비하고 사용자를 그곳으로 안내합니다. 그 계약을 바꾸려면 별도의 동작 변경이 필요합니다.

## 3. 사용자용 CLI와 관리자용 CLI를 분리해 제공한다

제품에는 서로 구분된 두 개의 명령줄 인터페이스가 있어야 합니다. 하나는 사용자와 그들의 인가된 에이전트를 위한 것이고, 다른 하나는 우리 팀이 서비스를 관리하기 위한 것입니다.

| | 사용자 CLI | 관리자 CLI |
|---|---|---|
| 대상 | 호스트, 요청자, 그들의 인가된 에이전트, 사용자 스크립트 | Find Me a Time을 운영하는 승인된 팀 구성원 |
| 목적 | 터미널에서 역할에 맞는 제품 작업 수행 | 권한이 필요한 서비스 관리 수행 |
| 예시 | 요청 상태 읽기, 인가된 선호 조건 설정, 미팅 조율, 필수적인 사람 검토 이어가기 | 호스트 정지 또는 복구, 비공개 진단 조회, 감사(audited) 복구 작업 수행 |
| 권한 | 로그인한 사용자 또는 위임된 클라이언트의 범위가 한정된 권한 | 해당 환경에 대한 명시적 운영자 인가 |
| 인터페이스 경계 | 관리자 명령이나 서비스 자격 증명 없음 | 별도의 명령 진입점, 인증, 문서 |

두 CLI 모두 다른 인가된 화면과 동일한 도메인 연산과 검증을 사용해야 하며, 자동화에 적합한 구조화된 결과를 반환하고, 오류와 미완료 작업을 명확하게 알려야 합니다. 두 CLI의 권한은 서버에서 분리되어 있어야 하며, 사용자 도움말에서 관리자 명령을 숨기는 것만으로는 충분하지 않습니다. 관리자 CLI를 사용자 연결의 상승된 모드로 구현해서는 안 됩니다.

### 계획된 도구와 남은 결정 사항

[CLI 방향](technical_specification/05_cli.md)은 향후의 사용자 및 관리자 화면을 정의합니다. 명령이나 기능 동등성은 아직 구현되지 않았습니다.

최종 실행 파일 이름, 패키징/배포, 전체 명령 목록, 관리자 인증은 아직 명세해야 하는 구현상의 결정입니다. 이 문서는 명령을 만들어 내거나 검증되지 않은 지원을 주장하지 않고, 두 개의 CLI라는 방향만 확립합니다.

## 4. 한 번에 하나만 생각하게 한다

사용자가 너무 많이 생각하게 해서는 안 됩니다. 각 순간에는 결정 하나만 요청하고, 그 결정이 끝난 뒤에야 다음 결정을 보여 줍니다.

1. 대화에서는 한 번에 아티팩트, 카드 또는 질문 하나만 보여 줍니다. 사용자가 훑어보고, 비교하고, 스크롤하며 오가야 하는 여러 카드를 쌓아 두지 않습니다.
2. 각 아티팩트는 작게 유지합니다. 제목으로 쓰는 질문 하나, 출처가 붙은 제안 답변, 짧은 이유 하나, 그리고 액션으로 구성합니다. 작성창 위에서 휴대폰 뷰포트에 들어맞아야 하며, 긴 편집기는 카드 안에서 스크롤됩니다.
3. 결정에 필요한 근거는 그 결정의 아티팩트 안에 두고, 그 밖의 내용은 접힌 펼침 영역 뒤에 둡니다.
4. 진행 상황(“9단계 중 3단계”)과 되돌아갈 방법을 보여 주어, 한 번에 한 단계씩 나아가도 이전 답변이 숨겨지지 않게 합니다. 최종 검토에서는 모든 답변을 하나의 간결한 목록으로 모아 보여 줍니다.

첫 호스트 온보딩 호스팅 테스트에서 큰 카드 여러 개가 한꺼번에 나타나 설정을 따라가기 어려웠던 점을 반영해 2026-10-20에 추가했습니다.

## 원칙 적용하기

각 기능마다 다음을 검토합니다.

- 사용자가 에이전트에게 해당 작업을 수행하도록 요청할 수 있으며, 모든 예외가 명시되어 있는가?
- 에이전트가 수동 설정을 요구하기 전에 유용한 제안을 먼저 제시하는가?
- 필수 확인을 유지하면서, 채팅에서의 수락과 대화형 컨트롤이 동일한 인가된 결과에 도달할 수 있는가?
- 각 순간이 사용자에게 한 가지만 요청하며, 화면에 들어맞는 작은 아티팩트를 사용하는가?
- 이 기능은 사용자 CLI, 관리자 CLI, 또는 서로 다른 인가를 갖는 양쪽 모두에 속하는가?

공백은 범위가 한정된 OpenSpec 변경으로 추적합니다. 이러한 변경이 구현되고 검증됨에 따라 해당 기능 명세를 계속 정렬해 두십시오.
